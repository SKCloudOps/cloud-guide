Quick notes

One screen to skim right before you walk in.

Agentic AI

  • Planning styles: ReAct, Plan-and-Execute, Reflection
  • An agent = an AI + tools + memory + a loop with a stop rule
  • Safety: step limit, spend limit, allowed tools, checks
  • Team of agents: planner, worker, checker
  • Test the path it took, not just the final answer

GraphRAG

  • Vector search = find similar text. Graph = real links.
  • Use both for multi-step and big-picture questions
  • Build it: pull out things and links, then group them
  • Narrow question = nearby graph. Broad question = summaries
  • Every answer must point back to a real source

Context + MCP

  • Chunk by meaning, then test the size
  • Add labels: source, section, things, date
  • Summarise long text, do not just cut it off
  • MCP = a standard way to connect AI to tools and data
  • The MCP server is the safety boundary

Semantic systems

  • Ontology = the types of things, their traits, and links
  • SPARQL queries RDF facts. Cypher queries Neo4j graphs.
  • A catalog is the agent's map of what data exists
  • Make search easy: short paths, clear link names
  • Auto-tag with NLP + AI, mapped to ontology terms

Worked examples

Open-ended design questions. Two are named in the job post. Talk through the steps out loud and draw the boxes.

1. Credit risk agent (named in the job post)

"Build an agent that helps an analyst judge the credit risk of a company client, using our knowledge graph of companies, filings, and links."

How I frame it

This needs several steps of linked reasoning, which is exactly where GraphRAG shines. Credit risk is not one document. It is a web: the client, its sub-companies, its guarantors, shared directors, its industry, and past filings. Plain text search loses those links. So I use the graph to follow the links and vector search to read the filings and news.

The design

A planner agent splits the request into steps: find the companies, map the exposure, pull the financial signals, then write the risk summary. Each step is a tool call. Graph tools answer who is linked to whom, behind an MCP server. A search tool pulls the right text from filings and news. A checker agent makes sure every claim in the summary points back to a real source.

Context handling

I attach the source labels to every chunk so the model never uses an unsourced fact. For long filings I summarise the less important parts instead of cutting them off. The risk rules go in a fixed system setting, not the user's question.

Trade-offs to mention

Freedom vs trust. In credit risk the answer must be defensible, so I limit how freely the agent acts, require a source trail, keep a human approving the final risk grade in a POC, and judge the agent on whether its evidence is right, not just the grade.

2. Customer onboarding workflow (named in the job post)

"Build an agent workflow that takes a new customer's data, tags it against our ontology, matches it to existing records, and flags conflicts."

How I frame it

This is auto-tagging plus matching new data against what we already have, which the role mentions directly. The agent's job is to take messy incoming data and make it fit the company's shared dictionary (the ontology).

The design

An intake agent cleans up the new records. A tagging agent reads them and maps the terms to real ontology types, not free text. A matching agent searches the graph for likely matches and scores them. A conflict agent flags the unsure matches for a person, instead of quietly merging them. MCP sits between the agents and the graph so they get a safe, controlled way in.

Context handling

I give the tagging agent the relevant slice of the ontology so it uses real terms. A few examples lock the format.

Trade-offs to mention

Accuracy vs speed. Auto-merging everything is fast but ruins the data on a bad match. So I flag anything below a confidence line for review, and let the business set that line. For a POC, I prove the tagging and matching accuracy on a sample before talking about scale.

3. GraphRAG pipeline over many documents

"We have thousands of internal documents. Build a GraphRAG pipeline that answers both narrow and broad questions."

Walk the steps

Break documents into meaningful chunks. Read them to pull out things and links and build the graph. Group related things and summarise each group for big-picture questions. Build a vector search over the chunks too. When a question comes in, send narrow ones to the graph plus matching chunks, and broad ones to the group summaries. Combine and answer with sources.

Testing

This is where I stand out. I do not ship search on a feeling. I measure how relevant and faithful the answers are on a known test set, and I compare graph-plus-vector against vector-only to prove the graph is helping. If it is not, I cut it.

Trade-offs to mention

Building the graph costs time and money, and it goes stale as documents change. I say that openly and only recommend the graph where multi-step questions need it. For a simple FAQ, plain vector search is right, and I will say so.

4. MCP server for safe access to the graph

"How would you build an MCP server so agents can safely query our knowledge graph and catalog?"

The design

The server is the safety boundary. Agents never get direct database keys. I give them a few clear tools: a safe, limited query tool, a catalog look-up, and read-only data. Small and clear, so the agent cannot run anything it likes or change the data. Login and rate limits live on the server.

Grounded in my work

I have built this. My MCP server for Patient Connect Ops at Takeda runs on EC2, behind a network load balancer, with a private connection and the safety boundary on the server. That is why I think about MCP as a security and design job first.

Trade-offs to mention

A tighter set of tools is safer but less flexible. For a regulated company, that is the right default. I would rather add a tool on purpose than leave an open query door and hope the prompt holds.

"My hands-on work has been with LangChain, LlamaIndex, and AutoGen. If they push on ontologies, RDF, OWL, SPARQL

"I will be straight with you. I am the agent-layer architect, not a full-time ontology expert. I am comfortable working with knowledge graphs, I know the difference between the two main graph styles and how agents query each, and I know how to build the agent and MCP layer that uses an ontology. The deep ontology building is something I would partner with your semantic data architects on, which is how your job post describes it too. My value is making the semantic layer usable by agents."

Simple rule for weak spots

Say the gap honestly in one sentence, connect it to a nearby strength, then stop. Do not over-apologise, and do not bluff. Interviewers trust I would partner on that far more than a fake expert.

Good questions to ask them

  • How built-out is the semantic layer today, and who owns the ontology?
  • What does POC success mean here: a demo, a proven accuracy number, or a path to production?
  • When a POC works here, what happens to it? Does another team take it to production, or does this team carry it forward? (This tells you how stable the role is.)
  • Is the knowledge graph the RDF style or the property style, and how is it queried today?
  • Are you standardising on MCP across teams, or is this fresh ground?
  • How do the agent architect and the semantic data architects split the work day to day?
