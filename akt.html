Architecture

10 questions
Q1

Walk me through an AWS architecture you designed from scratch.

A multi-tier enterprise web platformCloudFront + WAF at the edge for CDN/DDoS protection; Route 53 with latency-based routing; API Gateway with custom Lambda Authorizers; stateless microservices hosted on EKS across 3 Availability Zones; Aurora MySQL Multi-AZ for transactional data; ElastiCache Redis for session caching; S3 with KMS for static assets; and Terraform/GitHub Actions for automated GitOps infrastructure delivery.
Q2

How do you design a highly available application on AWS?

Deploy compute across at least 3 AZs behind an ALB/NLB; use Auto Scaling Groups (or EKS node pools); decouple components asynchronously using SQS / EventBridge; use Aurora Multi-AZ for seamless database failover; manage DNS routing via Route 53 health checks; and cache static content at edge locations via CloudFront.

Q3

How do you achieve multi-region disaster recovery?

Choose a strategy based on RTO/RPO requirements

Backup & Restore (RTO/RPO hours)S3 Cross-Region Replication (CRR), cross-region AWS Backup.
Pilot Light (RTO tens of mins)Core data continuously replicated (Aurora Global Database, DynamoDB Global Tables), compute templates ready in standby region via Terraform.
Warm Standby (RTO mins)Scaled-down production replica running in DR region.
Active-Active (RTO ~0, RPO ~0)Route 53 Application Recovery Controller (ARC), Multi-Region Aurora/DynamoDB Global Tables.
Q4

How do you design for 99.99% availability?

99.99% availability allows maximum 52.6 minutes of downtime per year. Requires zero single points of failure (SPOFs), multi-AZ active-active deployment, stateless compute layers, automated circuit breakers (AWS App Mesh/Envoy), health checks with rapid automated failover, and non-disruptive Canary/Blue-Green deployments.

Q5

Explain your architecture review process.

Perform periodic AWS Well-Architected Framework Reviews (WAFR) across all 6 pillars. Identify High/Medium Risk Issues (HRIs/MRIs), create prioritized backlog remediation tickets, maintain Architecture Decision Records (ADRs) in Git, and enforce security/cost compliance guardrails using AWS Config and AWS Security Hub.

Q6

How do you decide between ECS, EKS, EC2, and Lambda?

LambdaEvent-driven, execution <15 mins, stateless, rapid scaling, zero server management.
ECSContainerized apps seeking low operational overhead within a pure AWS-native ecosystem.
EKSComplex microservices requiring Kubernetes API standardization, Helm/ArgoCD tooling, and multi-cloud portability.
EC2Stateful legacy monoliths, custom OS kernel requirements, or continuous 24/7 fixed compute workloads.
Q7

What are the AWS Well-Architected pillars?

Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, and Sustainability.

Q8

How do you reduce cloud costs without impacting performance?

Right-size instance types; purchase Compute Savings Plans / Reserved Instances for baseline workloads; use Spot Instances for fault-tolerant/batch workloads; enforce S3 Lifecycle Rules and Intelligent-Tiering; eliminate unattached EBS volumes and idle Elastic IPs; and optimize database provisioned IOPS.

Q9

How do you migrate a monolithic application to AWS?

Follow the 6 Rs framework (Rehost, Replatform, Refactor, Repurchase, Retire, Retain). Lift-and-shift initially using AWS Application Migration Service (MGN) to minimize downtime, then strangulate the monolith incrementally into containerized/serverless microservices behind API Gateway (Strangler Fig Pattern).

Q10

Explain a cloud migration you led.

Led a migration of monolithic legacy appscontainerized the application tier onto EKS, migrated relational databases to RDS Aurora using AWS DMS with minimal downtime, automated infrastructure via Terraform, and refactored CI/CD pipelines into GitHub Actions.

AWS Networking

10 questions
Q11

Explain your VPC design.

A /16 CIDR block spanning 3 AZs. Each AZ contains three subnet tiers

Public SubnetInternet Gateway (IGW), ALBs, NAT Gateways.
Private App SubnetEKS worker nodes, ECS, Lambda tasks (routes egress traffic through NAT Gateway).
Isolated DB SubnetRDS Aurora, ElastiCache (no route to the internet).

Uses VPC Endpoints (Gateway & Interface) to keep AWS service traffic off the public internet.

Q12

Public vs Private subnet?

Public SubnetHas a direct route (0.0.0.0/0) to an Internet Gateway (IGW); resources can be assigned public IPs.
Private SubnetNo direct route to an IGW; egress traffic is routed via a NAT Gateway located in a public subnet.
Q13

NAT Gateway vs Internet Gateway?

Internet Gateway (IGW)Scalable VPC component enabling bi-directional communication between public subnet resources and the public internet.
NAT GatewayManaged service allowing resources in private subnets to initiate outbound internet connections while blocking unsolicited inbound connections from the internet.
Q14

How does Route53 routing work?

Authoritative DNS service that maps domain names to AWS resources using various routing policies: Simple, Weighted (A/B testing), Latency-based, Failover (active-passive DR), Geolocation, Geoproximity, and Multi-Value Answer.

Q15

Explain Transit Gateway.

A central network transit hub that connects thousands of VPCs and on-premises networks (via VPN or Direct Connect) in a hub-and-spoke topology, replacing complex VPC Peering meshes.

Q16

When would you use VPC Peering?

For high-throughput, low-latency, non-transitive connection between a small number of VPCs (e.g., 2 to 5 VPCs) where Transit Gateway data processing fees are unnecessary.

Q17

Explain Direct Connect.

A dedicated physical network connection from an on-premises data center directly to AWS, providing consistent bandwidth, lower network latency, and reduced data egress costs compared to VPNs over the public internet.

Q18

Hybrid connectivity design?

Dual redundant AWS Direct Connect links connected to an AWS Transit Gateway with dynamic BGP routing, backed up by an IPsec Site-to-Site VPN tunnel over the public internet for automatic failover.

Q19

How do you isolate workloads?

Multi-account architecture managed by AWS Organizations (separate accounts for Dev, Staging, Prod); distinct VPCs per environment; strict Security Groups / NACLs; and governance via Service Control Policies (SCPs).

Q20

Explain Security Groups vs NACLs.

Security GroupStateful, operates at the instance/ENI level, supports Allow rules only, evaluates all rules before making a decision.
NACLStateless, operates at the subnet level, supports Allow and Deny rules, evaluated in strict numerical order.

API Gateway

10 questions
Q21

Describe your API Gateway architecture.

Regional REST/HTTP API Gateway protected by AWS WAF at the front. Requests are authenticated using a custom Lambda Authorizer (validating JWTs against corporate IdP). Integrates directly with EKS services or Lambda functions, with caching enabled at the stage level.

Q22

REST API vs HTTP API?

REST APIFull-featured (API keys, usage plans, request validation, WAF native integration, client SDK generation, X-Ray tracing).
HTTP APIOptimized for speed, up to 70% cheaper, lower latency, native support for OIDC/OAuth2, built for Lambda and HTTP backends.
Q23

Lambda Authorizer vs Cognito?

CognitoManaged identity pool/user pool for standard user management, issuing OIDC/JWT tokens out of the box.
Lambda AuthorizerCustom authorization logic (RBAC, ABAC, database permission checks, parsing custom header signatures).
Q24

JWT validation flow?

Client attaches Bearer JWT token in HTTP header -> API Gateway passes token to Lambda Authorizer -> Authorizer checks cached JSON Web Key Set (JWKS) from Identity Provider -> Validates signature, expiration (exp), issuer (iss), and audience (aud) -> Generates an IAM policy (Allow/Deny) cached by API Gateway.

Q25

How do you implement throttling?

Uses the Token Bucket algorithm. Configured globally across the account, per API stage, or per client usage plan (using API Keys) by setting Rate (average requests/sec) and Burst (maximum concurrent capacity).

Q26

API versioning strategy?

URI path versioning (e.g., /v1/resource, /v2/resource) combined with API Gateway Stages (dev, staging, v1) or custom header routing (Accept-Version: v1).

Q27

How do you secure APIs?

Enforce TLS 1.2+; place AWS WAF in front (OWASP Top 10 rules, rate limiting); require JWT auth via Lambda Authorizers; implement mutual TLS (mTLS); hide private backends in private subnets; and enforce usage plans via API keys.

Q28

Explain custom domain mapping.

Map a human-readable domain name (e.g., api.example.com managed in Route 53 with an ACM SSL certificate) to an API Gateway endpoint using Custom Domain Names and base path mappings.

Q29

Explain request transformation.

Uses Velocity Template Language (VTL) mapping templates to modify, add, or strip HTTP headers, query parameters, or JSON payloads before sending requests to the integration backend or returning responses to the client.

Q30

Explain API caching.

Provision a dedicated cache cluster on an API Gateway stage to store backend responses for a defined Time-To-Live (TTL, default 300s), reducing load on backend microservices and lowering response latency.

Terraform

10 questions
Q31

How do you organize Terraform modules?

Follow a standardized structuremain.tf, variables.tf, outputs.tf, providers.tf. Separate into:
Core Infrastructure ModulesReusable, version-controlled modules (VPC, EKS, RDS) hosted in a central Git repo.
Environment Live Root ModulesEnvironment configurations (environments/dev, environments/prod) invoking version-pinned core modules.
Q32

Explain remote state.

Storing terraform.tfstate centrally in an S3 bucket (with versioning, server-side encryption, and public access blocked) paired with a DynamoDB table for state locking to prevent concurrent executions and state corruption.

Q33

Terraform workspace vs separate backend?

WorkspacesSingle backend storing state for multiple environments in different keys; suitable for non-production variants, risky for production blast radius.
Separate BackendSeparate S3 buckets/accounts for each environment; gold standard for strict security, state separation, and IAM access isolation.
Q34

How do you manage secrets?

Never put plaintext secrets in .tf or state files. Fetch secrets dynamically at runtime from AWS Secrets Manager or HashiCorp Vault using data sources, or inject them via secure CI/CD environment variables (TF_VAR_secret_name).

Q35

How do you manage multiple AWS accounts?

Use AWS Organizations / Landing Zone patterns combined with Terraform Provider Aliases. Define an IAM cross-account deployment role in target accounts and assume it in the deployment pipeline

provider "aws" {
  alias = "prod"
  assume_role { role_arn = "arn:aws:iam::123456789012:role/TerraformDeploymentRole" }
}
Q36

How do you avoid state corruption?

Enforce DynamoDB state locking; enable S3 bucket versioning; execute Terraform exclusively through automated CI/CD pipelines (never local developer machines); avoid manual state edits; and run terraform plan reviews.

Q37

Explain Terraform lifecycle.

Meta-arguments controlling resource creation/destruction behavior

create_before_destroy = true (replaces resources without downtime)
prevent_destroy = true (protects databases/critical assets)
ignore_changes = [tags, scaling_config] (prevents drift on auto-scaled properties)
Q38

Terraform vs CloudFormation?

TerraformMulti-provider/cloud-agnostic, HCL syntax, explicit state file management, flexible ecosystem.
CloudFormationAWS-native, state managed automatically by AWS, declarative YAML/JSON, seamless integration with AWS StackSets.
Q39

How do you review Terraform changes?

Automated Pull Request checks running

terraform fmt & terraform validate

Static security analysis using tfsec or Checkov Cost estimation using Infracost Posting output of terraform plan as a PR comment for team approval.

Q40

How do you promote infrastructure across environments?

GitOps flowfeature branch -> merge to dev (runs terraform apply on Dev) -> release tag to stage -> manual approval gate -> release tag to prod. All environments use the exact same root modules, changing only environment-specific terraform.tfvars.

GitHub & DevOps

10 questions
Q41

Explain your Git branching strategy.

Trunk-Based Development. Short-lived feature branches (feature/ABC-123) created from main. Changes are reviewed via Pull Requests, continuously integrated, and merged into main, which automatically triggers deployments to lower environments and builds release tags for production.

Q42

GitFlow vs Trunk-Based Development?

GitFlowMultiple long-lived branches (main, develop, release, feature, hotfix); high overhead, complex merge conflicts, slow release velocity.
Trunk-BasedSingle main branch with short-lived feature branches; relies on automated CI/CD and feature flags; enables rapid continuous deployment.
Q43

GitHub Actions architecture?

Workflows (.github/workflows/*.yml) triggered by events (e.g., push, pull_request). Workflows contain Jobs running on Runners (GitHub-hosted or self-hosted in EKS via Actions Runner Controller), executing sequential Steps (Actions/scripts).

Q44

Reusable workflows?

Centrally managed GitHub Actions workflow files (workflow_call) that accept inputs and secrets. Allows multiple application repositories to call standard pipelines (e.g., standard security scan, container build, Helm deploy), eliminating duplicate code.

Q45

How do you secure GitHub Actions?

Use OIDC (OpenID Connect) federated authentication with AWS (eliminating long-lived access keys); pin third-party actions to full commit SHAs; grant minimal explicit permissions: scope; enforce secret scanning; and run builds on isolated ephemeral self-hosted runners.

Q46

How do you store secrets?

Pipeline secrets are stored in GitHub Actions Secrets (Environment secrets for stage separation). Runtime secrets are dynamically fetched directly from AWS Secrets Manager via OIDC execution roles.

Q47

Explain deployment approvals.

Use GitHub Environments (e.g., production). Configure environment protection rules requiring designated individual or team approvals before a deployment job targeting that environment can execute.

Q48

Blue-Green deployment?

Maintaining two identical production environments (Blue = live, Green = new release). The pipeline deploys the new artifact to Green, runs automated integration smoke tests, and then switches traffic instantly at the Load Balancer / Route 53 level.

Q49

Canary deployment?

Rolling out a new software version to a small subset of users first (e.g., 10% traffic via ALB weighted target groups or AWS App Mesh). Monitor CloudWatch error/latency alarms; automatically roll back if errors increase, or scale up to 100% if healthy.

Q50

Rollback strategy?

Automated rollbacks triggered by CloudWatch / Datadog alarms during Blue-Green/Canary deployments. For stateful deployments, Git release tags are reverted, triggering automated redeployment of the previous known-good container image and executing database roll-forward migrations.

Kubernetes / Containers

10 questions
Q51

Why EKS instead of ECS?

Industry-standard Kubernetes APIs, portability, rich CNCF ecosystem (Helm, ArgoCD, Istio, Prometheus, Kyverno), granular CRD extensions, and complex pod placement/scheduling policies.

Q52

Explain Ingress.

An API object managing external HTTP/S access to services within a cluster. Handled by an Ingress Controller (e.g., AWS Load Balancer Controller), which automatically provisions and configures an AWS Application Load Balancer (ALB) based on routing rules.

Q53

ALB vs NLB?

ALBLayer 7 load balancer; path-based/host-based routing, TLS termination, WAF integration, sticky sessions.
NLBLayer 4 load balancer; handles millions of requests/sec with ultra-low latency, static IP support, ideal for gRPC, TCP, or UDP traffic.
Q54

Horizontal Pod Autoscaler?

HPA automatically scales the number of pod replicas in a deployment based on observed CPU/Memory utilization (via Metrics Server) or custom metrics (e.g., SQS queue depth via KEDA).

Q55

Cluster Autoscaler?

Automatically adds worker nodes when pods cannot be scheduled due to insufficient cluster resources, and removes underutilized nodes. Modern recommendation: Karpenter for faster, right-sized EC2 instance provisioning directly based on pod requirements.

Q56

How do you deploy applications?

Using GitOps with ArgoCD or FluxCD. Application manifests (Helm charts or Kustomize templates) are maintained in Git; ArgoCD continuously reconciles the cluster state with the target Git repository state.

Q57

Explain Helm.

A package manager for Kubernetes that uses templated YAML manifests bundled into Charts, utilizing a values.yaml file to configure environmental variables across different deployment targets.

Q58

How do you debug failed pods?

kubectl describe pod <pod-name> (check Events for OOMKilled, ImagePullBackOff, node scheduling issues).
kubectl logs <pod-name> --previous (check application crash stack traces).
kubectl exec -it <pod-name> -- /bin/sh (inspect network and local container environment).
Q59

Kubernetes security best practices?

Use IRSA (IAM Roles for Service Accounts); enforce Kubernetes RBAC with least privilege; use Pod Security Standards (Restricted profile); enable network policies (Calico/Cilium); scan container images for vulnerabilities; use read-only root filesystems; and run containers as non-root users.

Q60

How do you upgrade EKS?

Upgrade EKS Control Plane version via AWS/Terraform. Upgrade core cluster add-ons (CoreDNS, kube-proxy, VPC CNI). Upgrade worker node groups using rolling node updates (Karpenter or Managed Node Groups). Verify API deprecations using tools like pluto or kubent.

Security

10 questions
Q61

IAM Role vs IAM User?

IAM UserLong-term identity with permanent credentials (passwords, static access keys); intended for legacy human/system access.
IAM RoleIdentity with temporary security credentials issued via AWS STS; assumed by services, applications, or federated users.
Q62

How do you implement least privilege?

Start with explicit deny-by-default; write granular IAM policies restricted to specific actions and resource ARNs; use condition keys (aws:PrincipalOrgID, aws:SecureTransport); utilize IAM Access Analyzer to trim unused permissions based on activity logs; and set permission boundaries.

Q63

KMS vs Secrets Manager?

KMSCryptographic service for generating, managing, and invoking encryption/decryption keys (Symmetric/Asymmetric).
Secrets ManagerSecure storage service for dynamic secrets (database credentials, API keys) featuring automated secret rotation, versioning, and native KMS encryption integration.
Q64

WAF architecture?

Attach AWS WAF Web ACLs to CloudFront, API Gateway, or ALBs. Configure rule groups including AWS Managed Rules (OWASP Top 10, IP Reputation, SQLi protection) and custom rate-limiting rules to mitigate Layer 7 DDoS and abusive traffic.

Q65

JWT authentication flow?

Client authenticates with IdP -> Receives signed JWT -> Client includes JWT in Authorization: Bearer <token> header -> AWS API Gateway / Application layer extracts token -> Verifies signature using IdP public key (JWKS) -> Grants access based on token claims.

Q66

OAuth flow?

Authorization Code Flow with PKCE (for SPAs/Mobile Apps)Client redirects user to Authorization Server -> User logs in -> Authorization server returns Authorization Code to client -> Client exchanges Code + PKCE code verifier for Access Token & ID Token.
Q67

Zero Trust architecture?

Operating under the assumption that network perimeter defense is insufficient

Validate every identity and request explicitly. Enforce mTLS for all microservice-to-microservice traffic. Grant least privilege access using IRSA and dynamic tokens. Micro-segment workloads using network security policies.

Q68

Encryption at rest vs in transit?

At RestData encrypted on disk using AWS KMS Customer Managed Keys (CMKs) across S3, EBS, RDS, DynamoDB, and EFS.
In TransitTLS 1.2 or TLS 1.3 enforced on all HTTP endpoints (ALB, CloudFront, API Gateway) and inter-service communications.
Q69

SCPs in AWS Organizations?

Service Control Policies (SCPs) set maximum permission guardrails at the Organization, OU, or Account level. They override all local IAM permissions (e.g., explicitly blocking the creation of non-approved AWS regions or preventing S3 buckets from being made public).

Q70

Security monitoring?

GuardDutyIntelligent threat detection (analyzing VPC Flow Logs, CloudTrail, DNS logs).
Security HubCentralized security posture management and compliance checks.
CloudTrailImmutable audit trail of all API calls.
AWS ConfigReal-time tracking of resource configuration changes and compliance drift.

Monitoring

10 questions
Q71

Explain your monitoring architecture.

Observability strategy based on three pillars

MetricsCloudWatch & Prometheus (scraped by OpenTelemetry collector).
LogsCloudWatch Logs / Datadog (structured JSON logs).
TracesAWS X-Ray / OpenTelemetry.

Visualized via Grafana/Datadog dashboards, triggering PagerDuty/Slack alerts via SNS topics.

Q72

CloudWatch Logs vs Metrics?

LogsText/JSON timestamped event records detailing execution flow, debug information, or stack traces.
MetricsNumerical time-series data points representing system performance variables (CPU utilization, latency, error count) sampled over time intervals.
Q73

What is X-Ray?

AWS distributed tracing service that collects application request execution spans across distributed microservices, generating a service map to identify performance bottlenecks and latent calls.

Q74

Explain distributed tracing.

Propagating a unique Correlation/Trace ID through HTTP request headers across all microservice boundaries. Allows developers to trace an entire end-to-end request lifecycle and diagnose slow down points across deep service dependencies.

Q75

How do you troubleshoot latency?

Check high-level CloudWatch/Datadog latency metrics (p95, p99). Inspect X-Ray / OpenTelemetry traces to pinpoint the specific microservice or DB call causing the bottleneck. Analyze DB query execution plans, connection pool saturation, or CPU/Memory throttling on compute nodes.

Q76

What dashboards do you create?

Executive DashboardSLA/SLO metrics, error budgets, cost tracking, system availability.
Application / Service DashboardThe 4 Golden Signals (Latency, Traffic, Errors, Saturation).
Infrastructure DashboardEKS pod health, node resource limits, RDS IOPS, DB replication lag, NAT Gateway throughput.
Q77

Alert strategy?

Alert on symptoms affecting end users (e.g., error rate > 1%, elevated latency) rather than internal causes (e.g., high CPU). Route critical action-required alerts to PagerDuty with runbook links, and low-priority informational alerts to Slack.

Q78

Root cause analysis process?

Establish incident timeline -> Isolate blast radius -> Correlate CloudTrail audit logs with deployment timestamps -> Analyze log traces during the incident window -> Conduct 5-Whys analysis -> Document findings in a blameless Post-Mortem and create preventive automation tasks.

Q79

What metrics matter most?

The Four Golden Signals

LatencyTime taken to service a request.
TrafficDemand placed on the system (RPS).
ErrorsRate of requests that fail.
SaturationHow full the most constrained resource is (Memory, CPU, IOPS).
Q80

Observability vs Monitoring?

MonitoringTracks known metrics to tell you when a predefined system state is bad (addresses "known-unknowns").
ObservabilityMeasures internal system state based on external outputs (Logs, Metrics, Traces), enabling you to infer why something novel failed (addresses "unknown-unknowns").

Cost Optimization

10 questions
Q81

How do you reduce AWS costs?

Right-size compute/DB resources; purchase Compute Savings Plans; adopt Spot Instances for stateless non-prod and batch workloads; turn off dev/stage environments during non-business hours; use S3 Intelligent-Tiering; and delete unattached EBS volumes and idle NAT Gateways.

Q82

Reserved Instances vs Savings Plans?

Reserved Instances (RIs)Direct discount tied to specific EC2/RDS configurations (Instance Family, Region, OS); rigid structure.
Savings PlansFlexible hourly spend commitment ($/hr) covering EC2, Fargate, and Lambda across any region, family, or OS (offering up to 72% savings).
Q83

Spot Instances?

Spare AWS compute capacity available at up to 90% discount compared to On-Demand prices. Subject to 2-minute interruption notices; ideal for fault-tolerant, stateless EKS workloads, CI/CD runners, and batch processing.

Q84

Cost Explorer?

AWS reporting tool that visualizes historical usage patterns, forecasts future spend, identifies top cost drivers, and provides recommendations for Savings Plans and Reserved Instances.

Q85

CloudWatch cost optimization?

Reduce log group retention periods (change default "Never Expire" to 14 or 30 days); filter out debug logs at the application logging driver layer; and limit custom metric cardinalities.

Q86

S3 lifecycle?

Policy rules moving data automatically through storage classes to reduce cost

Standard -> Standard-IA (30 days) -> Glacier Flexible Retrieve (90 days) -> Glacier Deep Archive (180 days) -> Expiration.

Q87

Compute optimization?

Use AWS Compute Optimizer recommendations; migrate x86 workloads to AWS Graviton (ARM64) processors (20% lower cost, up to 40% better price-performance); and use auto-scaling based on real demand.

Q88

Database optimization?

Use Aurora Serverless v2 for unpredictable workloads; introduce ElastiCache Redis in front of relational databases to offload read operations; and right-size instance classes using performance insights.

Q89

Storage optimization?

Migrate legacy EBS gp2 volumes to gp3 (up to 20% cheaper with independent IOPS/throughput provisioning); delete unattached EBS snapshots; and enable S3 Intelligent-Tiering for unknown access patterns.

Q90

Tagging strategy?

Enforce mandatory cost allocation tags (Environment, Owner, CostCenter, Application, ManagedBy) using AWS Config and Terraform variables to assign usage costs directly to business units.

Databases

10 questions
Q91

RDS vs Aurora?

RDSTraditional managed database running community engines (PostgreSQL, MySQL) on standard EBS block storage.
AuroraCloud-native engine; highly performant (3-5x faster), decouples compute from storage; automatically replicates data 6 ways across 3 AZs with self-healing storage up to 128TB.
Q92

DynamoDB vs RDS?

DynamoDBFully managed NoSQL key-value/document database; provides consistent single-digit millisecond latency at any scale; schema-less; HTTP API access.
RDSRelational SQL database; enforcing strict ACID transactions, complex JOINs, rigid schemas, and traditional TCP connections.
Q93

Read replicas?

Asynchronous read-only database copies used to offload heavy read queries from the primary writer database. Can be promoted to a primary database in a disaster recovery scenario.

Q94

Multi-AZ?

Synchronous replication of a database to a secondary Availability Zone for high availability. In the event of primary database failure, AWS automatically performs a DNS failover to the standby replica (RTO < 60s, RPO ~0).

Q95

Database backup strategy?

Automated daily DB snapshots + continuous transaction logs enabling Point-In-Time Recovery (PITR) down to the second (up to 35 days); cross-region snapshot copies for disaster recovery; enforced by AWS Backup.

Q96

Database migration?

Use AWS Schema Conversion Tool (SCT) to convert database schemas between heterogeneous engines, and AWS Database Migration Service (DMS) with Change Data Capture (CDC) for continuous replication with near-zero cutover downtime.

Q97

Connection pooling?

Managing database connection overhead. Use RDS Proxy to pool and share database connections efficiently, preventing application connection exhaustion during traffic surges (especially critical for serverless Lambda applications).

Q98

Aurora Serverless?

On-demand auto-scaling deployment option for Aurora. Instantly scales database compute capacity (ACUs) up or down seamlessly based on application load without dropping active connections.

Q99

Redis use cases?

In-memory caching, user session management, API rate limiting, real-time leaderboards, pub/sub messaging channels, and geospatial indexing.

Q100

ElastiCache architecture?

Managed Redis/Memcached cluster deployed across Multi-AZs with primary-replica replication groups, automatic failover, and cluster mode enabled for horizontal sharding across multiple node groups.

Leadership

Tell us about a difficult architecture decision.

Deciding between EKS and Serverless Lambda for an enterprise core application platform. Evaluated team skillsets, vendor lock-in risk, operational cost, and deployment predictability. Selected a hybrid model (API Gateway + Lambda for stateless event flows, EKS for complex core microservices), documenting trade-offs in an Architecture Decision Record (ADR) to align stakeholders.

Q102

How do you mentor engineers?

Run regular architectural design reviews, pair-program on complex technical implementations, teach first-principles thinking rather than giving direct code answers, and delegate component ownership to help engineers grow into leads.

Q103

How do you handle disagreements?

Rely on objective data and proof-of-concepts (POCs). Frame discussions around business goals and technical trade-offs (cost, complexity, maintainability), document options in an ADR, and practice "Disagree and Commit."

Q104

How do you influence teams without authority?

Build technical trust by listening to team pain points, building working POCs that solve immediate developer friction, demonstrating clear value through proof, and fostering collaborative architecture guilds.

Q105

Describe an architecture review you led.

Led an AWS Well-Architected Review for a business-critical application. Identified high risks around hardcoded secrets and single-region database reliance. Created a prioritized remediation plan, replacing hardcoded keys with AWS Secrets Manager and converting the DB tier to Aurora Multi-AZ.

Q106

How do you prioritize technical debt?

Quantify risk in terms of operational cost, security exposure, or delivery velocity impact. Allocate a fixed budget (e.g., 20% of every sprint) directly to tech debt, infrastructure upgrades, and refactoring tasks.

Q107

How do you communicate with executives?

Abstract low-level technical jargon into business outcomesRisk reduction, Cost efficiency, Speed to market, and Reliability/SLA metrics. Use clear high-level target state architecture diagrams.
Q108

How do you balance speed vs quality?

Build modular, adaptable foundation layers. Ensure non-negotiables (Security guardrails, CI/CD pipelines, Observability) are established on day one, allowing developers to build features rapidly without sacrificing long-term technical integrity.

Q109

Modernizing legacy, fragile CI/CD pipelines into modular, standard GitHub Actions reusable workflows and multi-account Terraform codebases-cutting deployment times by 60%, enforcing automated security scans, and achieving zero-downtime production deployments.

Q110

Describe a project failure and what you learned.

Underestimated cross-region network egress costs during an active-active multi-region data replication pilot. Learned to rigorously profile cross-region network throughput and cost structures during initial POC phases, implementing edge caching strategies upfront.

Run terraform refresh or target-import/taint the corrupted resource (terraform taint <resource_name>), fix the code root cause, and re-run terraform plan/apply.
