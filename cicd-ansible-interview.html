CI/CD & Ansible Interview Questions

Advanced CI/CD pipeline design, GitHub Actions, Jenkins, deployment strategies, and artifact management — plus Ansible architecture, playbooks, roles, Vault, and production automation patterns.

⚙️ CI/CD Fundamentals & Concepts
C1 – C10 CI · CD · Pipelines

Understanding the distinction between Continuous Integration, Continuous Delivery, and Continuous Deployment — and how each stage fits into the software delivery lifecycle — is the foundation of every CI/CD interview.

C1What is the difference between Continuous Integration, Continuous Delivery, and Continuous Deployment?
  • Continuous Integration (CI): Developers merge code to a shared branch frequently (multiple times per day). Each merge triggers an automated build and test suite — catching integration issues early.
  • Continuous Delivery (CD): Every passing build is automatically prepared and proven deployable to production, but the actual deployment trigger is manual. Suitable when business or compliance requires human approval gates.
  • Continuous Deployment: Every passing build is deployed to production automatically with no human intervention. Requires very high test coverage and robust monitoring/rollback capability.
Key distinction: Delivery = always ready to deploy; Deployment = always deployed.
C2What are the key stages in a CI/CD pipeline?
A typical pipeline flows through:
  1. Source: Code push or PR triggers the pipeline (Git webhook).
  2. Build: Compile code, resolve dependencies, produce an artifact.
  3. Test: Unit tests → integration tests → end-to-end tests → coverage gates.
  4. Static Analysis: SAST, linting, dependency vulnerability scan (Trivy, Snyk, SonarQube).
  5. Package & Publish: Build Docker image, push to registry; or package to S3 / Artifactory.
  6. Deploy to Staging: Deploy artifact to a staging/pre-prod environment.
  7. Acceptance Tests: Smoke tests, performance tests against staging.
  8. Deploy to Production: Manual gate (CD) or automatic (Continuous Deployment) with canary/blue-green strategy.
  9. Monitor & Notify: Track error rates, latency; alert on anomalies; auto-rollback on SLO breach.
C3What is a pipeline as code and why is it important?
Pipeline as code means the CI/CD pipeline definition lives in a file versioned alongside the application source code (e.g., .github/workflows/ci.yml, Jenkinsfile, .gitlab-ci.yml).

Benefits:
  • Version control: Every pipeline change is tracked, reviewable, and reversible.
  • PR reviews: Pipeline changes go through the same review process as code.
  • Reproducibility: The pipeline that built version 1.2.3 can be checked out and re-run years later.
  • Consistency: All branches and forks share the same pipeline definition.
  • Auditability: Know exactly who changed what in the pipeline and when.

C5What is a CI/CD artifact and how should artifacts be managed?
An artifact is the immutable, versioned output of a build stage — a Docker image, JAR file, ZIP, binary, or Helm chart — stored in an artifact repository.

Management best practices:
  • Immutability: Never overwrite a published artifact. If a build fails, publish a new version.
  • Versioning: Tag artifacts with Git SHA or semantic version — never use latest for production deploys.
  • Central registry: Use JFrog Artifactory, Nexus, AWS ECR, GitHub Packages, or GitLab Package Registry.
  • Retention policies: Automatically expire old artifacts (keep last 10 builds of non-release branches; retain all release tags).
  • Promotion: Promote the same artifact through dev → staging → prod. Never rebuild for each environment.
C6What is the shift-left security principle in CI/CD?
Shift-left means moving security testing earlier in the pipeline — as close to the developer's commit as possible — rather than leaving it for a late-stage security scan or manual pen test.

Shift-left layers:
  • Pre-commit hooks: Secret scanning (git-secrets, detect-secrets), linting.
  • PR / build stage: SAST (SonarQube, Semgrep, CodeQL), dependency CVE scan (Snyk, Trivy, OWASP Dependency-Check).
  • Artifact stage: Container image scan before push to registry.
  • Deploy stage: DAST (OWASP ZAP) against staging environment.
  • Runtime: RASP, WAF, anomaly detection in production.
Finding a vulnerability at commit time costs ~$100 to fix; in production it costs ~$10,000+.
C7What are pipeline quality gates and how do you implement them?
Quality gates are automated pass/fail checks that block pipeline progression unless defined thresholds are met.

Common gates:
  • Test coverage: Fail if coverage drops below 80% (SonarQube, Istanbul/NYC).
  • Test pass rate: Any failing test fails the pipeline.
  • Code duplication: Block merges if duplication exceeds threshold.
  • Security vulnerabilities: Block on Critical/High CVEs in dependencies or container images.
  • Performance regression: Fail if p95 latency increases >20% vs baseline (k6, Gatling).
  • License compliance: Block GPL-licensed dependencies in proprietary code.
C8What is a monorepo CI/CD strategy and what are the challenges?
In a monorepo (all services in one Git repo), naively running all pipelines on every commit is wasteful and slow.

Affected-only builds: Detect which services changed and run only their pipelines.
  • GitHub Actions: paths filter on workflow triggers; or tools like Nx affected / Turborepo for smart task graphs.
  • GitLab CI: rules: changes: directives per job.
  • Bazel / Buck2: Build-system-level change detection with remote caching.
Challenges: Shared library changes may affect many downstream services (require dependency graph analysis); pipeline configuration sprawl; slow CI if not parallelized; merge queue contention.
C9What is GitOps and how does it differ from traditional CI/CD?
GitOps uses Git as the single source of truth for infrastructure and application desired state. An agent running in the cluster (Argo CD, Flux) continuously reconciles the live state with what is declared in Git — no pipeline pushes deployments.

C10What metrics do you use to measure CI/CD pipeline health?
The DORA (DevOps Research and Assessment) metrics are the industry standard:
  • Deployment Frequency: How often code is deployed to production. Elite = multiple times/day.
  • Lead Time for Changes: Time from code commit to running in production. Elite = <1 hour.
  • Change Failure Rate: % of deployments causing incidents/rollbacks. Elite = 0–5%.
  • Mean Time to Restore (MTTR): How quickly you recover from a failed deployment. Elite = <1 hour.
Additional pipeline-specific metrics: build duration, flaky test rate, queue wait time, cache hit rate.
DORA benchmark: Elite performers deploy 973× more frequently and have 3× lower change failure rates than low performers. The single biggest lever is reducing batch size — smaller, more frequent commits surface issues earlier.
🔁 GitHub Actions & Jenkins Pipelines
C11 – C20 Actions · Jenkins · Runners

Deep knowledge of GitHub Actions YAML structure and Jenkins declarative pipelines separates candidates who have actually built and maintained pipelines from those who only know the theory.

C11Explain the structure of a GitHub Actions workflow file.
A workflow lives at .github/workflows/<name>.yml:
  • name: Display name in the Actions UI.
  • on: Event triggers — push, pull_request, schedule, workflow_dispatch, workflow_call.
  • env: Workflow-level environment variables.
  • jobs: One or more jobs running in parallel (or sequentially with needs:). Each job runs on a runner.
  • steps: Ordered commands within a job — uses: (reusable action) or run: (shell script).
Jobs run in parallel by default. Use needs: [build, test] to enforce ordering. Use strategy.matrix to fan-out across multiple OS or language versions in one job definition.
C12What are GitHub Actions reusable workflows and composite actions?
  • Reusable Workflow (workflow_call): An entire workflow file that can be called from another workflow. Runs as a separate job. Best for sharing complete pipeline patterns (e.g., a standardized deploy workflow) across multiple repos. Inputs, secrets, and outputs are passed explicitly.
  • Composite Action (action.yaml with using: composite): A sequence of steps bundled into a single uses: step. Runs inline within the caller's job — shares the same runner and environment. Best for extracting common step sequences (e.g., setup + auth + deploy steps).
Key difference: Reusable workflow = separate job (own runner, environment isolation); Composite action = steps within the same job.
C13How do you securely pass secrets in GitHub Actions?
  • Repository/organization secrets: Stored encrypted in GitHub; injected as environment variables via env: MY_SECRET: ${{ secrets.MY_SECRET }}. Never printed in logs (masked).
  • OIDC (preferred for cloud): Use permissions: id-token: write + aws-actions/configure-aws-credentials with role-to-assume. GitHub issues a short-lived JWT; AWS/GCP/Azure exchanges it for temporary credentials. No stored cloud credentials at all.
  • Environments: Scope secrets to specific environments (staging, production) with required reviewers for deployment gates.
Never: Echo secrets in run steps, pass secrets as workflow inputs (they appear in logs), or store credentials in the repository.
C14How do you optimize GitHub Actions for speed and cost?
  • Caching: actions/cache to cache node_modules, Maven ~/.m2, pip, Go modules. Cache key on lock file hash — invalidate only when dependencies change.
  • Docker layer cache: cache-from: type=gha with docker/build-push-action to reuse unchanged image layers across runs.
  • Concurrency groups: Cancel in-progress runs when a new commit is pushed to the same PR — avoid wasting minutes on stale builds.
  • Path filters: Only trigger workflows when relevant files change.
  • Matrix parallelism: Fan tests across multiple runners simultaneously.
  • Larger runners: GitHub's 8-core or 16-core runners can halve build time for CPU-intensive builds at proportional cost.
C15What is a self-hosted runner and when would you use one?
A self-hosted runner is a machine you manage that executes GitHub Actions (or GitLab CI) jobs — instead of using GitHub's hosted runners.

When to use:
  • Jobs that need access to private network resources (internal registries, on-prem databases, VPN).
  • Air-gapped environments with no internet access.
  • Specific hardware (GPU for ML builds, ARM for cross-compilation).
  • High-volume pipelines where hosted runner minutes cost more than self-hosted infrastructure.
Security considerations: Self-hosted runners on public repos are a serious security risk — a malicious PR can run arbitrary code on your runner. Restrict to private repos or use ephemeral runners (launch fresh VM per job, terminate after).
C16What is the difference between a declarative and scripted Jenkins pipeline?
  • Declarative pipeline: Structured YAML-like Groovy DSL with a strict pipeline { } block containing stages { }, agent, environment, post { } sections. Easier to read and validate; built-in linting; Blue Ocean UI friendly. Recommended for all new pipelines.
  • Scripted pipeline: Full Groovy code inside a node { } block — maximum flexibility, any Groovy construct is valid. More powerful but harder to read, no structure enforcement, no built-in lint.
You can embed script { } blocks inside a declarative pipeline for the rare cases where you need scripted power within a structured framework.
C17How do you implement parallel stages in Jenkins and GitHub Actions?
Jenkins (declarative): 
stage('Test') {
  parallel {
    stage('Unit Tests')        { steps { sh 'npm run test:unit' } }
    stage('Integration Tests')  { steps { sh 'npm run test:int' } }
  }
}
GitHub Actions — jobs run in parallel by default; use needs: only to serialize: 
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps: [...]

  integration-tests:
    runs-on: ubuntu-latest
    steps: [...]

  deploy:
    needs: [unit-tests, integration-tests]  # waits for both
    steps: [...]
C18How do you handle flaky tests in CI/CD?
Flaky tests (pass/fail non-deterministically) erode team trust in the pipeline and cause false failures.

Detection:
  • Track test failure rates over time (GitHub Actions: test reporting; Jenkins: JUnit trend); flag tests with >2% failure rate on passing builds.
Mitigation strategies:
  • Quarantine: Move flaky tests to a separate suite that doesn't block the pipeline — still run for visibility.
  • Retry with limits: Retry a failing test 1–2 times before marking as failed (pytest-rerunfailures, Jest --retries). Never retry more than 3× — masks real failures.
  • Root cause: Most flakiness comes from: shared state between tests, time-dependent assertions, uncontrolled network calls, race conditions in async code. Fix the root cause — don't just retry.
  • Test isolation: Each test gets a fresh database (test containers), no shared global state.
C19How do you implement environment promotion in a CI/CD pipeline?
Environment promotion means moving the same versioned artifact through a series of environments, with automated tests and manual gates at each stage.

Typical promotion chain: dev → integration → staging → production

Implementation patterns:
  • GitOps promotion: PR-based — a bot auto-updates the image tag in the staging Helm values file; a human approves a PR to update production values.
  • Pipeline environments (GitHub Actions): Define environment: production on a job; configure required reviewers in GitHub settings — pipeline pauses for approval.
  • Jenkins: Use input step for manual approval gates between stages.
  • Feature flags: Deploy to 100% of instances but enable for 5% of users — decouple deployment from release.
C20What is a merge queue and why does it matter at scale?
A merge queue (GitHub Merge Queue, GitLab merge trains) serializes PRs for merging, running CI on each PR combined with the current state of the target branch — preventing the "works on my PR but breaks main" problem.

The problem without it: PR A and PR B both pass CI independently. Both merge concurrently. Their interaction breaks main. This is the "semantic merge conflict" — no textual conflict but a logical one.

With merge queue: PRs are queued and tested as A+main, then B+A+main. If A+B breaks, only the conflicting PR is dropped. Essential for teams merging >10 PRs/day.
Pipeline speed targets: Fast feedback is critical — aim for CI to complete in <10 minutes. If tests take longer, parallelize, use test splitting (pytest-split, Jest --shard), or move slow E2E tests to a nightly schedule rather than every PR.
🚀 Deployment Strategies
C21 – C28 Blue/Green · Canary · Rolling · Feature Flags

Choosing the right deployment strategy balances risk, rollback speed, infrastructure cost, and the ability to validate changes with real traffic before full release.

C21Compare rolling, blue/green, and canary deployments.

C22How does a blue/green deployment work in practice on AWS?
  1. Run the current version (blue) behind an Application Load Balancer (ALB) target group.
  2. Deploy the new version (green) to a separate set of EC2 instances / ECS tasks / Lambda aliases.
  3. Run smoke tests and acceptance tests against the green environment directly (via a test listener rule or internal DNS).
  4. Switch the ALB listener rule to point to the green target group — traffic shifts atomically.
  5. Monitor error rates, latency, and business metrics for 15–30 minutes.
  6. If healthy: terminate the blue environment. If unhealthy: update the listener rule back to blue — rollback in <60 seconds.
AWS CodeDeploy, ECS deployment controller, and Lambda traffic shifting all support blue/green natively. Route 53 weighted routing can also implement blue/green at the DNS level.
C23What is a canary deployment and how do you automate the traffic shift?
A canary deployment routes a small percentage of production traffic to the new version while the rest stays on the stable version — acting as the "canary in the coal mine" for issues.

Automated progressive delivery (Argo Rollouts / Flagger):
  1. Deploy canary at 5% traffic.
  2. Query Prometheus metrics (error rate, latency p99, success rate) every 1 minute.
  3. If metrics are within SLO thresholds: increase to 20%, 50%, 100% automatically.
  4. If any metric breaches threshold: automatically roll back to 0% canary and alert.
AWS CodeDeploy Linear and Canary Lambda/ECS deployment configurations provide the same automation without Kubernetes.
C24What are feature flags and how do they decouple deployment from release?
Feature flags (feature toggles) are conditional code paths controlled by a runtime configuration value — not a code deployment.
  • Deploy: The new code ships to 100% of servers, but behind a flag that is OFF.
  • Release: The flag is turned ON for 1% of users → 10% → 100% — controlled independently of deployment.
Benefits:
  • Instant kill switch — turn off a broken feature without a deployment.
  • A/B testing — compare behavior between flag variants.
  • Trunk-based development — merge WIP code daily without exposing it.
Tools: LaunchDarkly, Unleash, AWS AppConfig, Flagsmith, GrowthBook.
C25How do you handle database schema migrations in CI/CD?
Database migrations are the hardest part of zero-downtime deployments because they must be compatible with both the old and new application version during the transition window.

Expand-contract (parallel change) pattern:
  1. Expand: Add a new column/table alongside the old one. Both app versions work. Deploy app v2 (writes to both old and new).
  2. Migrate: Backfill data into the new column.
  3. Contract: Once all instances run v2, drop the old column in a separate migration.
Tools: Flyway, Liquibase, Alembic, Django migrations. Run migrations as an init container or a pre-deployment step. Always wrap in transactions. Always have a tested rollback script.
C26What is an automated rollback and how do you implement one?
An automated rollback triggers the previous-version deployment when post-deploy monitoring detects an SLO breach — without human intervention.

Implementation layers:
  • Kubernetes / Argo Rollouts: Define analysis metrics (Prometheus); rollout automatically aborts and reverts if thresholds are breached.
  • AWS CodeDeploy: Configure autoRollbackConfiguration — triggers on deployment failure or CloudWatch alarm breach.
  • Lambda: Traffic shifting with a pre-traffic hook that runs tests; CodeDeploy rolls back if the hook fails.
  • Helm: helm rollback <release> <revision> as a post-deploy step triggered by a CloudWatch/Datadog alert webhook.
Key requirement: Automated rollback is only safe if the deployment is truly stateless or schema migrations are backward-compatible.
C27What is immutable infrastructure and how does CI/CD enable it?
Immutable infrastructure means servers are never modified after deployment — instead, a new version is built from scratch and the old one is replaced.

In practice (baked AMI / container pattern):
  1. CI pipeline builds and tests a Docker image (or bakes an AMI with Packer).
  2. The artifact is versioned and pushed to a registry.
  3. Deployment replaces running instances with new ones running the new image — no SSH, no in-place patching.
Benefits: Eliminates configuration drift; deployments are predictable; rollback = launch previous image; security patching = rebuild the image, not patch running servers.
C28How do you implement a CI/CD pipeline for a multi-service (microservices) application?
  • Independent pipelines per service: Each service has its own pipeline, triggered only when its code changes. Deploy independently — no "big bang" releases.
  • Contract testing: Use Pact or Spring Cloud Contract to verify producer/consumer API compatibility without running full integration tests across all services.
  • Shared library pipelines: Extract common pipeline steps (security scan, image build, deploy) into reusable GitHub Actions actions or Jenkins shared libraries.
  • Service catalog / dependency tracking: When a shared library changes, automatically trigger downstream service pipelines.
  • Coordinated releases (rare): When multiple services must deploy together, use Argo CD App of Apps or Helm umbrella charts to orchestrate.
Rollback vs roll forward: For simple bugs, roll forward (fix + deploy) is often faster than a full rollback — especially if the deployment included database migrations. Design your pipelines so a fix can be deployed in <10 minutes.
🔐 CI/CD Security, SLSA & Supply Chain
C29 – C34 SLSA · SBOM · OIDC · Secrets

Software supply chain attacks (SolarWinds, Log4Shell, XZ Utils) have made CI/CD security a top-tier interview topic. Understanding provenance, signing, and least-privilege pipelines is essential.

C29What is SLSA (Supply-chain Levels for Software Artifacts) and what does each level mean?
SLSA is a security framework (pronounced "salsa") that defines progressive levels of supply chain integrity guarantees:
  • SLSA 1: Build process is scripted/automated (not manual). Provenance document generated (what was built, from what source, by what process).
  • SLSA 2: Provenance is signed by the build service. Source is version controlled. Build uses a hosted CI platform.
  • SLSA 3: Build is isolated (no persistent credentials, ephemeral runners). Provenance is non-forgeable. Source is protected from tampering (branch protection, code review required).
  • SLSA 4: Two-person review for all changes. Hermetic and reproducible builds. Highest assurance — required for critical infrastructure software.
GitHub Actions + Sigstore/cosign achieves SLSA 3 relatively easily.
C30What is OIDC-based authentication in CI/CD and why is it superior to stored credentials?
Traditional CI/CD stores long-lived credentials (AWS access keys, GCP service account JSON) as secrets — these are static, long-lived, and a major breach vector.

OIDC flow (GitHub Actions → AWS):
  1. GitHub's OIDC provider issues a short-lived JWT signed by GitHub for the specific workflow run.
  2. The workflow sends this JWT to AWS STS AssumeRoleWithWebIdentity.
  3. AWS verifies the JWT's signature and claims (repo, branch, environment); issues temporary STS credentials (15-minute expiry).
  4. No AWS credentials are ever stored in GitHub secrets.
Benefits: Zero stored credentials; credentials expire with the job; compromise of one run's credentials is useless after 15 minutes; each job gets least-privilege temporary credentials.
C31What is a software supply chain attack and how do you defend against it in CI/CD?
Supply chain attacks compromise a dependency, build tool, or CI system to inject malicious code into legitimate software artifacts (SolarWinds, XZ Utils, event-stream npm package).

CI/CD defenses:
  • Pin dependency versions (lockfiles: package-lock.json, poetry.lock). Pin GitHub Actions to a commit SHA, not a tag: uses: actions/checkout@abc1234.
  • SBOM generation: Know every component in every artifact.
  • Dependency review: GitHub Dependency Review Action blocks PRs that introduce high-severity CVEs.
  • Signed artifacts: Sign images/packages with Sigstore Cosign. Verify signature before deploy.
  • Minimal permissions: GITHUB_TOKEN should use least-privilege (permissions: contents: read only).
  • Ephemeral runners: Fresh runner per job — compromised runner can't persist malware.
  • Private dependency mirror: Proxy npm/PyPI through Artifactory/Nexus — scan before caching.
C32How do you implement least-privilege for CI/CD pipeline permissions?
  • GitHub Actions — GITHUB_TOKEN permissions: Set permissions: {} at the workflow level (deny all), then grant only what each job needs: contents: read, packages: write, id-token: write (for OIDC).
  • AWS IAM — pipeline roles: One IAM role per pipeline stage. The build role can read S3 and ECR; the deploy role can update ECS services. Neither role has admin or iam:* permissions.
  • Separate credentials per environment: The staging deploy role cannot assume the production deploy role — enforced by IAM trust policies.
  • Secrets scoping: GitHub environment secrets are only accessible to jobs targeting that environment — production secrets are never available to a PR build.
C33What is a release train vs continuous deployment and when do you choose each?
  • Release train: Scheduled release cadence (weekly, bi-weekly, monthly). Features are batched — if a feature isn't ready for the next train, it waits. Common in enterprise, regulated industries, mobile apps (AppStore review cycle), or when customers run their own installations (self-hosted software).
  • Continuous deployment: Every merged PR deploys to production automatically. Requires: feature flags for WIP, very high test coverage, automated rollback, strong monitoring, and a culture that tolerates small frequent changes over big infrequent ones.
Key question: What is your customer's deployment model? SaaS = continuous deployment is natural. On-prem software with customer-managed updates = release train is required.
C34How do you test infrastructure changes in a CI/CD pipeline (IaC testing)?
  • Static analysis: terraform validate, terraform fmt --check, tflint — syntax and lint checks before any cloud API calls.
  • Policy as code: Checkov, Terrascan, tfsec — scan for security misconfigurations (public S3 bucket, unencrypted RDS, open security groups) and block on violations.
  • Speculative plan: terraform plan on every PR — show reviewers exactly what will change. Never apply on a PR build.
  • Module testing: Terratest (Go) — spin up real infrastructure in a sandbox AWS account, run assertions, destroy. Slow and costly but provides real validation.
  • Drift detection: Scheduled pipeline runs terraform plan; alerts if drift is detected between desired and actual state.
Pipeline permissions audit: Run gh api /repos/:owner/:repo/actions/permissions and review every workflow's permissions: block. Most security incidents in CI/CD come from over-privileged pipeline tokens, not from external attackers — harden from within.
📋 Ansible Architecture & Core Concepts
A1 – A10 Inventory · Modules · Ad-hoc

Ansible's agentless, push-based architecture and idempotent module system make it a dominant configuration management tool. Understanding how it connects, what it runs, and how it handles state is foundational.

A1How does Ansible work architecturally? What makes it agentless?
Ansible is a push-based, agentless configuration management tool. The control node (your laptop or CI server) connects to managed nodes over SSH (Linux) or WinRM (Windows) — no persistent daemon is required on the target.

Execution flow:
  1. Ansible reads inventory (list of target hosts) and the playbook.
  2. For each task, Ansible generates a Python module script.
  3. The script is pushed to the managed node via SCP/SFTP, executed by the node's Python interpreter, and the results are returned over SSH.
  4. The temporary script is deleted after execution.
Agentless benefit: No agent to install, update, or secure on thousands of nodes. The only requirement is SSH access and Python (≥2.7 or 3.5+) on the target.
A2What is idempotency in Ansible and why is it critical?
An idempotent operation produces the same result regardless of how many times it is run. If the desired state already exists, Ansible does nothing and reports ok instead of changed.

Why it matters:
  • Safe to re-run playbooks at any time — even after partial failures — without side effects.
  • Enables convergence: run the same playbook against 1,000 servers; already-compliant servers are untouched; non-compliant servers are corrected.
  • Drift remediation: scheduled cron runs of playbooks continuously enforce desired state.
Common non-idempotent trap: command: echo "hello" >> /etc/file — appends every run. Fix: use the lineinfile module with create: yes instead.
A3What is an Ansible inventory and what are the different inventory types?
The inventory defines what hosts Ansible manages and how to group them.
  • Static inventory (INI / YAML): A file listing hosts and groups. Simple for small, stable environments.
  • Dynamic inventory: A script or plugin that queries an external source (AWS EC2, GCP, Azure, Kubernetes, Vault) at runtime and returns hosts as JSON. Essential for auto-scaled cloud environments where instance IPs change.
  • Inventory plugins (recommended): amazon.aws.aws_ec2, google.cloud.gcp_compute — configured in inventory.yml, queried automatically by ansible-inventory.
Hosts can belong to multiple groups. Use group_vars/ and host_vars/ directories to assign variables to groups and individual hosts.
A4What is the difference between a module, a task, a play, and a playbook?
  • Module: A reusable unit of work — ansible.builtin.apt, ansible.builtin.copy, amazon.aws.s3_object. Modules are idempotent Python programs.
  • Task: A single invocation of a module with specific arguments and a name: - name: Install nginx / ansible.builtin.apt: name=nginx state=present.
  • Play: A mapping of a group of hosts to a list of tasks. Defines remote user, become (sudo), and variables for that group.
  • Playbook: A YAML file containing one or more plays. The top-level unit you run with ansible-playbook.
Hierarchy: Playbook → Plays → Tasks → Modules.
A5What is gather_facts and what information does it collect?
gather_facts: yes (default) runs the setup module at the start of each play, collecting system facts from each target host:
  • OS family, distribution, version (ansible_os_family, ansible_distribution)
  • Architecture, kernel, hostname
  • Network interfaces, IP addresses (ansible_default_ipv4)
  • Memory, CPU count, disk partitions
  • Python interpreter path
Facts are available as variables in all tasks: {{ ansible_distribution }}.

Performance tip: Set gather_facts: no for large inventories where you don't need facts — saves ~0.5s per host. Use gather_subset: ['network'] to collect only what you need.
A6What is the difference between become and become_user?
  • become: yes: Enables privilege escalation for a play or task. By default, escalates to root using sudo.
  • become_user: postgres: Specifies which user to become (instead of root). Useful for running tasks as a service account (e.g., run psql as the postgres user).
  • become_method: How to escalate — sudo (default), su, pbrun, doas.
Always scope become to only the tasks that need it — don't set it at play level if only 2 of 20 tasks need root.
A7What are Ansible ad-hoc commands and when should you use them?
Ad-hoc commands run a single module against an inventory group without writing a playbook: 
# Ping all web servers
ansible webservers -m ping

# Check disk usage on all hosts
ansible all -m shell -a "df -h"

# Restart nginx on app servers
ansible appservers -m service -a "name=nginx state=restarted" --become
When to use: One-off operational tasks, quick fact gathering, emergency remediation, or testing module behavior before writing a playbook.

When NOT to use: Any action that needs to be repeatable, audited, or version-controlled — write a playbook instead.
A8How does Ansible handle task execution across multiple hosts — serial vs parallel?
By default, Ansible runs each task on all hosts in parallel (up to forks at a time, default 5) before moving to the next task — this is the "task-centric" model.

serial keyword: Controls rolling deployment behavior:
  • serial: 1 — run all tasks on 1 host, then the next host. Slowest but safest (never more than 1 host down).
  • serial: "30%" — run against 30% of hosts at a time.
  • serial: [1, 5, 20%] — progressive batches: 1 host, then 5, then 20% at a time.
max_fail_percentage: Abort the play if more than N% of hosts fail — prevents a bad change from cascading to all servers.
A9What is the Ansible forks setting and how do you tune it?
forks (default: 5) controls how many hosts are managed simultaneously by the control node. Each fork is a separate process.

Tuning:
  • Set in ansible.cfg: [defaults] forks = 50 or override with -f 50.
  • Higher forks = faster execution on large inventories, but more RAM and CPU on the control node.
  • Network bandwidth to target hosts and SSH connection limits on targets are the practical ceiling.
  • ControlPersist SSH multiplexing: Enable in ansible.cfg — reuses a single SSH connection for all tasks to a host, drastically reducing connection overhead for large playbooks.

📝 Playbooks, Roles & Variables
A11 – A20 Roles · Templates · Handlers · Loops

Writing well-structured, reusable Ansible code requires mastery of roles, variable precedence, Jinja2 templating, handlers, and conditionals.

A11What is an Ansible role and what is its directory structure?
A role is a reusable, self-contained unit of Ansible automation with a standardized directory layout: 
roles/
  nginx/
    tasks/
      main.yml        # task list (required)
    handlers/
      main.yml        # handlers triggered by notify
    templates/
      nginx.conf.j2   # Jinja2 templates
    files/
      index.html      # static files for copy module
    vars/
      main.yml        # role-scoped variables (high precedence)
    defaults/
      main.yml        # default variables (lowest precedence)
    meta/
      main.yml        # role dependencies, galaxy metadata
    README.md
Apply a role in a playbook: roles: [nginx, firewall, monitoring]. Roles promote code reuse across playbooks and projects — share them via Ansible Galaxy or a private automation hub.
A12What is Ansible variable precedence and why does it matter?
Ansible has 22 levels of variable precedence (lowest to highest — higher wins):
  • Lowest: Role defaults (roles/x/defaults/main.yml) — intended to be easily overridden.
  • Mid: Inventory variables → group_vars/ → host_vars/ → play vars → task vars.
  • High: Role vars (roles/x/vars/main.yml) — not easily overridden (use for internal role constants).
  • Highest: Extra vars (-e "key=value" on command line) — override everything.
Best practice: Use defaults/main.yml for variables you expect users to override. Use vars/main.yml for internal role constants. Document all expected variables with defaults.
A13What are Ansible handlers and when do they run?
Handlers are tasks that run only when notified by another task — and only if the notifying task made a change (reported changed, not ok).

Example: 
tasks:
  - name: Deploy nginx config
    template: src=nginx.conf.j2 dest=/etc/nginx/nginx.conf
    notify: Restart nginx

handlers:
  - name: Restart nginx
    service: name=nginx state=restarted
Key behaviors:
  • Handlers run once at the end of the play, regardless of how many tasks notified them — prevents multiple restarts.
  • Force immediate execution mid-play with meta: flush_handlers.
  • Multiple tasks can notify the same handler; it still only runs once.
A14How does Jinja2 templating work in Ansible?
Ansible uses Jinja2 for dynamic content in templates (.j2 files) and in task arguments.

Common patterns:
  • Variable substitution: {{ variable_name }}
  • Conditionals: {% if ansible_os_family == "Debian" %}...{% endif %}
  • Loops: {% for server in groups['webservers'] %}{{ server }}{% endfor %}
  • Filters: {{ my_list | join(', ') }}, {{ path | basename }}, {{ 'hello' | upper }}
  • Tests: {% if var is defined %}...{% endif %}
Templates are rendered on the control node and the rendered file is pushed to the target. Use the template module (not copy) for .j2 files.
A15How do you use loops in Ansible?
Modern syntax (loop:, Ansible 2.5+): 
- name: Install packages
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
  loop:
    - nginx
    - python3
    - git
Loop over dictionaries: 
- name: Create users
  ansible.builtin.user:
    name: "{{ item.name }}"
    groups: "{{ item.groups }}"
  loop:
    - { name: alice, groups: sudo }
    - { name: bob,   groups: docker }
Avoid: with_items (legacy), with_dict, etc. — replaced by loop + filters. Use loop_control.label to customize what item is shown in output (avoid logging secrets).
A16How do conditionals (when) work in Ansible?
The when clause skips a task if the condition is false. It evaluates a Jinja2 expression (without {{ }} braces): 
- name: Install Apache (Debian only)
  ansible.builtin.apt:
    name: apache2
    state: present
  when: ansible_os_family == "Debian"

- name: Install Apache (RedHat only)
  ansible.builtin.yum:
    name: httpd
    state: present
  when: ansible_os_family == "RedHat"
Multiple conditions:
  • AND: list form — each item ANDed: when: [condition1, condition2]
  • OR: explicit: when: condition1 or condition2
when combined with loop: condition evaluated per item.
A17What is block, rescue, and always in Ansible?
Ansible's error handling structure, similar to try/catch/finally: 
- block:
    - name: Deploy application
      command: ./deploy.sh
    - name: Run smoke test
      uri: url=http://localhost/health
  rescue:
    - name: Rollback on failure
      command: ./rollback.sh
    - name: Notify team
      slack: msg="Deploy failed, rolled back"
  always:
    - name: Clean up temp files
      file: path=/tmp/deploy state=absent
rescue runs only if a task in block fails. always runs regardless. Blocks also support when, become, and tags applied to all tasks within.
A18What is register and how do you use it to capture task output?
register captures the return value of a task into a variable for use in subsequent tasks: 
- name: Check if config exists
  stat: path=/etc/myapp/config.yml
  register: config_stat

- name: Deploy default config
  template: src=config.yml.j2 dest=/etc/myapp/config.yml
  when: not config_stat.stat.exists
The registered variable is a dictionary with keys like rc (return code), stdout, stderr, changed, failed.

Common use: Check command output, conditionally run follow-up tasks, pass data between tasks (e.g., grab an instance ID from AWS CLI output).
A19What are Ansible tags and how do you use them for partial playbook runs?
Tags allow selective execution of tasks or roles within a playbook: 
tasks:
  - name: Install nginx
    apt: name=nginx state=present
    tags: [nginx, install]

  - name: Configure nginx
    template: src=nginx.conf.j2 dest=/etc/nginx/nginx.conf
    tags: [nginx, configure]
  • ansible-playbook site.yml --tags nginx — run only nginx tasks.
  • ansible-playbook site.yml --skip-tags install — skip install tasks.
  • ansible-playbook site.yml --tags all — run everything.
  • --list-tags — preview all available tags without running.
Use case: Re-run only configuration tasks after a config change without re-running the full install sequence.
A20What is include_tasks vs import_tasks and why does it matter?
  • import_tasks (static): Pre-processed at playbook parse time. All tasks are included before any task runs. Supports tags on the imported tasks (tags on the import statement apply to all tasks within). Cannot use variables in the filename.
  • include_tasks (dynamic): Processed at runtime when the task is reached. Can use variables in the filename: include_tasks: "{{ ansible_os_family }}_setup.yml". Tags on the include_tasks statement do NOT propagate to inner tasks.
Rule of thumb: Use import_tasks for static includes you want taggable from the command line. Use include_tasks when you need dynamic file selection or loops.
Role development workflow: Use ansible-galaxy role init my_role to scaffold the directory structure. Test roles with Molecule — it spins up Docker or Vagrant instances, applies the role, and runs testinfra/pytest assertions to verify the final state.
⚡ Advanced Ansible — Vault, Collections, AWX & Performance
A21 – A30 Vault · Collections · AWX · Delegation

Production Ansible usage involves securing secrets with Vault, distributing automation via Collections, managing execution at scale with AWX/Automation Controller, and debugging complex failures.

A21What is Ansible Vault and how do you use it?
Ansible Vault encrypts sensitive data (passwords, API keys, certificates) using AES-256 so secrets can be safely stored in version control alongside playbooks.

Common operations: 
# Encrypt an entire file
ansible-vault encrypt group_vars/all/vault.yml

# Encrypt a single string (embed in YAML)
ansible-vault encrypt_string 'mysecret' --name db_password

# Edit an encrypted file
ansible-vault edit group_vars/all/vault.yml

# Run playbook with vault password
ansible-playbook site.yml --vault-password-file ~/.vault_pass
ansible-playbook site.yml --ask-vault-pass
Best practice: Store only the vault password file path in a password manager or CI secret; never commit the vault password. Use multiple vault IDs (--vault-id dev@prompt --vault-id prod@~/.prod_vault_pass) to manage per-environment secrets.
A22How do you integrate Ansible Vault with external secrets managers (HashiCorp Vault, AWS Secrets Manager)?
For enterprise environments, using Ansible Vault (file-based) has key/rotation limitations. External secrets managers provide dynamic, audited secrets:

HashiCorp Vault: Use the community.hashi_vault collection: 
- name: Get DB password from Vault
  set_fact:
    db_password: "{{ lookup('hashi_vault', 'secret=secret/data/db token=...' ) }}"
AWS Secrets Manager: Use the amazon.aws.aws_secret lookup plugin: 
db_password: "{{ lookup('amazon.aws.aws_secret', '/prod/db/password') }}"
Benefits: Secrets are fetched at runtime, never stored on disk, automatically rotated, and every access is audited.
A23What are Ansible Collections and how do they improve code distribution?
Collections (introduced in Ansible 2.9) are distribution packages that bundle modules, plugins, roles, and playbooks together under a namespace:
  • amazon.aws — official AWS collection (EC2, S3, RDS modules).
  • community.docker — Docker management modules.
  • kubernetes.core — kubectl and Helm modules.
Install: ansible-galaxy collection install amazon.aws or pin in requirements.yml: 
collections:
  - name: amazon.aws
    version: ">=6.0.0"
Collections decouple module releases from Ansible core releases — AWS collection can ship new EC2 features without waiting for an Ansible core release.
A24What is AWX / Ansible Automation Controller and what problems does it solve?
AWX (open-source) / Red Hat Ansible Automation Controller (commercial) is a web-based UI and API on top of Ansible that solves enterprise automation governance:
  • Role-based access control (RBAC): Different teams can run their playbooks without seeing each other's inventories or credentials.
  • Credential management: SSH keys and vault passwords stored encrypted in the database — operators never see raw credentials.
  • Job scheduling: Cron-like scheduled playbook runs without cron access to a control node.
  • Audit trail: Every playbook run, who triggered it, output, and result — stored and searchable.
  • Workflows: Visual DAG of multiple playbook runs with conditional branching.
  • Scalable execution: Execution nodes and hop nodes for running automation in remote or air-gapped environments.
A25What is delegate_to and when do you use it?
delegate_to runs a specific task on a different host than the one currently being configured — while still using the current host's variables: 
- name: Deregister from load balancer before deploy
  command: aws elbv2 deregister-targets --target-group-arn {{ tg_arn }} ...
  delegate_to: localhost
  
- name: Deploy application
  git: repo=... dest=/app version=main

- name: Re-register with load balancer
  command: aws elbv2 register-targets ...
  delegate_to: localhost
Common patterns:
  • Run AWS CLI / API calls from localhost while iterating over EC2 instances.
  • Update a DNS record or load balancer from a central node while rolling out app servers.
  • delegate_to: localhost + run_once: true — execute a task exactly once from the control node regardless of how many hosts are in the play.
A26How do you write custom Ansible modules?
Custom modules let you extend Ansible when no existing module covers your need. They are Python scripts that accept JSON input and return JSON output: 
from ansible.module_utils.basic import AnsibleModule

def main():
    module = AnsibleModule(
        argument_spec=dict(
            name=dict(type='str', required=True),
            state=dict(type='str', default='present')
        ),
        supports_check_mode=True
    )
    # ... implement logic ...
    module.exit_json(changed=True, result="done")

if __name__ == '__main__':
    main()
Place in library/ next to your playbook or package in a Collection. Always implement supports_check_mode (dry-run). Return changed: false when the desired state already exists (idempotency).
A27How do you test Ansible roles with Molecule?
Molecule is the standard testing framework for Ansible roles — it provisions test instances, applies the role, verifies the result, and destroys the instances.
  • molecule init scenario — scaffold test infrastructure in molecule/default/.
  • molecule.yml: Configure the driver (Docker, Vagrant, EC2), platforms (Ubuntu 22.04, RHEL 9), and verifier.
  • converge.yml: The playbook that applies your role under test.
  • verify.yml / tests/: testinfra (pytest) or ansible.builtin.assert tasks that validate the final system state.
Full test cycle: molecule test — creates → converge → idempotency check (run again, assert 0 changed) → verify → destroy. The idempotency check is the most valuable automated test — catches tasks with non-idempotent side effects.
A28How do you optimize Ansible performance for large inventories?
  • SSH multiplexing / ControlPersist: Reuse a single SSH connection per host across all tasks — the biggest single improvement: [ssh_connection] ssh_args = -o ControlMaster=auto -o ControlPersist=60s
  • Pipelining: pipelining = True in ansible.cfg — execute module code over stdin without an SCP upload. Reduces SSH round trips per task from 3 to 1. Requires requiretty disabled in sudoers.
  • Fact caching: Cache gathered facts to Redis or JSON files — skip re-collection on subsequent runs: fact_caching = redis, fact_caching_timeout = 86400
  • Increase forks: forks = 50+ for large inventories.
  • Mitogen strategy plugin: Replaces the default execution strategy — 2–7× faster for complex playbooks by using Python-level process reuse.
A29How do you use Ansible for CI/CD application deployment alongside Docker?
Ansible complements Docker in deployment scenarios where you need to orchestrate beyond docker run: 
- name: Deploy application container
  community.docker.docker_container:
    name: myapp
    image: "myrepo/myapp:{{ version }}"
    state: started
    restart_policy: always
    ports: ["80:8080"]
    env:
      DB_HOST: "{{ db_host }}"
      DB_PASS: "{{ vault_db_password }}"
    volumes: ["/data/myapp:/app/data"]
Full deployment play pattern:
  1. Drain host from load balancer (delegate_to: localhost).
  2. Pull new image (community.docker.docker_image).
  3. Stop and remove old container.
  4. Start new container with updated image tag.
  5. Wait for health check: uri module polling /health.
  6. Re-register host with load balancer.
A30What are Ansible callback plugins and how do you use them for notifications?
Callback plugins hook into Ansible's execution events (task start, task result, playbook complete, failure) to customize output or trigger external actions.

Built-in callbacks:
  • yaml / json — change output format.
  • profile_tasks — show task execution times (identify bottlenecks).
  • timer — total playbook elapsed time.
  • mail — email on failure.
Enable in ansible.cfg: stdout_callback = yaml, callback_whitelist = profile_tasks,timer.

Custom callback for Slack/PagerDuty: Write a Python class extending CallbackBase and override v2_playbook_on_stats() to post a summary to Slack with pass/fail counts — useful for scheduled compliance-run notifications.

✓ All secrets in Ansible Vault or external secrets manager — none in plaintext  ·  ✓ Roles tested with Molecule (idempotency check passes)  ·  ✓ SSH pipelining + ControlPersist enabled  ·  ✓ Dynamic inventory for cloud environments  ·  ✓ --check + --diff dry-run before production runs  ·  ✓ max_fail_percentage set for rolling deployments  ·  ✓ Playbooks version-controlled with peer review  ·  ✓ AWX/Automation Controller for team access and audit trail  ·  ✓ FQCN module names (e.g. ansible.builtin.apt not apt)
Debugging tips: -v (verbose) through -vvvv (connection debug). Use ansible-playbook --check --diff to preview changes without applying them. The debug module with var: hostvars[inventory_hostname] dumps all variables for a host — invaluable for troubleshooting variable precedence issues.
