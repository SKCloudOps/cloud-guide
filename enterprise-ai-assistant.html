How a single request travels the system

  1. A user asks in Teams, Slack, web, or email. The request hits API Gateway behind WAF, where the OIDC / JWT token is validated and identity, groups, and roles are attached.
  2. The supervisor agent classifies intent and decides which specialized agent owns the work — DevOps, Knowledge, Change/Incident, Monitoring, or Security.
  3. The context engineering layer assembles seven context streams and the optimizer ranks, de-duplicates, compresses, budgets tokens, and redacts PII before anything reaches the model.
  4. The agent proposes a plan. The validation & tool selection pipeline runs eight deterministic stages — RBAC/ABAC, confidence scoring, policy validation, and human approval for sensitive actions.
  5. Only an approved plan is executed through the MCP adapter layer to GitHub, Jira, ServiceNow, Terraform, AWS, Kubernetes, and other tools. The model never touches infrastructure directly.
  6. Execution aggregates results, handles errors, and generates a response, while observability, the event bus, and storage capture a full audit trail of every decision.

The fourteen zones, explained

Each numbered block on the diagram plays one role. Together they wrap a powerful but untrusted model so that intelligence stays flexible while the governance boundary stays fixed.

Zone 1 · 2

Users & entry point

L1–L3 support, DevOps, admins, and business users reach the assistant over Web, Teams, Slack, or email. Microsoft Entra ID handles SSO, MFA, and conditional access; every call enters through API Gateway behind AWS WAF carrying an OIDC / JWT token, with identity, groups, and roles travelling alongside it.

Zone 3

AI orchestration layer

Amazon Bedrock agents. A supervisor owns intent understanding, task planning, tool selection, reasoning, response generation, and memory. Collaborating specialists — DevOps, Knowledge, Change/Incident, Monitoring, Security & Compliance — each own a single domain to bound blast radius.

Agent Memory

Four memory tiers

Short-term conversation buffer, session state in Redis, long-term conversation history, and a vector store on OpenSearch Serverless. Together they let the assistant hold context across turns instead of starting cold on every request.

Zone 4

Context engineering layer

Seven context streams — identity, conversation, application & infra, knowledge (RAG), live operational data, execution state, and business rules — are merged by a context optimizer that ranks, de-duplicates, summarizes, compresses, budgets tokens, redacts PII, and formats for the model.

Zone 5

Validation & tool selection

The deterministic heart. Eight stages: intent classification, capability registry lookup, RBAC/ABAC filtering, tool ranking, confidence scoring, plan validation against policy, human approval if required, and a final execution-ready plan. A rules engine runs input, permission, data, business-rule, security, and risk checks.

Zone 6

Tool orchestration via MCP

Approved plans run through the MCP adapter layer — GitHub, Jira, ServiceNow, Confluence, Terraform, Ansible, AWS, Kubernetes, and custom servers — with token forwarding, request/response transformation, error handling, rate limiting, and retries.

Zone 7

Execution & response

Executes the validated tools, aggregates results across systems, handles errors and retries, and summarizes a clean response back to the user.

Zone 8

Human approval workflow

Sensitive actions trigger a configurable, multi-level approval flow before they execute, bounded by risk level, environment, and action type. High-risk operations pause and wait rather than run autonomously.

Zone 9

Enterprise integrations

The execution plane: Jira, ServiceNow, Confluence, GitHub/GitLab, and other HR / finance / ITSM systems. Agents never call these directly — only validated MCP tool calls reach them.

Zone 10

Observability & monitoring

CloudWatch, X-Ray, OpenSearch analytics, and CloudTrail provide a full reasoning-and-action audit trail, so any production decision can be reconstructed end to end.

Zone 11

Security & governance

Entra ID conditional access, IAM RBAC/ABAC, KMS encryption, Secrets Manager, Bedrock guardrails, prompt-injection defense, content filters, and audit reviews — governance enforced as architecture, not paperwork.

Zone 12 · 13 · 14

Data, events & lifecycle

S3 for docs and backups, OpenSearch vectors, Neptune graph relationships, and DynamoDB session state. EventBridge and SNS/SQS carry change, security, and workflow events. A CI/CD lifecycle deploys agent code, prompts, and tools with versioning, rollback, and canary releases.

How a single request travels the system — technically

The same six steps, one layer deeper: the protocols, AWS services, data structures, and failure controls that make each hop safe, observable, and reversible.

1
Zones 1 · 2 — Ingress & identity

Authenticated entry and request normalization

The user sends a message from Teams, Slack, a web widget, or email. The channel adapter posts it to Amazon API Gateway, which sits behind AWS WAF for rate limiting, IP reputation, and payload inspection before any compute is touched.

AuthenticationA JWT / OIDC bearer token issued by Microsoft Entra ID is validated at the gateway using a Lambda authorizer or JWT authorizer. Signature, iss, aud, and exp are checked; expired or malformed tokens are rejected with 401 before reaching backend services.
Claims → contextVerified claims (user id, groups, roles, tenant) are extracted and attached to the request as a signed context object. This becomes the authority for every downstream RBAC/ABAC decision — the model never re-derives identity.
SessionThe Session Service (ECS/Fargate) resolves or creates a session id, writes state to DynamoDB, and mints a correlation / trace id used across the whole request for X-Ray.
Failure controlsWAF throttling, gateway usage plans, and input schema validation reject oversized or malformed payloads at the edge, keeping injection surface and cost down.
API GatewayAWS WAFEntra ID (OIDC/JWT)Lambda authorizerECS / FargateDynamoDB session
2
Zone 3 — Orchestration & routing

Intent classification and agent routing

The normalized request reaches the supervisor / orchestrator agent on Amazon Bedrock. Its job is decomposition and routing, not domain execution.

Intent NLUA lightweight, cheap model classifies the request into an intent and a target domain (deploy, incident, query, change). Using a small model here keeps routing fast and inexpensive — flagship models are reserved for genuinely hard reasoning.
RoutingBased on the classified domain, the supervisor dispatches to a specialized agent — DevOps, Knowledge, Change/Incident, Monitoring, or Security & Compliance. Each specialist holds its own least-privilege IAM role, which bounds blast radius.
Memory hydrationThe Memory Manager loads relevant state: short-term buffer, session state from Redis, long-term history, and semantic recall from the OpenSearch Serverless vector store.
Multi-agent tasksIf the task spans domains, the supervisor decomposes it into ordered sub-tasks and synthesizes results through shared session memory — each sub-task still passes its own validation gates.
Bedrock AgentsSupervisor / routerModel tieringRedis (session)OpenSearch vectorsPer-agent IAM role
3
Zone 4 — Context engineering

Context assembly, RAG retrieval and optimization

Before the model reasons, the context engineering layer builds exactly the right prompt payload from seven streams: identity, conversation, app & infra, knowledge (RAG), live operational data, execution state, and business rules.

RAG retrievalThe Knowledge stream does hybrid retrieval — semantic (vector) + keyword — against runbooks and SOPs in OpenSearch, then reranks so only the most relevant top-k reaches the model. Retrieved content carries provenance metadata.
Live operational dataCurrent system status, recent tool outputs, and metrics are pulled live via MCP so the model reasons over the real state of infrastructure, not a stale snapshot.
Optimizer pipelineThe assembler runs relevance ranking, de-duplication, summarization, compression, freshness checks, token-budget management, and PII redaction, then formats for the model. This controls both accuracy and cost per invocation.
Trust boundaryAll retrieved content is treated as untrusted data, never instructions — delimited and tagged — so a poisoned runbook produces a proposal, not an action. This is the first line against indirect prompt injection.
Hybrid retrieval + rerankOpenSearch ServerlessToken budgetingPII redactionProvenance taggingUntrusted-data pattern
4
Zones 5 · 8 — Deterministic validation

The validation pipeline and human approval

The agent proposes a plan — a structured set of tool calls with parameters. That proposal is free; execution is not. It now passes eight deterministic gates whose logic lives in data, not in the prompt, so the model cannot talk its way past them.

Schema & capabilityIntent classification → capability registry lookup in DynamoDB (tool metadata, permissions, SLA/limits). The proposed call is strictly schema-validated against the tool definition; a malformed plan is rejected with certainty.
RBAC / ABACPermissions are filtered against the JWT claims from step 1 — the caller must be authorized for both the tool and the target resource/environment.
Confidence scoringNot the model's self-reported confidence. Structural signals — schema pass, parameters inside hardcoded bounds, and a separate classifier's intent-to-tool match — are thresholded per risk tier. The threshold is deterministic, the model only supplies evidence.
Policy & riskPlan validation checks BlockedEnvironments, change windows, and risk/impact. The rules engine runs input, permission, data, business-rule, security, and risk checks.
Human-in-the-loopIf the action is high-risk (prod mutation, destructive op), it enters the approval workflow (Zone 8): the request pauses, an approver is notified, and only an explicit approval releases the final execution-ready plan. Multi-level approvals are configurable by risk, environment, and action type.
DynamoDB policy storeCapability registryRBAC / ABACSchema validationRisk tieringApproval workflow
5
Zones 6 · 9 — Brokered execution

Tool execution through the MCP adapter layer

Only a validated plan is executed, and never by the model directly. It is dispatched to the MCP server (adapter) layer, which exposes a standardized tool interface over the Model Context Protocol.

Adapter responsibilitiesEach MCP server (GitHub, Jira, ServiceNow, Confluence, Terraform, Ansible, AWS, Kubernetes, custom) handles auth token forwarding, request/response transformation, error handling, rate limiting, and retries against its downstream system.
Least privilegeThe adapter uses scoped, short-lived credentials from Secrets Manager / IAM role assumption — narrowed with aws:SourceAccount and aws:SourceArn conditions to close confused-deputy paths. The model never sees a raw credential.
ResilienceIdempotency keys, exponential backoff with jitter, timeouts, and circuit breakers keep a flaky or slow downstream from cascading. The enterprise systems in Zone 9 are only ever reached through this validated path.
MCP protocolAdapter layerSecrets ManagerSTS role assumptionBackoff + retriesCircuit breaker
6
Zones 7 · 10 · 12 · 13 — Response & audit

Aggregation, response generation and the audit trail

The execution & response stage collects tool outputs, reconciles partial failures, and asks the model to summarize a clear, grounded answer for the user — while the platform records everything that happened.

AggregationResults from one or more tools are aggregated, errors are handled and retried where safe, and the response is generated with citations back to the sources used, keeping the answer auditable.
ObservabilityX-Ray captures the reasoning-and-tool timeline (which agent, which tools, latency between generation and execution); CloudWatch holds metrics and errors; CloudTrail records API-level audit.
Immutable auditEvery proposal, gate decision, approval, and state mutation is emitted to Amazon EventBridge and persisted — the queryable record that makes autonomy defensible in a security or compliance review. SNS/SQS fan out notifications.
State & memoryOutcomes are written back to DynamoDB (session/state), S3 (artifacts/logs), and the vector store, so the next turn starts with accurate context and the full decision chain is reconstructable end to end.
X-Ray tracingCloudWatchCloudTrailEventBridge auditSNS / SQSS3 · DynamoDB
