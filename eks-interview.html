E1 – E5 Core Architecture

E1What is Amazon EKS and how does it differ from self-managed Kubernetes on EC2?

Amazon EKS is a fully managed Kubernetes service that runs the control plane (API server, etcd, scheduler, controller-manager) across three Availability Zones. AWS handles upgrades, patching, and HA for the control plane.

Cost$0.10/hr control plane + worker nodesOnly EC2 costs, but higher ops overhead

Architect Tip: EKS Auto Mode (GA 2024) further reduces ops by auto-managing node groups, Karpenter, CoreDNS add-ons, and EBS CSI driver — making EKS closer to a "serverless K8s" experience.

E3Explain the Kubernetes control plane components and how EKS manages them differently from vanilla K8s.

The Kubernetes control plane consists of five core components:

ComponentRoleEKS Management
kube-apiserverREST API gateway for all K8s operations. Validates and processes requests.HA across 3 AZs, auto-scaled, managed TLS certs
etcdDistributed key-value store for cluster stateEncrypted at rest (AWS KMS), automated backups, 3-AZ replication

Key EKS Difference
In EKS, the control plane runs in an AWS-managed VPC (not your VPC). Communication between your worker nodes and the API server happens via ENIs injected into your VPC or through a public endpoint. You choose: public, private, or public+private endpoint access.

E5What is the EKS Kubernetes version upgrade strategy? How would you plan a version upgrade for a production cluster with 200+ microservices?

EKS supports the latest 4 Kubernetes minor versions. AWS deprecates versions ~14 months after release. Upgrade strategy:

  1. Pre-upgrade Checklist:
    • Run kubectl get --raw /apis to find deprecated APIs
    • Use pluto or kubent to scan manifests for removed API versions
    • Test all Helm charts / Kustomize overlays against new version
    • Verify add-on compatibility (VPC CNI, CoreDNS, kube-proxy, CSI drivers)
  2. Upgrade Sequence: Control plane first → Add-ons → Node groups (rolling)
  3. Node Upgrade with Karpenter: Set drift policy to auto-replace nodes when AMI changes. Karpenter cordons, drains, and replaces nodes with zero manual intervention.
  4. Rollback Plan: Cannot downgrade control plane. Use blue/green cluster strategy — spin up new cluster, migrate workloads via GitOps (ArgoCD), cutover DNS.
# Check deprecated APIs before upgrade
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

# Upgrade control plane
aws eks update-cluster-version \
  --name my-cluster \
  --kubernetes-version "1.30"

# Upgrade managed node group
aws eks update-nodegroup-version \
  --cluster-name my-cluster \
  --nodegroup-name workers
Architect Tip: For 200+ microservices, use a blue/green cluster strategy managed via Terraform. Create the new cluster in parallel, deploy via ArgoCD ApplicationSets, run integration tests, then switch Route 53 weighted records. This provides instant rollback capability.

E6 – E10 Architecture Internals

Deep dive into pod scheduling, node lifecycle, container runtimes, and EKS-specific data plane configurations.

E6Walk through what happens when you run kubectl apply -f deployment.yaml — from API server to pod running on a node.
  1. Authentication & Authorization: kubectl sends request to API server → authenticates via kubeconfig token (IRSA/aws-iam-authenticator) → checks RBAC policies
  2. Admission Controllers: Mutating webhooks (e.g., inject sidecar, set defaults) → Validating webhooks (e.g., OPA/Gatekeeper policies)
  3. etcd Persistence: API server writes Deployment object to etcd
  4. Controller Loop: Deployment controller creates ReplicaSet → ReplicaSet controller creates Pod objects (still unscheduled)
  5. Scheduling: kube-scheduler finds suitable node (resource requests, affinity, taints/tolerations, topology spread) → binds pod to node
  6. Kubelet Execution: kubelet on the target node receives the pod spec → pulls container images → calls container runtime (containerd) → sets up networking via CNI plugin (VPC CNI assigns ENI IP)
  7. Readiness Probes: kubelet runs readiness probe → pod enters Ready state → kube-proxy updates iptables/IPVS rules → Service endpoints include the pod
EKS-Specific Detail
In EKS, VPC CNI assigns a real VPC IP to each pod (not overlay networking). This means pods are directly routable within the VPC — security groups, NACLs, and VPC Flow Logs work natively on pod traffic.

E8What are taints, tolerations, and node affinity? Design a multi-tenant EKS cluster where team-A workloads run only on team-A nodes.

Taints repel pods from nodes. Tolerations allow pods to schedule on tainted nodes. Node affinity attracts pods to specific nodes.

# Taint nodes for team-a
kubectl taint nodes team-a-pool team=a:NoSchedule

# Pod spec with toleration + affinity
spec:
  tolerations:
    - key: "team"
      operator: "Equal"
      value: "a"
      effect: "NoSchedule"
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: "team"
                operator: In
                values: ["a"]
Multi-Tenant Architecture Pattern
  • Namespace isolation: One namespace per team with ResourceQuotas and LimitRanges
  • Network policies: Deny all ingress by default, allow only within namespace
  • Node isolation: Taints + node affinity for workload separation
  • RBAC: Role + RoleBinding per namespace (not ClusterRole)
  • Karpenter NodePools: Separate NodePool per team with different instance types and budgets
E9What is Pod Topology Spread and why is it critical for production high availability?

Topology Spread Constraints distribute pods evenly across failure domains (AZs, nodes) to prevent all replicas from landing on the same node or AZ.

spec:
  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: "topology.kubernetes.io/zone"
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels:
          app: "payment-service"
    - maxSkew: 1
      topologyKey: "kubernetes.io/hostname"
      whenUnsatisfiable: ScheduleAnyway

maxSkew: 1 means the difference in pod count between any two zones is at most 1. With 3 replicas across 3 AZs, you get 1-1-1 distribution. If an AZ goes down, 2 replicas survive.

Production Rule: Always combine topology spread with Pod Disruption Budgets (minAvailable: 2 or maxUnavailable: 1) to prevent voluntary disruptions (upgrades, scaling) from taking down too many replicas simultaneously.
E10Explain resource requests vs limits in Kubernetes. What happens when a pod exceeds its memory limit? What about CPU?
AspectRequestsLimits
PurposeGuaranteed minimum — used for scheduling decisionsHard ceiling — enforced at runtime
CPU ExceededN/APod is CPU-throttled (not killed)

QoS Classrequests == limits → Guaranteed | requests < limits → Burstable | no requests/limits → BestEffort
✅ Best Practice
Always set requests (for proper scheduling). Set memory limits (prevents OOM cascade). Consider NOT setting CPU limits (let pods burst when spare capacity exists — Google's recommendation).
⚠️ Common Mistake
Setting requests too low → pods get scheduled on overcommitted nodes → node-level OOM. Setting limits too low → constant throttling → latency spikes. Use VPA recommendations to right-size.

🔌 VPC CNI & Pod Networking
E11 – E15Networking

How AWS VPC CNI assigns real VPC IPs to pods, ENI limits, prefix delegation, custom networking, and network policies.

E11How does the AWS VPC CNI plugin work? What problem does it solve compared to overlay networks?

The VPC CNI plugin assigns real VPC IP addresses from the node's subnet to each pod via secondary IPs on Elastic Network Interfaces (ENIs).

VPC CNI (EKS Default)
Pods get real VPC IPs. No encapsulation overhead. Native VPC routing, security groups, flow logs work on pod traffic. Performance matches EC2 networking. Pod-to-pod across nodes = direct VPC routing.
Overlay (Calico/Flannel)
Pods get IPs from a virtual overlay. Encapsulation (VXLAN/IPIP) adds ~5-10% CPU overhead. Cannot use VPC security groups on pods. Requires separate pod CIDR management.

ENI Limits: Each EC2 instance type has a max number of ENIs and IPs per ENI. For example, m5.large = 3 ENIs × 10 IPs = 29 pod IPs (minus node IPs). This limits pod density per node.

E12You're running out of pod IPs in your EKS cluster. The VPC subnet is /24 (254 IPs). What are your options?
  1. Prefix Delegation: Enable ENABLE_PREFIX_DELEGATION=true on VPC CNI. Instead of assigning individual IPs, each ENI slot gets a /28 prefix (16 IPs). This 16x increases pod density per node. 
    kubectl set env daemonset aws-node -n kube-system \
  ENABLE_PREFIX_DELEGATION="true" \
  WARM_PREFIX_TARGET="1"
  2. Secondary CIDR: Add a secondary CIDR block (e.g., 100.64.0.0/16) to your VPC. Use custom networking to place pods in the secondary CIDR subnets.
  3. Custom Networking: AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG=true — pods use subnets different from the node's subnet. Keeps node IPs separate from pod IPs.
  4. Larger Instance Types: m5.xlarge supports more ENIs and IPs per ENI than m5.large.
Architect Tip: For large clusters (500+ nodes), always plan IP capacity upfront. Use /16 secondary CIDRs from the 100.64.0.0/10 range (RFC 6598). Enable prefix delegation as the default for all new clusters.
E13What are Kubernetes Network Policies? How do you implement them in EKS?

Network Policies are K8s resources that control pod-to-pod traffic (L3/L4). They act as firewalls at the pod level. VPC CNI alone does NOT enforce Network Policies — you need an additional plugin.

Options for EKS:

  • VPC CNI Network Policy (native): Since VPC CNI v1.14+, AWS supports native network policies via eBPF. Enable with ENABLE_NETWORK_POLICY=true.
  • Calico: Full-featured network policy engine. Supports global policies, DNS-based rules, and L7 policies.
  • Cilium: eBPF-based, high performance, supports L7 policies and observability.
# Default deny all ingress in a namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: production
spec:
  podSelector: {}  # applies to all pods
  policyTypes: [Ingress]
  # empty ingress = deny all

Security Groups for Pods (SGP) allow you to assign AWS VPC Security Groups directly to individual pods, not just nodes. This enables fine-grained, VPC-native L3/L4 access control.

Use both together: Security Groups for Pods to control pod → RDS/ElastiCache access (e.g., only payment-service pods can reach the payment database). Network Policies for pod-to-pod isolation within the cluster.
E15How does CoreDNS work in EKS? A developer reports intermittent DNS resolution failures. How do you troubleshoot?

CoreDNS runs as a Deployment in kube-system. It serves DNS for service discovery (my-svc.my-ns.svc.cluster.local). Each node's kubelet configures pods to use CoreDNS ClusterIP (usually 10.100.0.10) as the DNS server.

Troubleshooting DNS failures:

  1. Check CoreDNS pods: kubectl get pods -n kube-system -l k8s-app=kube-dns — are they running? OOMKilled?
  2. Check CoreDNS logs: kubectl logs -n kube-system -l k8s-app=kube-dns — look for SERVFAIL, timeout, loop detection
  3. Scale CoreDNS: Default is 2 replicas. For 200+ node clusters, use the cluster-proportional-autoscaler to auto-scale CoreDNS based on node/pod count
  4. ndots issue: Default ndots:5 causes 4-8 DNS lookups per external name. Set ndots:2 in pod spec or use fully-qualified names with trailing dot (api.example.com.)
  5. NodeLocal DNS Cache: Deploy NodeLocalDNS (DaemonSet) to cache DNS on each node, reducing CoreDNS load and latency

E17What is the AWS Load Balancer Controller? How does it differ from the legacy in-tree cloud provider?

The AWS Load Balancer Controller (formerly ALB Ingress Controller) is an out-of-tree controller that watches for Ingress and Service resources and provisions AWS ALBs/NLBs.

AWS Load Balancer Controller (Recommended)
Creates ALB for Ingress, NLB for Service type LoadBalancer. Supports IP mode (routes directly to pod IPs — bypasses kube-proxy). Target group binding, WAF integration, Shield Advanced, Cognito auth.
Legacy In-Tree (Deprecated)
Only creates Classic Load Balancer. Instance mode only (routes to node ports). No ALB support, no IP mode, no WAF integration. Being phased out.

E20How would you expose a gRPC service running on EKS to external clients?

gRPC uses HTTP/2 with long-lived connections. This affects load balancing strategy:

  • Option 1 — NLB + gRPC: Use Service type LoadBalancer with NLB. NLB operates at L4 (TCP), so connections are balanced per-connection, not per-request. Works for few clients with many requests.
  • Option 2 — ALB + gRPC (Recommended): ALB supports gRPC natively (since 2020). It terminates HTTP/2, does per-request balancing. Use the AWS LB Controller with alb.ingress.kubernetes.io/backend-protocol-version: GRPC.
  • Option 3 — Service Mesh: Envoy-based mesh (Istio/Linkerd) does L7 load balancing for gRPC within the cluster. Combine with ALB for external traffic.
# ALB Ingress for gRPC
metadata:
  annotations:
    alb.ingress.kubernetes.io/backend-protocol-version: GRPC
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-protocol: HTTP
    alb.ingress.kubernetes.io/healthcheck-path: /grpc.health.v1.Health/Check

E22How does HPA work with custom metrics? Give an example using Prometheus metrics.

HPA can scale based on custom metrics via the Prometheus Adapter or KEDA. The flow: App → Prometheus scrapes metrics → Prometheus Adapter exposes them via K8s custom metrics API → HPA reads and scales.

# HPA with custom Prometheus metric (requests per second)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 3
  maxReplicas: 100
  metrics:
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "1000"  # scale up when >1000 RPS per pod
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # wait 5 min before scaling down
    scaleUp:
      stabilizationWindowSeconds: 0    # scale up immediately
E23What is KEDA and how does it enable scale-to-zero? Design a KEDA setup for an SQS-driven microservice.

KEDA (Kubernetes Event-Driven Autoscaling) extends K8s with event-driven scaling. Unlike HPA, KEDA can scale deployments to zero pods and back — critical for cost optimization.

# KEDA ScaledObject for SQS consumer
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-processor
spec:
  scaleTargetRef:
    name: order-processor
  minReplicaCount: 0    # scale to zero when queue is empty
  maxReplicaCount: 50
  cooldownPeriod: 60
  pollingInterval: 5
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.us-east-1.amazonaws.com/123/orders
        queueLength: "10"  # 1 pod per 10 messages
        awsRegion: us-east-1
      authenticationRef:
        name: keda-aws-creds  # uses IRSA

How it works: KEDA polls SQS every 5 seconds. At 0 messages → 0 pods. At 50 messages → 5 pods (50/10). At 500 messages → 50 pods (capped at max). When queue drains → cooldown 60s → scale to zero.

E24How does VPA work? Why shouldn't you use VPA in auto mode with HPA?

VPA (Vertical Pod Autoscaler) analyzes historical resource usage and recommends (or auto-applies) optimal CPU/memory requests and limits.

VPA Modes:

  • Off — Only calculates recommendations (view via kubectl describe vpa)
  • Initial — Sets requests at pod creation only, no restarts
  • Recreate — Evicts and recreates pods with updated requests (causes brief downtime)
  • Auto — Same as Recreate (currently), may support in-place resize in future

Conflict with HPA: If both VPA (auto) and HPA target CPU, VPA increases pod CPU requests → HPA sees lower CPU utilization → scales down pods → VPA increases requests again → oscillation loop. Solution: Use VPA in Off mode alongside HPA, apply VPA recommendations manually during maintenance windows.

E25What is the HPA scaling behavior configuration? How do you prevent flapping (rapid scale up/down cycles)?

HPA behavior lets you control the speed and stability of scaling decisions:

  • stabilizationWindowSeconds: How long to wait before scaling down (prevents flapping). Default: 300s for scale-down, 0s for scale-up.
  • policies: Rate-limit scaling. E.g., max 4 pods per 60 seconds for scale-up, max 10% per 60 seconds for scale-down.
  • selectPolicy: Max (most aggressive), Min (most conservative), Disabled (no scaling in that direction).
Anti-Flapping Strategy
Scale up fast (stabilization = 0, aggressive policies), scale down slow (stabilization = 300-600s, conservative policies). This ensures you handle traffic spikes quickly but don't prematurely release capacity.

E27Design a Karpenter NodePool configuration for a cluster running both Spot and On-Demand workloads with Graviton preference.
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      requirements:
        - key: "karpenter.sh/capacity-type"
          operator: In
          values: ["spot", "on-demand"]
        - key: "kubernetes.io/arch"
          operator: In

E28How does Karpenter handle Spot instance interruptions? What happens to the pods running on a Spot node that gets reclaimed?

Karpenter has native Spot interruption handling:

  1. AWS sends 2-minute warning via EC2 metadata and EventBridge
  2. Karpenter receives the event and immediately cordons the node (prevents new pods)
  3. Karpenter provisions a replacement node — picks a different instance type/AZ with available Spot capacity
  4. Pods are gracefully drained from the interrupted node (respects PDBs and terminationGracePeriodSeconds)
  5. Pods reschedule on the new node or existing nodes with capacity
Spot Best Practices
Diversify instance types (Karpenter does this automatically). Set topologySpreadConstraints across AZs. Always have a mix of Spot + On-Demand. Critical workloads (databases, payment processing) should be On-Demand only — use karpenter.sh/capacity-type: on-demand in pod spec.
E29What is Karpenter consolidation? Explain the difference between WhenEmpty and WhenEmptyOrUnderutilized.
PolicyBehaviorRisk Level
WhenEmptyOnly removes nodes with zero pods (after daemonsets)Low — very safe, no pod disruption
WhenEmptyOrUnderutilizedActively bin-packs: replaces multiple under-utilized nodes with fewer right-sized onesMedium — causes pod rescheduling, respects PDBs

How consolidation works: Karpenter continuously evaluates if the current set of nodes is optimal. If 3 nodes are running at 20% utilization, it can replace them with 1 larger node — saving 2 nodes worth of cost. It cordons, drains, and terminates the old nodes while ensuring pods move safely.

E30How do you handle the "cold start" problem with Karpenter? Pods need to wait for a new node to launch before they can run.

Node cold start = ~60-90 seconds (EC2 launch + kubelet registration + CNI setup). Strategies to reduce impact:

  • Over-provision buffer pods: Deploy low-priority "pause" pods that consume resources. When real pods arrive, the pause pods are evicted, and the real pods take their place immediately — no waiting for new nodes.

        requests:
          cpu: "2"
          memory: "4Gi"
  • Warm pools (Managed Node Groups): Keep pre-initialized EC2 instances in a warm pool — launch in seconds instead of minutes.
  • Pre-pull images: Use DaemonSet to pre-pull large container images on all nodes. Reduces pod startup by 30-60s for large images.

E31What is IRSA (IAM Roles for Service Accounts)? How does it work and why is it critical for EKS security?

IRSA maps a Kubernetes ServiceAccount to an IAM Role, allowing pods to assume AWS IAM roles without using node-level IAM roles or hardcoded credentials.

How it works:

  1. EKS cluster has an OIDC provider registered with IAM
  2. IAM Role trust policy trusts the OIDC provider with conditions on namespace and service account name
  3. Pod's ServiceAccount is annotated with eks.amazonaws.com/role-arn
  4. EKS mutating webhook injects AWS_ROLE_ARN and a projected JWT token into the pod
  5. AWS SDK exchanges the JWT for temporary STS credentials via AssumeRoleWithWebIdentity
# ServiceAccount with IRSA
apiVersion: v1
kind: ServiceAccount
metadata:
  name: s3-reader
  namespace: data-team
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123:role/S3ReadOnly
Security Principle
IRSA provides least-privilege, pod-level AWS access. Without IRSA, all pods on a node share the node's IAM role — if any pod is compromised, the attacker gets the node's full permissions. With IRSA, each pod gets only the permissions it needs.

E37What is OPA Gatekeeper and how does it complement Pod Security Standards?

OPA Gatekeeper is a policy engine that enforces custom policies via admission webhooks. While PSS handles basic security levels, Gatekeeper enables fine-grained, organization-specific policies.

Example policies:

  • All images must come from approved registries (ECR only)
  • All pods must have resource requests and limits
  • No latest tag allowed — require specific image digests
  • All services must have specific labels (team, cost-center)
  • Ingress hosts must match approved domains
Defense in Depth
PSS = baseline security guardrails. Gatekeeper = custom organizational policies. Use both: PSS restricted for security fundamentals + Gatekeeper for business rules (naming conventions, approved registries, required labels).
E38Design a container image security pipeline for EKS. How do you prevent vulnerable images from running in production?
  1. Build: Multi-stage Dockerfile, minimal base image (distroless/Alpine), non-root user
  2. Scan: ECR image scanning (Inspector) on push. Trivy/Snyk in CI pipeline. Block images with Critical/High CVEs.
  3. Sign: Use cosign to sign images. Verify signatures via Kyverno/Gatekeeper admission policy.
  4. Admit: Gatekeeper policy: only allow images from approved ECR registries, require digest (not tag), require signature verification.

E48What is GitOps and why is it the preferred deployment model for Kubernetes?

GitOps uses Git as the single source of truth for declarative infrastructure and application code. A GitOps operator (ArgoCD/Flux) continuously reconciles the cluster state with the Git repository.

  • Declarative: Desired state is in Git (YAML manifests, Helm charts, Kustomize)
  • Versioned: Every change is a Git commit — full audit trail, easy rollback
  • Automated: ArgoCD detects drift and auto-syncs (or alerts)
  • Self-healing: If someone manually changes a resource, ArgoCD reverts it to match Git
Push-Based CI/CD (Traditional)
CI pipeline runs kubectl apply. Pipeline needs cluster credentials. No drift detection. Rollback = re-run old pipeline. Hard to audit who deployed what.
Pull-Based GitOps (ArgoCD/Flux)
ArgoCD pulls from Git. No credentials outside cluster. Continuous drift detection. Rollback = git revert. Full audit trail via Git history.
E49Design a CI/CD pipeline for deploying microservices to EKS using GitHub Actions and ArgoCD.
  1. CI (GitHub Actions):
    • Build → Test → Scan (Trivy) → Build Docker image → Push to ECR
    • Sign image with cosign
    • Update image tag in GitOps repo (Kustomize overlay or Helm values)
  2. CD (ArgoCD):
    • ArgoCD watches the GitOps repo
    • Detects new image tag → syncs to cluster
    • Argo Rollouts performs canary deployment (5% → 25% → 100%)
    • Prometheus metrics check passes → auto-promote
Separation of Concerns
Keep two separate repos: 1) App source code repo (triggers CI), 2) GitOps config repo (Helm values, Kustomize overlays — consumed by ArgoCD). This prevents circular triggers and keeps app code changes separate from config changes.

E56Your EKS production cluster is experiencing increased API server latency. Pods take 30+ seconds to schedule. What's your troubleshooting approach?
  1. Check API server metrics: CloudWatch metrics for apiserver_request_duration_seconds. Is it all requests or specific verbs (LIST, WATCH)?
  2. Check etcd performance: Look for etcd_request_duration_seconds spikes. Large etcd database (>8GB) can slow writes.
  3. Look for chatty controllers: Custom controllers or operators making excessive LIST calls without pagination or caching. Check audit logs for high-frequency callers.
  4. Webhook latency: Mutating/validating webhooks add latency to every API call. Check apiserver_admission_webhook_admission_duration_seconds.
  5. Scheduler issues: Enable scheduler logs. Check if complex affinity rules or many unschedulable pods are causing scheduler backlog.
  6. Resource limits: Is the cluster hitting API server rate limits? Check for 429 Too Many Requests in audit logs.
Quick Fix: If caused by webhook latency, add failurePolicy: Ignore to non-critical webhooks and set timeoutSeconds: 5. For long-term, optimize webhook performance or eliminate unnecessary ones.

E60A pod keeps getting OOMKilled even though kubectl top pod shows it's using less than its memory limit. What's happening?

kubectl top shows RSS (Resident Set Size) — the working set. But the kernel OOM killer looks at total memory usage including:

  • Page cache: Memory-mapped files, buffered I/O
  • Kernel memory: Network buffers, inotify watches, cgroup overhead
  • Off-heap memory: JVM direct buffers, mmap allocations not tracked by app metrics

Fix: Check cat /sys/fs/cgroup/memory/memory.usage_in_bytes inside the container — this shows the real cgroup memory usage. Increase limits to account for kernel/cache overhead. For JVM apps, set -XX:MaxRAMPercentage=75 to leave room for non-heap memory.

E61How do you implement Pod Disruption Budgets (PDBs) and why are they critical for production?

PDBs limit the number of pods that can be simultaneously unavailable during voluntary disruptions (node upgrades, Karpenter consolidation, kubectl drain).

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2       # OR maxUnavailable: 1
  selector:
    matchLabels:
      app: api-server

Critical for: Karpenter consolidation (respects PDBs before draining nodes), EKS node group upgrades, cluster autoscaler scale-down. Without PDBs, all pods could be evicted simultaneously during a rolling upgrade.

E62How would you migrate 100 microservices from ECS to EKS with zero downtime?
  1. Phase 1 — Infrastructure: Provision EKS cluster via Terraform. Set up VPC CNI, Karpenter, observability stack. Same VPC as ECS (for service discovery).
  2. Phase 2 — Strangler Fig: Migrate services one at a time, starting with stateless, low-risk services. Each service runs on both ECS and EKS behind the same ALB.
  3. Phase 3 — Traffic Shift: Use ALB weighted target groups to shift traffic: 10% → 50% → 100% to EKS. Monitor latency, errors, logs throughout.
  4. Phase 4 — Decommission: Once all traffic is on EKS and stable for 2 weeks, decommission ECS services.
Key risk: Service discovery. ECS uses Cloud Map, K8s uses CoreDNS. During migration, services on both platforms need to discover each other. Solution: Use AWS Cloud Map with both ECS and K8s service registration, or use ALB-based routing for cross-platform calls.
E63How do you handle stateful workloads (Kafka, Redis, PostgreSQL) on EKS? When should you use managed services instead?
Self-Managed on EKS
Full control over configuration. Use operators (Strimzi for Kafka, CloudNativePG for PostgreSQL). PVC with EBS gp3 volumes. StatefulSet with stable network IDs. Requires deep K8s + database ops expertise.
AWS Managed Services
MSK for Kafka, ElastiCache for Redis, RDS/Aurora for PostgreSQL. Automated backups, patching, failover. Higher cost, less customization. Significantly lower ops burden.

Decision framework: Use managed services for business-critical data stores (payment DB, customer data). Self-managed on K8s is acceptable for: non-critical caches, development environments, workloads requiring custom configurations not available in managed services.
