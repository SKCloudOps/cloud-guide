🔐 Vault Architecture
V1 – V10 Core Concepts

Vault's storage model, request flow, barrier, audit devices, and high-availability deployment patterns.

V1What is HashiCorp Vault and what problems does it solve?

Vault is a secrets management platform that centralises the storage, access, and lifecycle of sensitive data — API keys, passwords, certificates, encryption keys, and cloud credentials.

Problems it solves:

  • Secret sprawl — secrets scattered across config files, env vars, and codebases.
  • Static credentials — long-lived keys that are never rotated.
  • No audit trail — who accessed what secret and when.
  • Manual rotation — Vault automates credential rotation and generates dynamic, short-lived secrets.
V2Explain Vault's core architecture: storage backend, barrier, and the request flow.

Vault has a layered architecture:

  • Storage backend — persists encrypted data (Raft integrated, Consul, S3, etc.). The backend only stores ciphertext — it never sees plaintext.
  • Barrier — AES-256-GCM encryption layer between Vault core and storage. All data crossing the barrier is encrypted with the master key. The barrier is sealed at startup.
  • Core — request router, token store, policy engine, expiry manager.

Request flow: Client → TLS → API → Auth → Token validation → Policy check → Secret engine → Storage (encrypted).

V3What is the difference between the Vault seal and the master key?
ConceptDescription
Master keyEncrypts the encryption key used by the barrier. Never stored on disk in plain form. Split via Shamir's Secret Sharing (default) or held by an HSM/Cloud KMS (auto-unseal).
Encryption keyActual key used to encrypt/decrypt data in storage. Encrypted by the master key and stored with the data.
SealState where Vault holds neither the master key nor the encryption key in memory. Vault cannot serve requests when sealed.
UnsealProcess of reconstructing the master key (by providing unseal key shares) to decrypt the encryption key and load it into memory.
V4What is Shamir's Secret Sharing and how does Vault use it?

Shamir's Secret Sharing splits a secret (the master key) into N shares such that any K shares can reconstruct it, but K-1 shares reveal nothing. The default Vault configuration uses 5 shares, threshold 3.

At init, Vault generates the master key, splits it, and distributes the shares to operators. To unseal, at least 3 operators must provide their share — no single person has full key access, enforcing separation of duties.

Auto-unseal (using AWS KMS, Azure Key Vault, GCP KMS) delegates master key protection to a cloud HSM, enabling automated restarts without manual operator intervention.

V6How does Vault HA work with the Integrated Raft storage backend?

In Raft HA, all Vault nodes form a Raft cluster. One node is elected leader and handles all reads and writes. Other nodes are followers/voters that replicate the log.

  • Clients should use a load balancer or Vault agent to redirect to the active node.
  • Vault Enterprise supports performance standbys (followers that serve read requests).
  • Auto-pilot manages automatic dead server cleanup and version upgrades.
  • Minimum recommended cluster size: 3 or 5 nodes (odd number for quorum).
V7What are audit devices and why are they critical in production?

Audit devices log every request and response to Vault in HMAC-hashed form. Types:

  • File — writes to a local file path.
  • Syslog — sends to syslog/journald.
  • Socket — sends to a TCP/UDP/Unix socket.

Critical for production: If all enabled audit devices fail to write a log entry, Vault blocks the request. This guarantees an unbroken audit trail — Vault will not process a request it cannot audit. Enable at least two audit devices for redundancy.

vault audit enable file file_path=/var/log/vault/audit.log
vault audit enable syslog tag=vault facility=AUTH
V8What is the Vault Agent and what problems does it solve?

Vault Agent is a client-side daemon that runs alongside applications, eliminating the need for apps to directly interact with Vault:

  • Auto-auth — authenticates to Vault automatically using the host's identity (AWS IAM, Kubernetes SA, Azure MSI).
  • Secret caching — caches tokens and secrets locally; apps request from the local agent (Unix socket or TCP) rather than Vault server.
  • Template rendering — renders secrets into config files using Consul Template syntax, triggering app restarts on rotation.
  • Resilience — if Vault is temporarily unreachable, agent serves from cache.

V10What are Vault namespaces (Enterprise) and how do they support multi-tenancy?

Namespaces create isolated Vault environments within a single cluster — each namespace has its own auth methods, secret engines, policies, and tokens. Teams interact only with their namespace and cannot see other namespaces.

vault namespace create team-a
vault secrets enable -namespace=team-a kv-v2
VAULT_NAMESPACE=team-a vault kv put secret/app key=value

Parent namespaces can manage child namespaces, enabling hierarchical multi-tenancy (org → team → service).

🏗️ Vault Init, Unseal & Lifecycle
V11 – V16 Init · Unseal · Auto-unseal · Rekey

Vault initialisation, unseal process, auto-unseal with cloud KMS, rekeying, and disaster recovery procedures.

V11Walk through the vault operator init command and its outputs.
vault operator init \
  -key-shares=5 \
  -key-threshold=3 \
  -pgp-keys="op1.asc,op2.asc,op3.asc,op4.asc,op5.asc"

Outputs:

  • 5 unseal key shares — encrypted with each operator's PGP key.
  • Initial root token — has full Vault privileges. Use to set up policies/auth then revoke.
Never store unseal key shares together or in Vault itself. Distribute to separate operators and store in a secure offline location (HSM, password manager).
V12How does Auto-unseal with AWS KMS work?
# vault.hcl
seal "awskms" {
  region     = "us-east-1"
  kms_key_id = "arn:aws:kms:us-east-1:123456789:key/abc-123"
}

On startup, Vault calls AWS KMS to decrypt the master key using the KMS key. The KMS key never leaves AWS — only the encrypted master key is stored in Vault's storage. If the KMS key is disabled, Vault cannot unseal, providing an emergency break-glass control.

The EC2/ECS/Lambda IAM role running Vault needs kms:Decrypt and kms:DescribeKey permissions.

V13What is vault operator rekey and when should you perform it?

Rekey generates a new master key and re-encrypts the existing encryption key, distributing new unseal key shares. Perform when:

  • An unseal key holder leaves the organisation.
  • You want to change the key-shares/threshold values.
  • An unseal key share is suspected to be compromised.
vault operator rekey -init -key-shares=5 -key-threshold=3
vault operator rekey <unseal-key-1>
vault operator rekey <unseal-key-2>
vault operator rekey <unseal-key-3> # completes rekey
V14What is the difference between vault operator seal and vault operator step-down?
CommandEffectWhen to use
operator sealDrops the master key from memory; Vault stops serving requests until manually unsealedSecurity emergency — suspected compromise
operator step-downActive node yields leadership; a follower is elected; node remains unsealed and rejoins as standbyMaintenance, graceful leader migration
V15How do you rotate Vault's encryption key (not the master key)?
vault operator rotate

This generates a new encryption key, adds it to the keyring, and uses it for all future writes. Existing data is not re-encrypted immediately. Vault maintains a keyring of all keys and decrypts old data with the appropriate key version. Old key versions can be explicitly removed once all data is re-encrypted.

V16How do you take a Vault snapshot and restore from it?
# Snapshot (Raft backend)
vault operator raft snapshot save vault-backup.snap

# Restore (will unseal automatically if auto-unseal configured)
vault operator raft snapshot restore vault-backup.snap

Raft snapshots capture the full cluster state. Automate daily snapshots to S3 with lifecycle policies. Test restoration periodically in a separate environment — an untested backup is not a backup.

🗝️ Authentication Methods
A1 – A10 Token · AppRole · K8s · AWS · OIDC

How Vault authenticates clients — token, AppRole, Kubernetes, AWS IAM, LDAP, OIDC, and JWT auth methods with configuration examples.

A1What are auth methods in Vault and how do they differ from secret engines?

Auth methods verify the identity of a client and issue a Vault token with attached policies. Secret engines store, generate, or encrypt data for already-authenticated clients. Auth methods are mounted at paths like auth/aws, auth/kubernetes. Secret engines are mounted at paths like secret/, database/.

A2Explain the AppRole auth method and its typical use case.

AppRole is designed for machine-to-machine authentication. It uses two credentials:

  • RoleID — non-secret identifier embedded in app config or AMI (equivalent to username).
  • SecretID — short-lived, single-use secret delivered to the app at runtime via a trusted channel (equivalent to password).
# Enable AppRole
vault auth enable approle
vault write auth/approle/role/my-app \
  token_policies="my-app-policy" \
  token_ttl="1h" \
  secret_id_ttl="10m" \
  secret_id_num_uses="1"

# Get RoleID (embed in app)
vault read auth/approle/role/my-app/role-id

# Get SecretID (deliver via CI/CD at runtime)
vault write -f auth/approle/role/my-app/secret-id
A3How does Kubernetes auth method work and why is it preferred over static tokens in clusters?

The Kubernetes auth method validates a pod's ServiceAccount JWT token against the Kubernetes API server. Vault calls the k8s TokenReview API to verify the token's authenticity and bind it to a namespace/SA combination.

vault auth enable kubernetes
vault write auth/kubernetes/config \
  kubernetes_host="https://k8s.example.com" \
  kubernetes_ca_cert=@/var/run/secrets/kubernetes.io/serviceaccount/ca.crt

vault write auth/kubernetes/role/my-app \
  bound_service_account_names="my-app-sa" \
  bound_service_account_namespaces="production" \
  policies="my-app-policy" \
  ttl="1h"

Why preferred: No static credentials to manage or rotate. The pod uses its projected ServiceAccount token (short-lived, rotated by k8s) to authenticate.

A4How does the AWS auth method work for EC2 instances and IAM roles?

Two sub-methods:

  • iam — the client signs an sts:GetCallerIdentity request with its IAM credentials; Vault calls STS to verify the identity. Works for EC2, Lambda, ECS, and any IAM principal.
  • ec2 — uses the EC2 instance identity document (signed by AWS) and optionally the PKCS7 signature. Tied to a specific instance or AMI.

IAM method is recommended — more flexible and works beyond just EC2.

vault auth enable aws
vault write auth/aws/role/my-role \
  auth_type="iam" \
  bound_iam_principal_arn="arn:aws:iam::123456789:role/my-ec2-role" \
  policies="my-policy" \
  ttl="1h"
A5What is the OIDC auth method and how does it enable SSO for human operators?

The OIDC auth method integrates Vault with any OIDC provider (Okta, Azure AD, Google, GitHub) for browser-based SSO. Operators log in via their IdP — Vault maps OIDC claims (groups, email) to Vault policies.

vault auth enable oidc
vault write auth/oidc/config \
  oidc_discovery_url="https://accounts.google.com" \
  oidc_client_id="my-client-id" \
  oidc_client_secret="my-client-secret" \
  default_role="default"

vault login -method=oidc  # Opens browser for SSO
A6What is token renewal and how do you prevent token expiry in long-running services?

Vault tokens have a TTL. Services must renew before expiry using vault token renew or the /auth/token/renew-self API endpoint. Renewal extends by the increment (up to max TTL).

Best practices for long-running services:

  • Use Vault Agent — it handles token renewal automatically.
  • Set token_max_ttl to a reasonable ceiling (e.g., 24h) and re-authenticate when the token expires.
  • Use periodic tokens (no max TTL, renewable indefinitely) for infrastructure daemons — enable via period in the auth role.
A7What is token accessor and why is it useful?

Every Vault token has an accessor — a public reference to the token that can be used to look up token properties, renew it, or revoke it, without exposing the actual token value.

  • Audit logs record accessors rather than token values.
  • Operators can revoke a token via its accessor when a token is compromised but the value is unknown.
  • Useful for building token management UIs or approving workflows.
vault token lookup -accessor <accessor>
vault token revoke -accessor <accessor>

A9How do you create a token hierarchy and why does it matter for revocation?

When a parent token creates a child token, a parent-child relationship is established. Revoking a parent also revokes all child tokens recursively — this prevents orphaned tokens with active access after a parent's privilege is removed.

# Create a child token scoped to a specific policy
vault token create -policy=app-read -ttl=2h

# Revoke parent token → child is also revoked
vault token revoke <parent-token>

Use orphan tokens only when you explicitly want a token that survives parent revocation (e.g., long-running daemon tokens created by a bootstrap script).

A10What is the JWT/OIDC auth method and how does it differ from the OIDC login flow?

The JWT auth method allows Vault to authenticate using a pre-existing signed JWT (e.g., a Kubernetes SA token, GitHub Actions OIDC token, or GitLab CI JWT) without a browser redirect flow. The JWT is verified against a JWKS endpoint or a static public key.

vault write auth/jwt/config \
  jwks_url="https://token.actions.githubusercontent.com/.well-known/jwks" \
  bound_issuer="https://token.actions.githubusercontent.com"

# In CI, authenticate with the OIDC token
vault write auth/jwt/login role=github-actions jwt="$ACTIONS_ID_TOKEN_REQUEST_TOKEN"

This is the basis for GitHub Actions ↔ Vault integration without static credentials.

SE1 – SE10 KV · Dynamic · PKI · Transit · DB

KV v1 vs v2, dynamic secrets for AWS/databases, PKI certificate management, Transit encryption-as-a-service, SSH signing, and Transform engine.

SE1What is the difference between KV v1 and KV v2 secret engines?
FeatureKV v1KV v2
VersioningNoYes — up to configurable max versions
Soft deleteNoYes — delete marks as deleted, destroy removes
MetadataNoYes — custom metadata per secret

Use KV v2 in production for the version history and soft-delete safety net.

SE2What are dynamic secrets and how do they improve security over static credentials?

Dynamic secrets are generated on-demand for each request — they are unique, time-limited, and automatically revoked on expiry. Static credentials are shared, long-lived, and must be manually rotated.

Static Secret
One DB password shared by all apps. Lives months/years. Compromise affects all consumers. Manual rotation causes downtime.
Dynamic Secret
Unique DB creds per app instance. TTL 1h. Compromise affects only one token. Expiry is automatic revocation.
SE3How does the Database secrets engine generate dynamic credentials?
# Enable and configure PostgreSQL
vault secrets enable database
vault write database/config/my-postgres \
  plugin_name=postgresql-database-plugin \
  allowed_roles="readonly" \
  connection_url="postgresql://{{username}}:{{password}}@db:5432/mydb" \
  username="vault-admin" \
  password="admin-password"

vault write database/roles/readonly \
  db_name="my-postgres" \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" \
  max_ttl="24h"

# App requests credentials
vault read database/creds/readonly

Vault creates a real DB user, returns the credentials, and drops the user on TTL expiry or revocation.

SE4How does the AWS secrets engine generate dynamic IAM credentials?
vault secrets enable aws
vault write aws/config/root \
  access_key="AKIAIOSFODNN7EXAMPLE" \
  secret_key="wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY" \
  region="us-east-1"

vault write aws/roles/s3-read \
  credential_type="iam_user" \
  policy_document='{
    "Version": "2012-10-17",
    "Statement": [{"Effect": "Allow","Action": "s3:GetObject","Resource": "*"}]
  }'

# Request dynamic IAM keys
vault read aws/creds/s3-read

Vault creates a real IAM user or generates STS AssumeRole tokens. IAM users are deleted on TTL expiry.

SE5What is the PKI secrets engine and how does it automate certificate lifecycle?

The PKI engine turns Vault into an internal CA — it issues X.509 certificates on demand with short TTLs, eliminating long-lived certs and manual renewals.

vault secrets enable pki
vault secrets tune -max-lease-ttl=8760h pki  # 1 year root
vault write pki/root/generate/internal \
  common_name="example.com" ttl="8760h"

# Issue a certificate
vault write pki/issue/web-server \
  common_name="app.example.com" ttl="24h"

Pair with Vault Agent or cert-manager (k8s) to auto-renew before expiry. Short-lived certs (hours/days) are more secure than annual certs.

SE6What is the Transit secrets engine and how is it used for encryption-as-a-service?

Transit provides cryptographic operations (encrypt, decrypt, sign, verify, HMAC) without exposing the key to the application. The key never leaves Vault.

vault secrets enable transit
vault write -f transit/keys/my-app-key

# Encrypt
vault write transit/encrypt/my-app-key \
  plaintext=$(echo -n "my secret data" | base64)
# Returns: vault:v1:<ciphertext>

# Decrypt
vault write transit/decrypt/my-app-key \
  ciphertext="vault:v1:<ciphertext>"

The ciphertext includes the key version prefix — key rotation just changes which version encrypts new data; old data is still decryptable with older key versions.

SE7How does the SSH secrets engine enable certificate-based SSH access?

Instead of distributing static SSH keys, Vault signs short-lived SSH certificates. Only the Vault CA public key needs to be trusted on servers.

vault secrets enable ssh
vault write ssh/config/ca generate_signing_key=true

# Sign a public key (1h TTL)
vault write ssh/sign/operator \
  public_key=@~/.ssh/id_rsa.pub \
  valid_principals="ubuntu" \
  ttl="1h"

# Use signed cert
ssh -i ~/.ssh/id_rsa-cert.pub -i ~/.ssh/id_rsa ubuntu@server

Certificates expire automatically — no key revocation needed. All access is audited through Vault.

SE8What is secret engine lease and how does it relate to revocation?

Every dynamic secret issued by Vault has a lease — a TTL after which Vault automatically revokes it (calls the engine's revoke function, e.g., drops a DB user). Leases can be:

  • Renewed — extended before expiry (up to max TTL).
  • Revoked — immediately invalidated via vault lease revoke <lease-id>.
  • Force-revoked — vault lease revoke -force -prefix aws/creds/ — revokes all leases under a prefix even if the engine cleanup fails.
SE9What is the Vault Transform secrets engine and how does it differ from Transit?
TransitTransform (Enterprise)
Output formatOpaque ciphertext (base64)Format-preserving — same length/type as input
Use caseGeneral encryption, signingPCI compliance — encrypt CC numbers preserving format for legacy systems
TokenisationNoYes — replaces data with a random token, stores mapping in Vault

Example: encrypting 4111-1111-1111-1111 and storing 9876-5432-1234-5678 in the database (same format, no processing changes needed).

SE10How do you configure secret engine leases and what happens when a lease expires?
# Tune the lease TTL for a secret engine mount
vault secrets tune -default-lease-ttl=1h -max-lease-ttl=24h database/

When a lease expires:

  1. Vault's expiry manager detects the expired lease.
  2. Vault calls the secret engine's revoke function (e.g., DROP USER for database engine).
  3. The lease is removed from Vault storage.

If the revoke call fails (DB unreachable), Vault retries with exponential backoff. The credential may still exist in the DB until the retry succeeds — design systems to handle this.

🔒 Policies & Access Control
P1 – P8 HCL Policies · Capabilities · Path Glob

Writing fine-grained HCL policies, capability model, wildcard paths, policy templating, and the least-privilege principle in Vault.

P1What is a Vault policy and what capabilities can it grant?

A Vault policy is an HCL document that grants capabilities on API paths. Vault is deny-by-default — everything is denied unless explicitly permitted.

CapabilityHTTP verbEffect
createPOST/PUTCreate new data at path
readGETRead data at path
updatePOST/PUTUpdate existing data
deleteDELETEDelete data
listLISTList keys at path
sudoanyAllows access to root-protected paths
denyanyOverrides all other grants — explicit deny
P2Write a least-privilege policy for an app that reads only its own secrets from KV v2.
# policy: my-app.hcl
# KV v2 requires /data/ for read, /metadata/ for list

path "secret/data/my-app/*" {
  capabilities = ["read"]
}

path "secret/metadata/my-app/*" {
  capabilities = ["list"]
}

# Allow token to renew itself
path "auth/token/renew-self" {
  capabilities = ["update"]
}

path "auth/token/lookup-self" {
  capabilities = ["read"]
}
vault policy write my-app my-app.hcl
P3How do path wildcards and globs work in Vault policies?
PatternMeaning
secret/data/app/*Any path under app/ (one level and below)
secret/data/+/config+ matches exactly one path segment
secret/data/app/{{identity.entity.name}}/*Template — resolves to the authenticated entity's name

More specific paths take precedence. The deny capability always wins regardless of path specificity.

P4What is policy templating and how does it enable self-service secrets?

Policy templates use {{identity.entity.name}} or {{identity.groups.names}} to dynamically scope access based on the authenticated identity — one policy serves all users:

path "secret/data/users/{{identity.entity.name}}/*" {
  capabilities = ["create", "read", "update", "delete"]
}
# Alice can only access secret/data/users/alice/*
# Bob  can only access secret/data/users/bob/*

This eliminates the need to create per-user policies.

P5What are the built-in root and default policies?
  • root — attached to root tokens only. Grants all capabilities on all paths including sudo paths. Cannot be modified or deleted.
  • default — automatically attached to every token. Grants basic self-service capabilities: renew-self, lookup-self, revoke-self, cubbyhole access. Can be modified but not deleted.
Best practice: After initial setup, revoke the root token. Use OIDC/AppRole for ongoing admin access. Generate a new root token only for emergency operations via vault operator generate-root.
P6What is the cubbyhole secrets engine and how is it used for response wrapping?

The cubbyhole engine is private to each token — data stored in cubbyhole/ is accessible only to the token that created it and is deleted when the token expires.

Response wrapping uses cubbyhole to securely deliver secrets (e.g., SecretIDs in AppRole) — the secret is wrapped in a single-use token:

# Wrap the secret-id in a 5-minute token
vault write -wrap-ttl=5m -f auth/approle/role/my-app/secret-id
# Returns a wrapping_token, not the actual secret-id

# Recipient unwraps — only works once
vault unwrap <wrapping-token>

If an attacker intercepts the wrapping token and unwraps it first, the legitimate recipient's unwrap attempt fails — alerting that the token was compromised.

P7What is Vault's Identity system and how do entities and aliases work?

The Identity system creates a canonical entity for each unique person or machine, mapping multiple auth method logins (GitHub, LDAP, AppRole) to a single entity. This enables consistent policies across auth methods.

  • Entity — represents a single identity (person or service). Has a stable ID and metadata.
  • Alias — binds a specific auth method login (e.g., GitHub username) to an entity.
  • Group — collections of entities; policies attached to a group apply to all members. Can be internal (managed in Vault) or external (mapped to LDAP groups).

⚙️ Vault Operations & Best Practices
O1 – O6 Performance · DR Replication · Monitoring

Production operations — monitoring, performance replication, DR, upgrades, and troubleshooting patterns.

O1What metrics and health checks should you monitor for a production Vault cluster?
  • Seal status — /v1/sys/health returns HTTP 429 if standby, 503 if sealed. Alert on non-200.
  • Leader status — /v1/sys/leader — monitor ha_enabled and is_self.
  • Token count — vault.token.count — high counts indicate token sprawl.
  • Lease count — high counts can slow down the expiry manager.
  • Request latency — vault.core.handle_request histogram.
  • Audit log errors — monitor for write failures that block requests.

Vault exports Prometheus metrics at /v1/sys/metrics?format=prometheus when telemetry is configured.

O2What is the difference between Performance Replication and DR Replication (Enterprise)?
Performance ReplicationDR Replication
PurposeScale reads geographicallyDisaster recovery failover
Secondary can serve?Yes — read requestsNo — cannot serve requests (cold standby)
Tokens shared?No — secondary issues its own tokensYes — DR tokens accepted at secondary
FailoverN/A (secondary is active)Manual promotion required
O3How do you upgrade a Vault cluster with zero downtime?
  1. Read the Vault upgrade guide for your version — check for upgrade-blocking issues.
  2. Take a Raft snapshot: vault operator raft snapshot save pre-upgrade.snap
  3. Upgrade standby nodes first (one at a time) — they rejoin the cluster after restart.
  4. Step down the leader: vault operator step-down — a follower becomes leader.
  5. Upgrade the old leader node (now a follower).
  6. Verify cluster health: vault operator raft list-peers
O4How do you troubleshoot a "permission denied" error in Vault?
  1. Check the token's policies: vault token lookup <token>
  2. Check what capabilities the token has on a specific path: vault token capabilities <token> secret/data/myapp
  3. Verify the policy HCL for the exact path being requested (KV v2 uses /data/ and /metadata/ prefixes).
  4. Check audit logs for the exact request path and the denied policy.
  5. Remember: Vault is deny-by-default — a missing policy is a deny.
O5How do you handle Vault token lease explosion (too many leases)?

Lease explosion degrades performance because the expiry manager scans all leases. Causes: apps requesting too many short-lived tokens without renewing or revoking them.

Remediation:

  • Use Vault Agent — it manages token renewal automatically, preventing token churn.
  • Use batch tokens for high-throughput, stateless operations (not stored in Vault).
  • Revoke unused leases: vault lease revoke -force -prefix auth/approle/login/
  • Set conservative token_max_ttl on auth roles so tokens expire faster.
  • Monitor vault.expire.num_leases metric and alert above threshold.

🤖 Vault + Ansible Integration
I1 – I4 hashi_vault · Dynamic Inventory · AppRole

Reading Vault secrets in Ansible playbooks using the community.hashi_vault collection — authentication, lookup plugins, and dynamic credential patterns.

I1How do you authenticate Ansible to Vault and read a KV secret?
Ansible ↔ Vault

Install the collection: ansible-galaxy collection install community.hashi_vault

Install the Python dependency: pip install hvac

# playbook.yml — using AppRole auth
---
- hosts: all
  vars:
    vault_addr: "https://vault.example.com:8200"
    db_creds: "{{ lookup('community.hashi_vault.hashi_vault',
        'secret=secret/data/myapp/db
         auth_method=approle
         role_id={{ lookup(\"env\", \"VAULT_ROLE_ID\") }}
         secret_id={{ lookup(\"env\", \"VAULT_SECRET_ID\") }}
         url={{ vault_addr }}') }}"

  tasks:
    - name: Configure database connection
      ansible.builtin.template:
        src: db.conf.j2
        dest: /etc/myapp/db.conf
      vars:
        db_user: "{{ db_creds.data.data.username }}"
        db_pass: "{{ db_creds.data.data.password }}"
Never log secrets — use no_log: true on any task that handles Vault credentials.
I2How do you use Vault's dynamic database credentials in an Ansible deployment playbook?
# Request dynamic DB credentials from Vault at deploy time
---
- hosts: app_servers
  tasks:
    - name: Get dynamic DB credentials from Vault
      community.hashi_vault.hashi_vault:
        url: "https://vault.example.com:8200"
        path: "database/creds/readonly"
        auth_method: "aws_iam"
        region: "us-east-1"
      register: vault_db
      no_log: true

    - name: Write DB config with dynamic credentials
      ansible.builtin.template:
        src: templates/db.conf.j2
        dest: /etc/app/db.conf
        mode: '0600'
      vars:
        db_username: "{{ vault_db.secret.username }}"
        db_password: "{{ vault_db.secret.password }}"
      no_log: true

    - name: Restart application
      ansible.builtin.service:
        name: myapp
        state: restarted

The DB credentials are unique to this playbook run and expire automatically (TTL 1h). No long-lived credentials are stored on the host.

I3How do you store Ansible Vault passwords in HashiCorp Vault and retrieve them in CI?

Ansible Vault (the file encryption tool) can use a custom script as a password source. Store the Ansible Vault password in HashiCorp Vault and retrieve it at runtime:

#!/bin/bash
# vault-password-script.sh
export VAULT_ADDR="https://vault.example.com:8200"
export VAULT_TOKEN="$(vault write -field=token auth/approle/login \
  role_id=$VAULT_ROLE_ID secret_id=$VAULT_SECRET_ID)"
vault kv get -field=password secret/ansible/vault-password
# Run playbook using the script as password provider
ansible-playbook site.yml \
  --vault-password-file=./vault-password-script.sh \
  -i inventory/prod

This eliminates storing the Ansible Vault password in CI environment variables or on disk.

I4How do you configure the Vault lookup plugin using environment variables for cleaner playbooks?

Set connection parameters via environment variables to avoid repeating them in every lookup:

# Set in CI or shell before running ansible-playbook
export VAULT_ADDR="https://vault.example.com:8200"
export VAULT_AUTH_METHOD="approle"
export VAULT_ROLE_ID="$(cat /run/secrets/role-id)"
export VAULT_SECRET_ID="$(cat /run/secrets/secret-id)"
# playbook — clean lookup without inline auth params
vars:
  db_pass: "{{ lookup('community.hashi_vault.hashi_vault', 'secret=secret/data/app/db:password') }}"
  api_key: "{{ lookup('community.hashi_vault.hashi_vault', 'secret=secret/data/app/api:key') }}"

Alternatively, configure defaults in ansible.cfg under [hashi_vault_collection] for organisation-wide settings.

🏗️ Vault + Terraform Integration
I5 – I8 Vault Provider · Dynamic Creds · AppRole · TFC

Using the Vault Terraform provider to read secrets, generate dynamic AWS credentials, and configure Vault resources — all as code.

I5How do you configure the HashiCorp Vault Terraform provider and read a KV secret?
Terraform ↔ Vault
terraform {
  required_providers {
    vault = {
      source  = "hashicorp/vault"
      version = "~> 4.0"
    }
  }
}

provider "vault" {
  address = "https://vault.example.com:8200"
  # Auth via VAULT_TOKEN env var, or configure auth_login block
}

# Read a KV v2 secret
data "vault_kv_secret_v2" "db" {
  mount = "secret"
  name  = "myapp/db"
}

resource "aws_db_instance" "main" {
  username = data.vault_kv_secret_v2.db.data["username"]
  password = data.vault_kv_secret_v2.db.data["password"]
  # ...
}
Warning: Secret values read by Terraform are stored in the state file. Ensure state is encrypted and access-controlled.
I6How do you use Vault's AWS secrets engine to provide dynamic credentials to Terraform?

Instead of using static IAM keys in CI, Terraform authenticates to Vault via AppRole and requests dynamic AWS credentials:

provider "vault" {
  address = "https://vault.example.com:8200"
  auth_login {
    path = "auth/approle/login"
    parameters = {
      role_id   = var.vault_role_id
      secret_id = var.vault_secret_id
    }
  }
}

# Get dynamic AWS IAM STS credentials
data "vault_aws_access_credentials" "deploy" {
  backend = "aws"
  role    = "terraform-deployer"
  type    = "sts"  # STS AssumeRole — no IAM user created
}

provider "aws" {
  access_key = data.vault_aws_access_credentials.deploy.access_key
  secret_key = data.vault_aws_access_credentials.deploy.secret_key
  token      = data.vault_aws_access_credentials.deploy.security_token
  region     = "us-east-1"
}

The AWS credentials are short-lived STS tokens — no long-lived IAM access keys in CI pipelines.

I7How do you manage Vault configuration itself with Terraform (Vault-as-code)?

The Vault provider can also create Vault resources — policies, auth method roles, secret engines — treating Vault config as code:

# Create a KV v2 mount
resource "vault_mount" "kv" {
  path = "secret"
  type = "kv-v2"
}

# Create a policy
resource "vault_policy" "app" {
  name   = "my-app"
  policy = file("${path.module}/policies/my-app.hcl")
}

# Create an AppRole and bind the policy
resource "vault_approle_auth_backend_role" "app" {
  backend        = "approle"
  role_name      = "my-app"
  token_policies = [vault_policy.app.name]
  token_ttl      = "3600"
  secret_id_ttl  = "600"
  secret_id_num_uses = "1"
}

This gives you version history, PR reviews, and automated testing of Vault configuration changes.

I8How do you use Vault with Terraform Cloud (TFC) workspace variables securely?

Terraform Cloud can authenticate to Vault using its built-in OIDC token (TFC JWT auth):

# In Vault — configure JWT auth for TFC
vault auth enable jwt
vault write auth/jwt/config \
  jwks_url="https://app.terraform.io/.well-known/jwks" \
  bound_issuer="https://app.terraform.io"

vault write auth/jwt/role/tfc-workspace \
  role_type="jwt" \
  bound_audiences="vault.workload.identity" \
  bound_claims_type="glob" \
  bound_claims='{"sub":"organization:my-org:project:*:workspace:prod-*:run_phase:*"}' \
  policies="tfc-deploy" \
  ttl="20m"
# In TFC workspace — set env variables
TFC_VAULT_PROVIDER_AUTH = true
TFC_VAULT_ADDR          = https://vault.example.com:8200
TFC_VAULT_RUN_ROLE      = tfc-workspace

No static VAULT_TOKEN stored in TFC — the workspace authenticates via its short-lived JWT identity.

⚡ Vault + GitHub Actions Integration
I9 – I12 OIDC · JWT · hashicorp/vault-action

Authenticating GitHub Actions workflows to Vault using OIDC (no static secrets), reading KV secrets, dynamic AWS credentials, and PKI certificates in CI pipelines.

I9How does GitHub Actions authenticate to Vault without storing any static credentials?
GitHub Actions ↔ Vault

GitHub Actions generates a short-lived OIDC JWT for each workflow run. Vault validates it against GitHub's JWKS endpoint — no VAULT_TOKEN stored in GitHub Secrets.

Step 1 — Configure Vault JWT auth (one-time):

vault auth enable jwt

vault write auth/jwt/config \
  jwks_url="https://token.actions.githubusercontent.com/.well-known/jwks" \
  bound_issuer="https://token.actions.githubusercontent.com"

vault write auth/jwt/role/github-actions \
  role_type="jwt" \
  bound_audiences="https://github.com/my-org" \
  bound_subject="repo:my-org/my-repo:ref:refs/heads/main" \
  bound_claims='{"repository":"my-org/my-repo"}' \
  user_claim="actor" \
  policies="github-ci-policy" \
  ttl="20m"
I10Show a complete GitHub Actions workflow using hashicorp/vault-action to read KV secrets.
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write   # Required for OIDC token generation
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Get secrets from Vault
        uses: hashicorp/vault-action@v3
        with:
          url: https://vault.example.com:8200
          method: jwt
          role: github-actions
          jwtGithubAudience: "https://github.com/my-org"
          secrets: |
            secret/data/myapp/db    username | DB_USER ;
            secret/data/myapp/db    password | DB_PASS ;
            secret/data/myapp/api   key      | API_KEY

      - name: Deploy application
        run: |
          echo "Deploying with DB_USER=$DB_USER"
          ./scripts/deploy.sh
        env:
          DB_USER: ${{ env.DB_USER }}
          DB_PASS: ${{ env.DB_PASS }}
          API_KEY: ${{ env.API_KEY }}
Note: vault-action masks all secret values in workflow logs automatically.
I11How do you use Vault's AWS secrets engine in GitHub Actions to get dynamic IAM credentials?
# .github/workflows/terraform.yml
name: Terraform Apply
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  apply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Authenticate to Vault and get AWS creds
        uses: hashicorp/vault-action@v3
        with:
          url: https://vault.example.com:8200
          method: jwt
          role: github-actions
          secrets: |
            aws/creds/terraform-deployer access_key     | AWS_ACCESS_KEY_ID ;
            aws/creds/terraform-deployer secret_key     | AWS_SECRET_ACCESS_KEY ;
            aws/creds/terraform-deployer security_token | AWS_SESSION_TOKEN

      - name: Terraform Init and Apply
        run: |
          terraform init
          terraform apply -auto-approve
        env:
          AWS_ACCESS_KEY_ID:     ${{ env.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ env.AWS_SECRET_ACCESS_KEY }}
          AWS_SESSION_TOKEN:     ${{ env.AWS_SESSION_TOKEN }}

AWS credentials are generated fresh for each run (TTL 15–60 min) and auto-revoked by Vault after the run.

I12How do you request a short-lived TLS certificate from Vault PKI in a GitHub Actions deployment?
# .github/workflows/deploy-cert.yml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Auth to Vault
        id: vault-auth
        run: |
          VAULT_TOKEN=$(vault write -field=token auth/jwt/login \
            role=github-actions \
            jwt="$ACTIONS_ID_TOKEN_REQUEST_VALUE")
          echo "VAULT_TOKEN=$VAULT_TOKEN" >> $GITHUB_ENV
        env:
          VAULT_ADDR: https://vault.example.com:8200

      - name: Issue TLS certificate
        run: |
          vault write -format=json pki/issue/web-server \
            common_name="deploy-${{ github.run_id }}.internal.example.com" \
            ttl="2h" > cert.json

          cat cert.json | jq -r '.data.certificate' > /tmp/server.crt
          cat cert.json | jq -r '.data.private_key' > /tmp/server.key
          echo "Certificate issued for deployment ${{ github.run_id }}"
        env:
          VAULT_ADDR: https://vault.example.com:8200

      - name: Deploy with certificate
        run: ./scripts/deploy.sh --cert /tmp/server.crt --key /tmp/server.key

      - name: Revoke Vault token
        if: always()
        run: vault token revoke -self
        env:
          VAULT_ADDR: https://vault.example.com:8200

The certificate has a 2-hour TTL aligned to the deployment window. Always revoke the Vault token in a final if: always() step to clean up immediately rather than waiting for TTL expiry.
