Infrastructure as Code — Terraform

62 advanced questions covering Terraform core concepts, state management, modules, variables, workspaces, advanced HCL patterns, and Terraform Cloud security — with real-world answers and code examples.

🏗️ Terraform Basics
T1 – T10 Core Concepts

Foundational Terraform — workflow, configuration language, lifecycle, and how Terraform compares to other IaC tools.

T1What is Terraform and how does it differ from configuration management tools like Ansible or Chef?

Terraform is a declarative Infrastructure as Code (IaC) tool that provisions and manages cloud resources. It differs from configuration management tools in scope and purpose.

Terraform (IaC)
Provisions infrastructure (VMs, networks, databases). Declarative — describe desired state. Idempotent via state file. Best for cloud resource lifecycle.
Ansible / Chef (CM)
Configures software on existing machines. Procedural or declarative. No persistent state. Best for OS config, package installs, app setup.

They are complementary — Terraform creates a VM, Ansible configures it.

T2Explain the Terraform core workflow: init → plan → apply → destroy.
  • terraform init — downloads providers, sets up backend, initialises modules.
  • terraform plan — computes the diff between current state and desired config; shows additions, changes, deletions. No changes made.
  • terraform apply — executes the plan. Creates/updates/destroys real resources and updates the state file.
  • terraform destroy — equivalent to apply -destroy; removes all managed resources.
Tip: Always review terraform plan output carefully before applying, especially in production. Use -out=plan.tfplan to save and apply the exact plan.
T3What is a Terraform provider and why is provider versioning important?

A provider is a plugin that maps Terraform resource types to API calls for a target platform (AWS, GCP, Azure, Kubernetes, etc.). Each provider is maintained separately and downloaded during terraform init.

Provider versioning is critical because:

  • Breaking changes between major versions can destroy or recreate resources unexpectedly.
  • The .terraform.lock.hcl file pins exact provider checksums for reproducible runs.
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"  # allows 5.x but not 6.x
    }
  }
}
T4What is the difference between terraform.tfvars and *.auto.tfvars?

Both files provide variable values, but loading is automatic for *.auto.tfvars:

FileAuto-loaded?Use case
terraform.tfvarsYes (always)Default values for the root module
*.auto.tfvarsYes (alphabetical order)Environment-specific overrides checked in to VCS
-var-file=foo.tfvarsNo — explicit flag neededCI/CD pipelines, secrets

Precedence (lowest → highest): defaults → terraform.tfvars → *.auto.tfvars → -var-file → -var → TF_VAR_* env vars.

T5What is terraform refresh and when should you avoid it?

terraform refresh reconciles Terraform's state file with the real-world infrastructure without making any changes. It updates the state to reflect out-of-band modifications.

Avoid it when:

  • You suspect drift and want a plan to fix it — refresh accepts the drift, losing the diff.
  • In Terraform v1.x, terraform plan -refresh-only is preferred — it shows what would change and lets you review before accepting.
T6Explain the concept of idempotency in Terraform.

Idempotency means running the same Terraform config multiple times produces the same result. Terraform achieves this through its state-based model:

  • On each apply, Terraform reads state, refreshes real-world status, computes a diff, and applies only what has changed.
  • If nothing changed, the plan is empty and no API calls are made.

This is unlike procedural scripts where re-running may create duplicate resources. However, idempotency can break if resources are modified outside Terraform (drift).

T7What is the depends_on meta-argument and when is it needed?

Terraform automatically infers resource dependencies from attribute references. depends_on adds an explicit dependency when Terraform cannot detect it implicitly.

resource "aws_iam_role_policy_attachment" "attach" {
  role       = aws_iam_role.lambda.name
  policy_arn = aws_iam_policy.custom.arn

  depends_on = [aws_iam_role.lambda]  # explicit, usually not needed here
}

When needed: when a resource depends on a side-effect of another resource (e.g., IAM policy propagation) rather than an output attribute.

T8What is the lifecycle block and describe its key arguments.

The lifecycle meta-block controls resource replacement and deletion behaviour:

ArgumentEffect
create_before_destroyCreate replacement first, then destroy old resource. Prevents downtime for resources that cannot be updated in-place.
prevent_destroyCauses terraform plan to error if the resource would be destroyed. Protects production databases.
ignore_changesTerraform ignores specified attribute drifts. Useful for auto-scaling groups or user-managed tags.
replace_triggered_byForces replacement when a referenced resource or value changes.
T9How does Terraform handle sensitive values in configuration and state?

Marking a variable or output as sensitive = true prevents its value from appearing in plan/apply output. However, sensitive values are still stored in plain text in the state file.

  • Always use encrypted remote backends (S3 + SSE, Terraform Cloud) for state storage.
  • Never commit terraform.tfstate to VCS.
  • Use Vault or AWS Secrets Manager to inject secrets at runtime rather than storing them in variables.
Pitfall: sensitive = true is a display mask only — it does not encrypt the value in state.
T10What is the .terraform.lock.hcl file and should it be committed to version control?

The lock file records the exact versions and checksums of providers selected during terraform init. It ensures every team member and CI run uses identical providers.

Yes, commit it to VCS. Reasons:

  • Guarantees reproducible builds across environments.
  • Prevents silent provider upgrades that could introduce breaking changes.
  • Run terraform init -upgrade explicitly to update providers and regenerate the lock file.

T12How do you configure multiple provider instances for different AWS regions or accounts?

Use provider aliases to configure multiple instances of the same provider:

provider "aws" {
  region = "us-east-1"  # default
}

provider "aws" {
  alias  = "eu"
  region = "eu-west-1"
}

resource "aws_s3_bucket" "eu_bucket" {
  provider = aws.eu
  bucket   = "my-eu-bucket"
}

For multi-account setups, use assume_role blocks within each provider configuration.

T13What is the terraform_remote_state data source and what are its drawbacks?

terraform_remote_state reads outputs from another Terraform state file, enabling cross-stack data sharing (e.g., networking stack exports VPC ID consumed by app stack).

Drawbacks:

  • Tight coupling — consumer stack breaks if producer output is renamed or removed.
  • Read access to full state — the consumer needs access to the entire state file which may contain sensitive data.
  • Prefer alternatives: AWS SSM Parameter Store, Consul, or explicit outputs passed via CI/CD variables for looser coupling.
T14How does the required_providers block differ from the provider configuration block?

required_providers (inside the terraform block) declares which providers are needed and their version constraints — it is a dependency specification. The provider block configures how the provider authenticates and connects.

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region  = "us-east-1"
  profile = "prod"
}

T16Explain dynamic blocks in Terraform with an example.

dynamic blocks generate repeated nested configuration blocks programmatically, avoiding copy-paste for variable-length nested blocks like security group rules:

resource "aws_security_group" "web" {
  name = "web-sg"

  dynamic "ingress" {
    for_each = var.ingress_rules
    content {
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = ingress.value.cidrs
    }
  }
}

The iterator label (ingress) defaults to the block name but can be customised with iterator = rule.

T17What is a null_resource and when is it useful?

null_resource (from the hashicorp/null provider) is a resource with no real infrastructure backing. It's used to run provisioners or trigger re-runs based on arbitrary conditions:

resource "null_resource" "run_script" {
  triggers = {
    config_hash = filemd5("${path.module}/config.sh")
  }
  provisioner "local-exec" {
    command = "bash config.sh"
  }
}

The triggers map forces recreation when values change. In modern Terraform, prefer terraform_data (built-in equivalent added in v1.4) over null_resource.

T18How do you import existing infrastructure into Terraform management?

Two approaches — CLI import and the newer config-driven import block:

CLI (classic): terraform import aws_s3_bucket.my_bucket my-existing-bucket-name — updates state but does not write HCL config.

Import block (Terraform v1.5+):

import {
  to = aws_s3_bucket.my_bucket
  id = "my-existing-bucket-name"
}

resource "aws_s3_bucket" "my_bucket" {
  bucket = "my-existing-bucket-name"
}

Combine with terraform plan -generate-config-out=generated.tf to auto-generate the resource config.

🗄️ State Management Basics
S1 – S9 Remote State · Locking · Backends

Terraform state file structure, remote backends, state locking, and team collaboration patterns.

S1What is the Terraform state file and what does it contain?

The state file (terraform.tfstate) is a JSON document that maps Terraform resource addresses to real-world resource IDs and their current attribute values. It is the source of truth for Terraform's view of deployed infrastructure.

It contains: resource type, name, provider config, all attributes (including sensitive ones), resource metadata, dependencies, and output values.

Never edit it manually. Use terraform state sub-commands for any state manipulation.
S2Why should Terraform state be stored in a remote backend for team environments?
  • Shared access — all team members and CI pipelines read the same state.
  • State locking — prevents concurrent applies that could corrupt state.
  • Encryption at rest — S3 with SSE, Terraform Cloud encrypt sensitive state data.
  • Versioning / history — S3 bucket versioning allows rollback to a previous state.
  • Avoid VCS commits — state contains secrets; it must not be in git.
S3How does Terraform implement state locking with S3 and DynamoDB?

The S3 backend uses a DynamoDB table for distributed locking:

terraform {
  backend "s3" {
    bucket         = "my-tf-state"
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks"  # LockID as partition key
    encrypt        = true
  }
}

When terraform apply starts, it writes a lock item to DynamoDB. If another process holds the lock, Terraform waits or errors. The lock is released when apply finishes or crashes.

S4What happens if a Terraform apply crashes mid-run and leaves a stale lock?

Terraform detects the lock and prevents other runs. The lock record in DynamoDB contains the lock ID, operation, and timestamp.

Resolve with: terraform force-unlock <LOCK_ID>

Always verify the crashed apply didn't partially create resources before force-unlocking — check the state file and real infrastructure to understand the blast radius.

S5How do you migrate the Terraform backend from local to remote (e.g., S3)?
  1. Add the backend block to your Terraform config.
  2. Run terraform init — Terraform detects the new backend and asks: "Would you like to copy existing state to the new backend?"
  3. Answer yes — state is uploaded to S3.
  4. Delete the local terraform.tfstate and .terraform.tfstate.backup files.
  5. Commit the updated config (without the state file).
Take a backup of local state before migrating, in case something goes wrong.
S6What is state drift and how do you detect and remediate it?

Drift occurs when the real-world infrastructure differs from what's recorded in the Terraform state (e.g., someone manually changed a security group rule in the console).

Detect: terraform plan -refresh-only shows the diff between actual infrastructure and state without proposing config changes.

Remediate:

  • Accept drift — run terraform apply -refresh-only to update state to match reality.
  • Revert drift — run terraform apply normally to enforce the desired configuration.
S7Explain partial state and how Terraform handles resource creation failures.

If a terraform apply fails partway through, Terraform writes the state of successfully created resources to the state file before exiting. This is called partial state.

On the next terraform apply, Terraform resumes from partial state — it knows which resources exist and only attempts to create what's missing or fix what failed. This avoids duplicate resource creation.

S8What is the difference between a Terraform backend and a remote backend?

In Terraform terminology, backend refers to where state is stored and how operations run. There are two categories:

TypeState storedOperations run
local (default)Local diskLocally (your machine)
remote (e.g. S3, GCS)Remote storageLocally
Terraform Cloud / EnterpriseTerraform CloudRemotely (in TFC runners)
S9What is the purpose of the -target flag in Terraform plan/apply and when should you avoid it?

-target=aws_instance.web restricts the operation to a specific resource and its dependencies. Useful for:

  • Debugging a single resource during development.
  • Emergency hotfixes where a full apply would take too long.

Avoid in normal workflows: targeting bypasses dependency resolution and can leave the configuration in an inconsistent state where untargeted resources are out of sync with the config.

Rule: if you use -target in an emergency, follow up immediately with a clean full apply.
🔧 State Operations
S10 – S17 mv · rm · taint · untaint

Hands-on state manipulation commands — moving resources, removing from state, marking for replacement, and splitting state files.

S10When and how do you use terraform state mv?

terraform state mv renames a resource in state without destroying and recreating it. Common use cases:

  • Renaming a resource in your HCL config.
  • Moving a resource into a module.
  • Migrating from count to for_each.
terraform state mv aws_instance.old aws_instance.new
terraform state mv aws_instance.web module.app.aws_instance.web
Always take a state backup first: terraform state pull > backup.tfstate
S11What does terraform state rm do and when is it appropriate?

terraform state rm removes a resource from Terraform state without destroying the real infrastructure. Use when:

  • A resource should no longer be managed by Terraform (transferring to manual management).
  • A resource was deleted manually and you want to clean up state.
  • You're splitting a monolith state into smaller states (combined with import in the new config).

After removal, the resource becomes unmanaged — Terraform won't touch it.

S12What replaced terraform taint in modern Terraform versions?

In Terraform v0.15.2+, terraform taint was deprecated. The modern equivalent is terraform apply -replace=<address>:

terraform apply -replace="aws_instance.web"

This plans and immediately applies the resource replacement in one step, showing the plan before applying, unlike the old two-step taint → apply workflow.

S13How do you split a large Terraform state file into smaller ones?
  1. Create new Terraform root module for the extracted resources.
  2. Use terraform state pull > full.tfstate to get the current state.
  3. Use terraform state mv to move resources from the old state to the new workspace/state, or use state rm + import in the new module.
  4. Remove the migrated resource configs from the original module.
  5. Run terraform plan on both modules to verify no unintended changes.
S14What is the moved block introduced in Terraform v1.1?

The moved block allows you to refactor resource addresses in config and have Terraform automatically update state — without running terraform state mv manually:

moved {
  from = aws_instance.web
  to   = module.app.aws_instance.web
}

This is safe to commit to VCS and enables team-wide refactoring. Once all team members have applied, the moved block can be removed.

📦 Modules & Reuse
M1 – M9 Module Design · Registry · Versioning

Creating reusable, well-designed Terraform modules — structure, inputs/outputs, versioning, and module registry patterns.

M1What is a Terraform module and what are the components of a well-structured module?

A module is a directory of .tf files that encapsulates related infrastructure. Every Terraform configuration is a module (the root module). The key files in a reusable module:

FilePurpose
main.tfPrimary resource definitions
variables.tfInput variable declarations with types, defaults, descriptions, validations
outputs.tfExported values for callers to consume
versions.tfrequired_providers and required_version constraints
README.mdUsage docs, input/output table
M2What are the different module source types in Terraform?
SourceExample
Local pathsource = "./modules/vpc"
Terraform Registrysource = "terraform-aws-modules/vpc/aws"
GitHubsource = "github.com/org/repo//modules/vpc"
Git (generic)source = "git::https://example.com/vpc.git?ref=v1.2"
S3 bucketsource = "s3::https://bucket.s3.amazonaws.com/module.zip"

The // double-slash separates the repo root from the subdirectory within it.

M3How do you pass provider configurations to child modules?

By default, child modules inherit the default providers from the parent. For aliased providers, pass them explicitly using the providers argument:

module "eu_app" {
  source = "./modules/app"
  providers = {
    aws = aws.eu
  }
}

Inside the module, declare required_providers with a configuration_aliases if it needs to be explicit about which aliases it accepts.

M4What are module output values and how do you access them?

Outputs expose internal values of a module to the calling configuration. Defined in outputs.tf:

# Inside module
output "vpc_id" {
  value       = aws_vpc.main.id
  description = "The VPC ID"
}

# In root module
subnet_vpc_id = module.vpc.vpc_id

Outputs can be marked sensitive = true to suppress display. Module outputs are only visible after terraform apply.

M5How do you version-pin a module from the Terraform Registry?
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.1"  # allows 5.1.x but not 5.2
}

Version constraints follow SemVer operators: =, !=, >=, <=, ~> (pessimistic constraint). Always pin modules in production to avoid unexpected upgrades. Run terraform init -upgrade to explicitly bump.

M6How do you validate module inputs using variable validation blocks?
variable "environment" {
  type        = string
  description = "Deployment environment"
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Must be dev, staging, or prod."
  }
}

variable "instance_count" {
  type = number
  validation {
    condition     = var.instance_count >= 1 && var.instance_count <= 20
    error_message = "Instance count must be between 1 and 20."
  }
}

Validation errors fail at plan time, preventing invalid configurations from reaching the API.

M7What is the difference between root module and child module in Terraform execution context?

The root module is the directory where you run Terraform commands — it owns the state file and backend configuration. Child modules are called by the root (or other modules) and share the root's state file, with their resources addressed as module.name.resource_type.resource_name.

Child modules cannot have their own backend or state — they always operate within the caller's state context.

M8How do you call a module multiple times with different configurations?

Use multiple module blocks with different names, or use for_each on the module block:

# for_each on a module (Terraform 0.13+)
module "app" {
  source   = "./modules/app"
  for_each = toset(["us-east-1", "eu-west-1"])
  region   = each.key
  env      = "prod"
}

Resources are addressed as module.app["us-east-1"].aws_instance.web.

M9What is a monorepo vs. polyrepo pattern for Terraform modules?
Monorepo
All modules and root configs in one repo. Easy cross-module changes, single CI pipeline, good for small/medium teams. Risk: blast radius — a bad change affects everything.
Polyrepo
Each module in its own repo with independent versioning and CI. Better isolation and release cadence. Overhead: more repos to manage, version bumps require PRs.

Many large teams use a hybrid — shared modules in a dedicated registry repo, root configs per environment in separate repos.

V3When should you use locals over variables?

Use locals when:

  • The value is derived from other values (computed): locals { name = "${var.env}-${var.app}" }
  • You want to DRY up a repeated expression used in multiple places.
  • The value should not be overridden by callers — locals are private to the module.

Use variables for anything that needs to be configurable by the module caller.

V4How do environment variables map to Terraform variables?

Prefix the variable name with TF_VAR_:

export TF_VAR_region="us-west-2"
export TF_VAR_instance_count=5

This is useful in CI/CD pipelines to inject secrets (DB passwords, API keys) without storing them in .tfvars files. Environment variables have the second-highest precedence, overridden only by explicit -var flags.

V5Explain the for expression and for_each with a practical example.

The for expression transforms collections inline:

# Transform a list to a map
locals {
  sg_ids_map = { for sg in aws_security_group.web : sg.name => sg.id }
}

# Filter: only prod instances
locals {
  prod_instances = [for i in var.instances : i if i.env == "prod"]
}

for_each on a resource iterates a map or set to create multiple resource instances, each independently addressable in state.

V6What is the templatefile function and when is it preferred over heredoc?

templatefile(path, vars) reads a file and renders it as a template with variable substitution. Preferred over heredoc when:

  • The template is large (user-data scripts, policy documents).
  • The template is reused across multiple resources.
  • You want to keep HCL files clean and the template in a separate .tpl file.
user_data = templatefile("${path.module}/userdata.sh.tpl", {
  db_host = aws_db_instance.main.endpoint
  env     = var.environment
})
V7What is the coalesce and coalescelist function used for?

coalesce(val1, val2, ...) returns the first non-null, non-empty string argument. Useful for fallback logic:

name = coalesce(var.custom_name, "${var.env}-app")

coalescelist does the same for lists. The one() function (v1.0+) extracts a single value from a list of zero or one elements — handy when a data source may return 0 or 1 results.

V8How do you handle optional object attributes in Terraform variables?

Use the optional() modifier (Terraform v1.3+) inside object type constraints to mark attributes as optional with defaults:

variable "config" {
  type = object({
    name        = string
    port        = optional(number, 8080)
    enable_logs = optional(bool, false)
  })
}

Callers don't need to specify optional attributes; Terraform injects the default automatically.

🔁 Workspaces & Environments
W1 – W6 Workspaces · Multi-env · Patterns

Terraform workspaces for environment isolation, their limitations, and recommended multi-environment patterns.

W1What are Terraform workspaces and what problem do they solve?

Workspaces allow multiple state files to exist within the same backend configuration. Each workspace has an isolated state. The default workspace is named default.

terraform workspace new staging
terraform workspace select prod
terraform workspace list

They solve the problem of needing to manage multiple environments (dev/staging/prod) from the same configuration without separate backend configs.

W2What are the limitations of Terraform workspaces for environment management?
  • Same config/code — all workspaces use identical infrastructure code; you can't have meaningfully different architectures per environment without complex conditionals.
  • No access control — workspaces share the same backend; you can't restrict who runs production applies at the workspace level.
  • Hard to review — it's easy to accidentally apply to the wrong workspace.
Recommendation: Use separate directories or repos per environment for production-grade isolation. Workspaces are good for ephemeral per-PR environments.
W3How do you reference the current workspace name in a Terraform config?
resource "aws_s3_bucket" "data" {
  bucket = "myapp-${terraform.workspace}-data"
}

locals {
  is_prod    = terraform.workspace == "prod"
  min_size   = local.is_prod ? 3 : 1
}

terraform.workspace is a built-in value. Use it to vary resource sizes, tags, or feature flags per environment.

W4Describe a multi-environment Terraform directory structure without using workspaces.
infra/
├── modules/
│   ├── vpc/
│   └── app/
├── environments/
│   ├── dev/
│   │   ├── main.tf      # calls modules
│   │   ├── terraform.tfvars
│   │   └── backend.tf   # dev-specific backend
│   ├── staging/
│   └── prod/

Each environment directory has its own state file, backend, and variable values. Clear separation, independent CI pipelines, and IAM role isolation per environment.

W5What is Terragrunt and when would you use it over vanilla Terraform?

Terragrunt is a thin wrapper around Terraform that adds:

  • DRY backend configs — generate backend config from a root terragrunt.hcl instead of repeating it in every module.
  • Dependency management — dependency blocks that pass outputs between stacks without terraform_remote_state.
  • Run-all commands — apply multiple modules in dependency order.
  • Environment composition — layered variable files per environment/region/account.

Use Terragrunt when managing many environments and modules where Terraform's native DRY capabilities feel limiting.

W6How do you create ephemeral per-PR environments with Terraform?

Pattern using Terraform workspaces + CI/CD:

  1. On PR open: terraform workspace new pr-${PR_NUMBER} → terraform apply → post environment URL as PR comment.
  2. On PR update: terraform workspace select pr-${PR_NUMBER} → terraform plan → terraform apply.
  3. On PR merge/close: terraform workspace select pr-${PR_NUMBER} → terraform destroy → terraform workspace delete pr-${PR_NUMBER}.

Use consistent naming, resource tagging with the workspace name, and cost budgets to prevent runaway environments.

⚡ Advanced Terraform Patterns
A1 – A9 Meta-args · Functions · Expressions

Advanced HCL features, functions, provisioners, testing, and performance patterns for large-scale Terraform deployments.

A1What is the difference between toset, tomap, and tolist and when do you need them?

These are type conversion functions to ensure for_each receives the correct type:

  • toset(list) — deduplicates and converts a list to a set; required for for_each with a list of strings.
  • tomap({…}) — explicitly converts to a map type with consistent value types.
  • tolist(set) — converts a set to a list for indexing (sets are unordered).
for_each = toset(["web", "api", "db"])
# each.key == "web", "api", "db"
A2How do you use precondition and postcondition checks in Terraform?

Introduced in Terraform v1.2, these custom conditions validate assumptions about inputs and outputs:

resource "aws_instance" "web" {
  instance_type = var.instance_type

  lifecycle {
    precondition {
      condition     = contains(["t3.micro", "t3.small"], var.instance_type)
      error_message = "Only t3.micro or t3.small are allowed."
    }
    postcondition {
      condition     = self.public_ip != ""
      error_message = "Instance must have a public IP."
    }
  }
}

Preconditions run during plan; postconditions run after apply to verify the real outcome.

A3How does Terraform build and execute its dependency graph?

Terraform parses all .tf files and builds a directed acyclic graph (DAG) of resources based on attribute references. Independent resources are applied in parallel (default 10 concurrent operations); dependent resources are sequenced.

terraform graph | dot -Tsvg > graph.svg visualises the dependency graph.

Explicit ordering is added via depends_on. Circular dependencies cause a plan-time error.

A4What are Terraform provisioners and why should they be a last resort?

Provisioners (local-exec, remote-exec, file) run scripts as part of resource creation/destruction. They are a last resort because:

  • Non-idempotent — failure leaves resources in an unknown state.
  • No plan visibility — provisioner commands don't appear in terraform plan.
  • Network dependency — remote-exec requires SSH/WinRM access at apply time.

Prefer: user-data scripts, cloud-init, Packer images, or configuration management tools post-provisioning.

A6How do you structure a large Terraform codebase to avoid a single massive state file?

Split by lifecycle and blast radius — resources that change together should be in the same state; resources that change independently should be separated:

  • Foundation layer — VPCs, DNS zones, IAM roles (rarely changes, high risk).
  • Platform layer — EKS/RDS clusters, shared services (changes occasionally).
  • Application layer — app-specific resources (changes frequently).

Use outputs + SSM/remote_state for cross-layer data passing. Each layer has its own state file and CI pipeline with appropriate approval gates.

A7What is the check block in Terraform v1.5+ and how does it differ from lifecycle conditions?

The check block performs assertions that emit warnings rather than failures, allowing apply to succeed while flagging drift or configuration issues:

check "health_check" {
  data "http" "probe" {
    url = "https://${aws_lb.web.dns_name}/health"
  }
  assert {
    condition     = data.http.probe.status_code == 200
    error_message = "Health endpoint returned ${data.http.probe.status_code}"
  }
}

Unlike lifecycle postcondition (which blocks apply on failure), check blocks are non-blocking observability checks run after every apply.

A8How do you use jsonencode and yamlencode for IAM policies and Kubernetes manifests?

These functions convert HCL data structures to JSON/YAML strings, enabling type-safe policy authoring:

data "aws_iam_policy_document" is preferred, but inline:

policy = jsonencode({
  Version = "2012-10-17"
  Statement = [{
    Effect   = "Allow"
    Action   = ["s3:GetObject"]
    Resource = "${aws_s3_bucket.data.arn}/*"
  }]
})

Benefits over heredoc: HCL syntax checking, interpolation support, no JSON escaping issues.

A9What performance improvements can you apply to a slow terraform plan?
  • -parallelism=N — increase concurrent API calls (default 10). Use with caution — rate limits can trigger errors.
  • -refresh=false — skip state refresh if you know infra hasn't changed out-of-band.
  • Smaller state files — split monolith states into focused modules.
  • provider_meta caching — use provider-level assume_role caching where available.
  • Targeted plans — -target for development iteration (not production).

C2How do you avoid storing AWS credentials in Terraform CI pipelines using OIDC?

Use OpenID Connect (OIDC) to let GitHub Actions (or similar CI) assume an AWS IAM role without static credentials:

  1. Create an IAM OIDC identity provider for token.actions.githubusercontent.com.
  2. Create an IAM role with a trust policy allowing the GitHub OIDC provider to assume it, scoped to your repo/branch.
  3. In the workflow, use aws-actions/configure-aws-credentials with role-to-assume.

No long-lived access keys are stored in secrets. Tokens are short-lived (15 min) and automatically rotated.

C3What is Sentinel policy-as-code in Terraform Cloud?

Sentinel is HashiCorp's embedded policy-as-code framework that runs after terraform plan and before terraform apply. Policies inspect the plan JSON to enforce governance rules:

# Sentinel: require all S3 buckets to be private
import "tfplan/v2" as tfplan

all_s3_buckets = filter tfplan.resource_changes as _, rc {
  rc.type == "aws_s3_bucket"
}

main = rule {
  all all_s3_buckets as _, bucket {
    bucket.change.after.acl == "private"
  }
}

Policy sets can be advisory (warn), soft-mandatory (overridable), or hard-mandatory (block apply).

C4How do you handle secrets in Terraform — specifically database passwords and API keys?

Recommended patterns:

  • AWS Secrets Manager / SSM Parameter Store — store secrets externally and read via data source at apply time. The secret value passes through state but is never in VCS.
  • Vault provider — generate dynamic credentials (e.g., short-lived DB passwords) that expire automatically.
  • SOPS-encrypted tfvars — encrypt .tfvars with AWS KMS or PGP using Mozilla SOPS; decrypt in CI.
  • Environment variables (TF_VAR_) — inject from CI secret store at runtime.
Never put secrets as default variable values in variables.tf or hard-coded in .tf files.
C5What is the Terraform provider development workflow and how do you use a local provider?

For using a local/custom provider during development:

# ~/.terraformrc
provider_installation {
  dev_overrides {
    "example.com/myorg/myprovider" = "/path/to/provider/binary"
  }
  direct {}
}

This tells Terraform to use the local binary instead of downloading from the registry. Remove dev overrides before publishing to production.

C6How do you implement a GitOps workflow with Terraform and pull requests?
  1. PR opened — CI runs terraform fmt -check, tflint, tfsec, terraform plan. Plan output posted as PR comment.
  2. Review — team reviews plan diff; policy checks run automatically (Sentinel/OPA).
  3. PR merged to main — CI runs terraform apply with the saved plan file from the plan step.
  4. No direct CLI applies — all changes go through PRs; apply is gated on approval and passing checks.

Tools: Atlantis (self-hosted), Terraform Cloud VCS workflow, GitHub Actions + tfcmt for plan comments.

C7What is the terraform providers lock command and when should you run it?

terraform providers lock updates the .terraform.lock.hcl file with checksums for specific platforms without running a full init:

terraform providers lock \
  -platform=linux_amd64 \
  -platform=darwin_arm64 \
  -platform=windows_amd64

Run it when: developers use macOS (arm64) but CI runs on Linux (amd64) — the default lock only includes the platform that ran init. Pre-populating all platform checksums ensures all team members and CI can use the same lock file.

C8How do you enforce resource tagging policies across all Terraform resources?

Three approaches:

  • Provider default_tags (AWS) — automatically applies tags to all taggable resources without repeating them: 
    provider "aws" {
  default_tags {
    tags = {
      Team        = "platform"
      Environment = var.env
      ManagedBy   = "terraform"
    }
  }
}
  • Sentinel/OPA policy — reject plans where required tags are missing.
  • Module wrapper — require callers to pass a tags variable; merge with module-level required tags using merge(local.required_tags, var.tags).
