ADO to GitHub Actions Migration & CI/CD

The critical multi-year project. Importer workflow, concept mapping, OIDC to AWS, runners, and migration leadership. 14 questions

Why they askOpening question. They want to see if you understand the business reason, not just the tools.

Masterstroke answer

A few reasons usually drive this. First, one platform for everything. Code, CI/CD, security scanning, and code review all live in GitHub. Fewer tools means less context switching and lower license cost. Second, the ecosystem. The GitHub Actions Marketplace has thousands of ready-made actions, so teams build pipelines faster. Third, security. GitHub gives you OIDC federation to AWS, so you can remove long-lived credentials completely. Fourth, developer experience. Most engineers already know GitHub, so onboarding is easier. The trade-off is real too: ADO has strong built-in boards and test plans, so those pieces need a plan of their own. For a bank, I would lead with the security and audit story: every pipeline change goes through a pull request, and the full history is in Git.

Key points to hit

  • One platform: code + CI/CD + security
  • Marketplace ecosystem speeds up teams
  • OIDC to AWS removes stored credentials
  • Be honest about what ADO does well (boards, test plans)
  • For a bank: audit trail and PR-based change control

Likely follow-ups

What do we lose by leaving ADO?

Azure Boards and Test Plans have no direct GitHub equal. GitHub Projects covers simple tracking. For test management you may keep a separate tool. Classic release pipelines with UI-based gates need redesign as workflows with environments.

Is this migration worth the cost?

Measure it. Count license savings, time saved per build, and security risk removed. If teams ship faster and audit gets easier, the numbers usually work out over 2-3 years.

Why they askThis is the heart of the role. They want a step-by-step plan, not buzzwords.

Masterstroke answer

I would run it in five phases. Phase 1: audit. Run the GitHub Actions Importer audit command against the whole ADO organization. It converts every pipeline on paper and gives a report showing which pipelines convert cleanly, which convert partly, and which need manual work. Now I have real numbers, not guesses. Phase 2: design the target. Set up the GitHub organization structure, OIDC roles to AWS, runner strategy, and required security workflows before any team moves. Phase 3: pilot. Pick one friendly team with a medium-complexity app. Migrate them end to end, fix what breaks, and write the playbook from what we learn. Phase 4: waves. Group the remaining teams into waves by complexity and business risk. Simple pipelines first, regulated or complex apps last. Each wave uses the playbook plus a central support channel. Phase 5: close out. Freeze new pipelines in ADO, set a shutdown date, and track a dashboard of migrated vs remaining pipelines. The rule I hold: teams migrate with help, not alone, and nothing moves to prod without the security scans re-attached.

Key points to hit

  • Audit first with GitHub Actions Importer for real data
  • Build the target platform (OIDC, runners, guardrails) before moving teams
  • Pilot with one team, write the playbook
  • Migrate in waves by complexity and risk
  • Track progress with a dashboard and set an ADO end date

Likely follow-ups

How long does the pilot take?

Usually 3-4 weeks for one team. The goal is not speed. The goal is a tested playbook the next twenty teams can follow.

What if a team refuses to move?

I find out why. Usually it is fear of breaking prod or lack of time. I offer hands-on pairing and migrate their lowest-risk pipeline first to build trust.

Why they askDirect tool knowledge for their exact project. Know the three commands cold.

Masterstroke answer

It is the official migration tool from GitHub. It runs as a Docker container with a GitHub CLI extension. It has three main commands. Audit: 'gh actions-importer audit azure-devops' scans a whole ADO organization, converts every pipeline to a draft workflow, and writes a summary report of how complete the migration can be. Dry-run: 'gh actions-importer dry-run azure-devops pipeline --pipeline-id X' converts one pipeline and writes the workflow file to disk so I can review it. Nothing changes in GitHub. Migrate: 'gh actions-importer migrate' does the conversion and opens a pull request in the target repo with the new workflow. That PR step matters in a bank because every migrated pipeline gets a human review and an audit record. Setup needs a GitHub PAT with workflow scope and an ADO personal access token. It needs ADO API version 5.0 or newer.

Key points to hit

  • Three commands: audit, dry-run, migrate
  • Audit gives a migration completeness report for the whole org
  • Migrate opens a PR, so every change is reviewed
  • Runs as Docker container + GitHub CLI extension
  • Needs GitHub PAT (workflow scope) and ADO PAT

Likely follow-ups

What can it NOT convert?

Service connections, secrets and variable group values, agent pools, and some tasks have no auto-conversion. Those need manual work. Classic UI pipelines convert poorly compared to YAML ones.

How do you handle tasks it does not know?

Custom transformers. You write a small Ruby snippet that tells the importer how to convert a specific ADO task into GitHub Actions steps. Write one per common in-house task and the whole org benefits.

Why they askA quick fluency test. If you can translate between the two systems, you can lead the migration.

Masterstroke answer

Pipelines become workflows, stored as YAML in .github/workflows. Stages and jobs map to jobs. Tasks map to steps and actions. Task groups and YAML templates become composite actions or reusable workflows called with workflow_call. Variable groups become GitHub secrets and variables, set at org, repo, or environment level. Service connections become OIDC federation or GitHub App credentials. Environments with approvals exist in both, and GitHub adds required reviewers and wait timers. Self-hosted agent pools become self-hosted runners and runner groups. Branch policies become branch protection rules and rulesets. Azure Artifacts maps to GitHub Packages, or you keep Artifactory if the bank already uses it. The one with no direct equal is Azure Boards. GitHub Projects covers light tracking, but if the bank uses Boards heavily, that needs its own decision.

Key points to hit

  • Pipeline = workflow, task group = reusable workflow / composite action
  • Variable groups = secrets + variables + environments
  • Service connections = OIDC (the big security win)
  • Agent pools = runners and runner groups
  • Boards has no direct equal, needs a separate decision

Likely follow-ups

How do reusable workflows differ from composite actions?

A reusable workflow is a whole workflow another workflow calls. It can have multiple jobs and use environments. A composite action is a bundle of steps inside one job. Rule of thumb: composite action for small step bundles, reusable workflow for full pipeline patterns.

Where do variable group secrets go?

Secrets cannot be exported from ADO. Someone re-enters them into GitHub secrets or, better, we move them to AWS Secrets Manager and read them at run time. Migration is the perfect moment to clean up secrets.

Why they askTheir cloud is AWS. OIDC is the single most important technical pattern for this job.

Masterstroke answer

OIDC federation. I create the GitHub OIDC identity provider in AWS IAM once per account. Then I create IAM roles with trust policies that only trust tokens from specific repos and branches. The condition checks the sub claim, for example repo:fhlbc/payments-service:ref:refs/heads/main. In the workflow, the aws-actions/configure-aws-credentials action requests a short-lived token from GitHub, exchanges it for temporary AWS credentials, and the job runs with those. They expire in about an hour. No access keys stored anywhere. For a bank this is a strong story: no long-lived credentials to leak or rotate, least privilege per repo and per branch, and every role assumption lands in CloudTrail for audit. I scope prod deploy roles to the main branch plus a protected environment, so a feature branch physically cannot deploy to prod.

Key points to hit

  • One OIDC provider per AWS account, roles per repo/purpose
  • Trust policy conditions on the sub claim (repo and branch)
  • aws-actions/configure-aws-credentials in the workflow
  • Short-lived credentials, nothing stored, CloudTrail audit
  • Prod roles locked to main branch + protected environment

Likely follow-ups

What replaces ADO service connections exactly?

Each service connection becomes an IAM role with a scoped trust policy. I inventory service connections during the audit phase and map each to a role with least-privilege permissions.

How do you stop one repo assuming another repo's role?

The trust policy sub condition names the exact repo. I also use a naming convention and a Terraform module so every role is created the same safe way, never by hand.

Why they askTests whether you can build the paved road, not just migrate what exists.

Masterstroke answer

I would publish a reusable workflow that every team calls, so the standard lives in one place. On pull request: checkout, build, unit tests, SonarQube quality gate, Checkmarx SAST scan, container build, Trivy image scan, and results posted back to the PR. Nothing merges with a failed gate. On merge to main: rebuild, push the image to ECR tagged with the commit SHA, never latest, then deploy to dev automatically. Staging needs one approval through a GitHub environment. Prod needs approval plus a soak period in staging. AWS access is OIDC only. Caching for dependencies and Docker layers keeps PR checks under ten minutes, because slow pipelines kill adoption. Teams pass in their own build commands as inputs, but the security steps are not optional. When we improve the scan step, every team gets it on the next run without touching their repos.

Key points to hit

  • Reusable workflow = one standard, org-wide updates
  • PR: build, test, SonarQube, Checkmarx, image scan, gate on results
  • Main: SHA-tagged image to ECR, auto dev, approved staging/prod
  • GitHub environments for approval gates
  • Keep PR checks under 10 minutes with caching

Likely follow-ups

How do you stop teams bypassing the standard?

Rulesets and required workflows at the org level. The security workflow runs whether the team includes it or not, and branch protection requires it to pass.

Why SHA tags instead of latest?

latest is not traceable. A SHA tag ties the running container to the exact commit, which matters for rollback and for audit in a regulated environment.

Why they askA bank will not run everything on public GitHub-hosted runners. This tests infrastructure depth.

Masterstroke answer

Two workable patterns on AWS. First, Actions Runner Controller, ARC, on EKS. It runs runners as pods and scales them up and down with job demand. Since the bank already runs EKS, this fits their skills, and ephemeral runners mean each job gets a clean pod that is destroyed after, which is good security hygiene. Second, EC2 auto scaling runners, for example the Philips terraform-aws-github-runner module, which spins up instances on webhook events. I would default to ARC on EKS here. Design points: runner groups to separate prod deploy runners from general build runners, images with the bank's approved toolchain baked in, runners in private subnets with egress through inspection, no public inbound needed because runners poll GitHub. And I would restrict which repos can use which runner group, so a sandbox repo cannot run jobs on the prod deploy runners.

Key points to hit

  • ARC on EKS: runners as auto-scaling ephemeral pods
  • Fits the bank's existing EKS skills
  • Runner groups separate prod deploy from general builds
  • Private subnets, outbound-only, hardened runner images
  • Restrict repo access to sensitive runner groups

Likely follow-ups

Why ephemeral runners?

A runner that persists between jobs can leak secrets or state from one job to the next. Ephemeral pods start clean and are destroyed after one job. In a bank that is the only defensible pattern.

GitHub-hosted vs self-hosted?

GitHub-hosted for open-source-style builds with no internal network need. Self-hosted for anything touching internal systems, private artifacts, or deployments. Most banks end up mostly self-hosted.

Why they askMigrations always produce these bugs. They want a calm, methodical answer.

Masterstroke answer

I compare the two runs side by side, not from memory. First, diff the logic: what did the ADO pipeline actually run versus what the converted workflow runs. The importer sometimes drops implicit ADO behavior, like predefined variables, checkout depth, or the working directory. Second, check the environment: ADO agents come with certain tools pre-installed and GitHub runners have a different set, so a version drift in Node, Java, or the AWS CLI is a very common cause. Third, check identity: the ADO service connection may have had broader IAM permissions than the new OIDC role, so the deploy fails or behaves differently under least privilege. Fourth, check variables and secrets: variable group values that never made it across, or an environment variable name that changed case. I fix it, then add the finding to the migration playbook so wave two never hits the same bug. Half the value of a pilot is collecting exactly these differences.

Key points to hit

  • Diff old and new pipeline logic side by side
  • Tool version drift between ADO agents and GitHub runners
  • OIDC role permissions vs old service connection permissions
  • Missing variable group values or renamed variables
  • Feed every finding back into the migration playbook

Likely follow-ups

What implicit ADO behaviors bite people?

Predefined variables like Build.BuildId, automatic checkout behavior, and the default working directory. GitHub has equivalents like github.run_number but names and values differ.

How do you prevent this class of bug?

Run the migrated pipeline in parallel with the ADO one for a week, deploying to a non-prod environment, and compare outputs before switching prod traffic.

Why they askSecurity question with a compliance angle. Banks care deeply here.

Masterstroke answer

Layered approach. First choice: no secret at all. OIDC to AWS removes the biggest one, cloud credentials. Second: application secrets live in AWS Secrets Manager, and the workflow reads them at deploy time with its OIDC role. That gives rotation and audit in one place. Third: what remains goes in GitHub secrets, set at environment level so a dev workflow cannot read prod secrets. GitHub masks them in logs, but I still tell teams never to echo secrets, because masking is best effort. Fourth: protect the supply chain. Pin third-party actions to a full commit SHA, not a tag, so a hijacked action version cannot steal secrets. Limit GITHUB_TOKEN permissions to read-only by default and grant write only where needed. And secret scanning plus push protection on the repos, so a leaked key is blocked before it lands in history.

Key points to hit

  • OIDC first: remove cloud credentials entirely
  • App secrets in AWS Secrets Manager, read at runtime
  • Environment-level GitHub secrets separate dev from prod
  • Pin actions to commit SHAs, restrict GITHUB_TOKEN
  • Secret scanning with push protection on

Likely follow-ups

Why pin actions to a SHA?

A tag like v2 can be moved to malicious code if the action repo is compromised. A full commit SHA cannot be moved. For a bank I would also keep an allow-list of approved actions.

How do secrets move from ADO variable groups?

Values cannot be exported, so it is a manual re-entry moment. I use it as a cleanup: anything unused dies, anything real moves to Secrets Manager with an owner and rotation policy.

Why they askShared templates are the hardest part of real migrations. This separates leads from seniors.

Masterstroke answer

Shared templates are the skeleton of the whole CI estate, so I migrate them first, before any team pipelines. I inventory which templates exist and which pipelines use them, straight from the audit report. Then I rebuild each one properly as a reusable workflow or composite action in a central repo, for example fhlbc/actions. I do not just auto-convert them, because this is the one chance to redesign the standard: fold the security scans in, add OIDC, remove dead parameters. I version them with tags, v1, v2, so teams pin a version and upgrades are deliberate. Then team pipeline conversions become simple, because most of their YAML was template calls, and those become one uses line pointing at the central repo. The importer supports custom transformers, so I write one per old template that rewrites it to the new central call automatically across every pipeline.

Key points to hit

  • Migrate shared templates first, they unblock everything
  • Rebuild deliberately as reusable workflows, do not blind-convert
  • Central repo, versioned with tags, teams pin versions
  • Fold security and OIDC into the new standard while rebuilding
  • Custom transformers auto-rewrite template calls org-wide

Likely follow-ups

How do teams upgrade template versions safely?

Dependabot can raise PRs when the central action releases a new version. Teams review and merge. Critical security fixes can be forced through required workflows.

What if two teams need different behavior?

Inputs with defaults. The reusable workflow takes parameters for the honest differences and refuses parameters for things that must stay standard, like skipping scans.

Why they askPractical optimization plus adoption thinking.

Masterstroke answer

Speed matters double during a migration, because the new platform gets judged against the old one on day one. If GitHub Actions feels slower than ADO, adoption stalls no matter how good the security story is. My approach: measure first, then fix the biggest block. Cache dependencies, npm, pip, Maven, and cache Docker layers with BuildKit. Run lint, tests, and scans in parallel jobs instead of one long chain. Use path filters so a docs change does not trigger a full build. Right-size runners, bigger for heavy builds. For monorepos, build only what changed. I set a budget: PR checks under ten minutes, deploys under fifteen. In a previous platform I got release cycles from two days down to fifteen minutes, and the lesson was that every minute cut from the feedback loop showed up directly in how willingly teams used the platform.

Key points to hit

  • New platform is judged on speed from day one
  • Cache dependencies and Docker layers
  • Parallelize jobs, path-filter unnecessary runs
  • Budget: PR under 10 min, deploy under 15
  • Fast feedback drives adoption, proven by experience

Likely follow-ups

Biggest single win usually?

Docker layer caching. Rebuilding unchanged layers wastes minutes every run. Registry-backed BuildKit cache typically cuts build time hard.

How do you keep pipelines fast over time?

Track run duration as a metric with an alert on regression, the same way you track test failures. Slowness creeps in silently otherwise.

Why they askTests modern deployment thinking and judgment about when to apply it.

Masterstroke answer

GitOps means Git is the single source of truth and an agent in the cluster, like ArgoCD, pulls the desired state and makes the cluster match it. The difference from push CI/CD: the pipeline never touches the cluster. It just updates a manifest in Git, and ArgoCD applies it. For a bank this has three strong points. Audit: every change to prod is a Git commit with an author, a reviewer, and a timestamp. Rollback: revert the commit and the cluster follows. Security: the CI system no longer holds cluster credentials, only the in-cluster agent does, which shrinks the attack surface. Since they run EKS, I would use it: GitHub Actions builds and scans the image, pushes to ECR, updates the tag in a deployment repo, and ArgoCD syncs it. Drift correction is a bonus, if someone hand-edits the cluster, ArgoCD puts it back and flags it.

Key points to hit

  • Git as source of truth, agent pulls state into the cluster
  • CI never needs cluster credentials, smaller attack surface
  • Audit trail and rollback are Git-native, ideal for a bank
  • GHA builds and updates manifests, ArgoCD syncs to EKS
  • Automatic drift detection and correction

Likely follow-ups

ArgoCD or Flux?

Both work. ArgoCD has a UI that helps during incidents and onboarding, which is why most enterprises pick it. Flux is lighter if a team wants everything as code with no UI.

Does GitOps fit the migration timeline?

I would not force both at once. Migrate to Actions first with a clean push model, then introduce ArgoCD as a phase two for the EKS workloads. One big change at a time.

DevSecOps & Security

Shift-left in practice: Checkmarx, SonarQube, Prisma Cloud, supply chain, compliance, and incident judgment. 9 questions

Why they askStraight from the JD. They want practice, not the slogan.

Masterstroke answer

Shift-left means finding security problems while the developer is still working on the code, not weeks later in a security review. In practice it is a chain of checks, each at the earliest point it can run. In the editor and pre-commit: secret scanning and linting. On every pull request: SAST with Checkmarx for code flaws, SonarQube for code quality gates, dependency scanning for known-vulnerable libraries, and container image scanning before anything is pushed. On infrastructure code: Checkov or tfsec on Terraform plans, so a public S3 bucket is blocked before it exists. The key implementation detail: these run inside the standard reusable workflow, so teams get them by default instead of opting in. And findings must land where developers live, as PR comments with a clear fix, not in a security tool nobody opens. If the feedback is fast and actionable, developers fix issues in minutes. If it is slow or noisy, they route around it.

Key points to hit

  • Find issues at the earliest possible point, ideally the PR
  • Chain: secrets scan, SAST, dependency scan, image scan, IaC scan
  • Checks live in the standard reusable workflow, on by default
  • Findings surface as PR comments with clear fixes
  • Fast, low-noise feedback or developers route around it

Likely follow-ups

How do you handle false positives?

Tune the rulesets early with the security team, allow documented suppressions with an expiry date, and track the false positive rate. A noisy gate gets ignored, which is worse than no gate.

Gate hard or warn?

Gate hard on criticals and highs, warn on the rest at the start, and tighten over time. Blocking everything on day one just creates pressure to bypass.

Why they askThey name both tools in the JD. Show integration thinking even if your hands-on depth is elsewhere.

Masterstroke answer

Both vendors ship official GitHub Actions, so integration is a step in the reusable workflow. SonarQube: the scan step runs after tests so it can ingest coverage, then the quality gate check fails the job if the gate fails, and results show on the PR. I would define one bank-standard quality gate centrally rather than letting every team invent their own. Checkmarx: the CxFlow or Checkmarx One action triggers the SAST scan on PR, publishes findings as PR annotations, and breaks the build on high severity. Two design choices matter at enterprise scale. First, scan policies live centrally with the security team, not per repo, so standards cannot drift. Second, incremental scans on PRs for speed, full scans nightly on main, because a full Checkmarx scan on a big codebase is too slow for the PR loop. To be straightforward: I have integrated SAST and quality gates into pipelines throughout my career, and my admin-level depth on Checkmarx specifically is something I would build quickly in the first weeks, with the security team.

Key points to hit

  • Both have official actions, live in the reusable workflow

Why they askThe JD names Podman specifically. Short, honest, technically correct.

Masterstroke answer

Both build and run OCI-standard containers, so images, registries, Kubernetes, and the scanning chain are identical. The difference is architecture. Docker runs a central root daemon; every container operation goes through it, so the daemon is a single point of failure and a privileged attack surface. Podman is daemonless: containers are child processes of the user, and it runs rootless by default, so a container escape lands as an unprivileged user, not root. That is why security-conscious shops, and Red Hat environments, standardize on Podman for build hosts and developer machines. The CLI is intentionally compatible, alias docker to podman and most things work. Practical notes: docker-compose needs podman-compose or pods, and some CI tooling still assumes the Docker socket, so build steps may need Buildah or rootless adjustments. My production depth is Docker, and I have worked with Podman at the evaluation level; the concepts transfer directly and I would be candid about that split.

Key points to hit

  • Both OCI: images, registries, K8s identical
  • Docker: central root daemon; Podman: daemonless, rootless by default
