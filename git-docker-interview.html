Git & Docker Interview Questions

Advanced Git branching, rebasing, conflict resolution, and internals — plus Docker architecture, multi-stage builds, networking, security, and orchestration patterns.

🔀 Git Internals & Core Concepts
G1 – G10 Internals · Objects · Index

Understanding how Git stores data — blobs, trees, commits, and tags — lets you diagnose any situation and recover from disasters confidently.

G1What are the four Git object types and how are they related?
  • Blob: Stores raw file content (no filename, no metadata).
  • Tree: Maps filenames/directories to blobs and other trees — represents a directory snapshot.
  • Commit: Points to a root tree, parent commit(s), author, committer, and message.
  • Tag: Named pointer to a specific commit (annotated tags store extra metadata; lightweight tags are just refs).
Every object is content-addressed by its SHA-1 hash and stored in .git/objects/.
G2What is the difference between the working directory, the staging area (index), and the repository?
  • Working directory: The files you see and edit on disk.
  • Staging area (index): A prepared snapshot of what will go into the next commit. Lives in .git/index.
  • Repository (.git): The permanent object database of all commits, trees, and blobs.
git add moves changes from working directory → index. git commit moves the index → repository.
G3What does git reset do, and what is the difference between --soft, --mixed, and --hard?
git reset moves the current branch pointer (HEAD) to a target commit:
  • --soft: Moves HEAD only. Index and working tree unchanged. Changes appear as staged.
  • --mixed (default): Moves HEAD and resets the index. Changes appear as unstaged modifications.
  • --hard: Moves HEAD, resets index, and overwrites the working tree. Changes are discarded — use with caution.
G4What is the difference between git reset and git revert?
  • git reset: Rewrites history by moving the branch pointer backward. Dangerous on shared branches — force-push required, disrupts collaborators.
  • git revert: Creates a new commit that undoes a previous commit's changes. History is preserved — safe on shared branches.
Use revert on main; use reset only on local/private branches.
G5What is git stash and when would you use it?
git stash saves your uncommitted changes (staged and unstaged) onto a stack and reverts the working directory to the last commit — letting you switch context cleanly.
  • git stash push -m "message" — save with a label.
  • git stash list — view all stashes.
  • git stash pop — apply the latest stash and drop it from the stack.
  • git stash apply stash@{2} — apply a specific stash without dropping it.
Use case: You're mid-feature when an urgent hotfix arrives — stash, fix, push, then pop your stash.
G6What is the difference between git fetch and git pull?
  • git fetch: Downloads remote commits and updates remote-tracking refs (origin/main) but does not touch your local branch or working tree. Safe — just updates your knowledge of the remote.
  • git pull: Fetch + merge (or rebase if configured). Immediately integrates remote changes into your current branch.
Best practice: git fetch then inspect before merging; or configure git pull --rebase to keep a linear history.
G7What is a detached HEAD state and how do you recover from it?
Normally HEAD points to a branch. In detached HEAD state, HEAD points directly to a commit SHA — no branch tracks new commits you make.

How it happens: git checkout <commit-sha> or git checkout v1.0 (a tag).

Recovery:
  • If you made commits in detached HEAD: git branch new-branch-name to save them, then checkout the branch.
  • If you made no commits: simply git checkout main.
G8How does git cherry-pick work and when should you use it?
git cherry-pick <commit-sha> applies the changes introduced by a specific commit onto the current branch as a new commit (different SHA, same diff).

Use cases:
  • Backporting a bug fix to a release branch without merging the whole feature branch.
  • Pulling a single commit from a colleague's branch.
Caution: Creates duplicate commits — if both branches ever merge, you'll have conflict noise. Use sparingly.
G9What is git reflog and how can it save you?
git reflog records every time HEAD moves — including after reset --hard, amends, and rebases. It's a local safety net that retains entries for 90 days by default.

Recovery scenario: You accidentally ran git reset --hard HEAD~3 and lost 3 commits. Run git reflog, find the SHA before the reset, then git checkout -b recovery <sha>.
G10What is the difference between a fast-forward merge and a three-way merge?
  • Fast-forward merge: Possible when the target branch has not diverged from the source. Git simply moves the branch pointer forward — no merge commit created. Linear history.
  • Three-way merge: Required when both branches have diverged. Git finds the common ancestor and combines the two sets of changes, creating a merge commit with two parents.
Force a merge commit even when FF is possible: git merge --no-ff feature — useful to preserve branch history.
Quick mental model: Git is a content-addressed filesystem. Every state of every file is stored once by hash. Branches are just 40-byte files containing a SHA. Virtually nothing is ever truly deleted until git gc runs.
🌿 Branching Strategies & Workflows
G11 – G18 GitFlow · Trunk · PRs

Branching strategy choice directly impacts release velocity, merge conflict frequency, and CI/CD reliability. Knowing the trade-offs is essential for senior roles.

G11Compare GitFlow, GitHub Flow, and Trunk-Based Development.
StrategyBranchesRelease ModelBest For
GitFlowmain, develop, feature/*, release/*, hotfix/*Scheduled/versioned releasesSoftware products with distinct versions
GitHub Flowmain + short-lived feature branchesContinuous deployment from mainWeb apps, SaaS — deploy on every merge
Trunk-BasedSingle trunk (main); feature flags hide WIPMultiple deploys per dayHigh-velocity teams with strong CI
G12What is git rebase and how does it differ from merge?
git rebase base-branch re-applies your commits on top of the base branch one by one, rewriting their SHAs — producing a linear history.

Merge creates a merge commit preserving the exact history of both branches.

Golden rule of rebase: Never rebase commits that have been pushed to a shared remote branch — it rewrites SHAs and will force everyone else to reconcile diverged history.
G13What is an interactive rebase and what can you do with it?
git rebase -i HEAD~N opens an editor listing the last N commits. You can:
  • pick: Keep a commit as-is.
  • squash / fixup: Combine commit with the previous one (squash prompts for new message; fixup silently discards the message).
  • reword: Change a commit message.
  • edit: Pause at a commit to amend files or split it into multiple commits.
  • drop: Delete a commit entirely.
  • reorder: Change the order of commits.
Use before opening a PR to clean up "WIP", "fix typo", "oops" commits into a coherent story.
G14How do you resolve a merge conflict?
  1. git status — identify conflicted files.
  2. Open each file; find conflict markers (<<<<<<<, =======, >>>>>>>).
  3. Edit the file to the desired final state and remove all markers.
  4. git add <file> to mark resolved.
  5. git merge --continue (or git rebase --continue) to finish.
Use a merge tool: git mergetool (integrates with VS Code, vimdiff, IntelliJ). Configure with git config --global merge.tool vscode.
G15What is git bisect and how do you use it?
git bisect performs a binary search through commit history to find the exact commit that introduced a bug.
  • git bisect start
  • git bisect bad — mark current commit as broken.
  • git bisect good v2.3.0 — mark a known-good commit.
  • Git checks out the midpoint; you test and run git bisect good or git bisect bad.
  • After O(log N) steps Git identifies the culprit commit.
  • git bisect reset returns you to the original HEAD.
Can be automated: git bisect run ./test.sh — script returns exit 0 for good, non-zero for bad.
G16How do you squash multiple commits before merging a PR?
Two approaches:
  • Interactive rebase: git rebase -i origin/main, mark all but the first commit as squash, then force-push: git push --force-with-lease.
  • Merge squash: git merge --squash feature-branch on main — stages all changes as a single uncommitted diff; then commit once. This doesn't rewrite the feature branch itself.
--force-with-lease is safer than --force: it rejects the push if someone else has pushed to the branch since you last fetched.
G17What are Git hooks and give practical examples?
Git hooks are shell scripts in .git/hooks/ that run automatically at lifecycle events.
  • pre-commit: Run linters (ESLint, Black) and block commit if they fail.
  • commit-msg: Enforce commit message format (e.g., conventional commits pattern).
  • pre-push: Run tests before allowing git push.
  • post-merge: Auto-run npm install if package-lock.json changed.
Use Husky (Node.js) or pre-commit (Python) to manage hooks in version control so the whole team shares them.
G18What is git worktree and when is it useful?
git worktree add ../hotfix hotfix/v2.1 creates an additional working directory linked to the same repository but checked out to a different branch — without stashing or switching branches.

Use cases:
  • Review a PR while still working on a feature — two terminals, two branches, one repo clone.
  • Run a slow build on a release branch without interrupting active development.
Rebase vs Merge decision: Use rebase to maintain a clean linear history on your local feature branch before pushing. Use merge commits on shared long-lived branches (develop, main) to preserve the true history of integrations.
⚡ Advanced Git — Performance, Submodules & Monorepos
G19 – G26 Submodules · LFS · Monorepos

Large-scale Git usage introduces challenges around repository size, dependency management across repos, and tooling for monorepo architectures.

G19What is Git LFS (Large File Storage) and when do you need it?
Git stores every version of every file in .git/objects/. Large binary files (videos, datasets, compiled artifacts) bloat the repo permanently.

Git LFS replaces large files with lightweight text pointers in the repo; actual binary content lives on a remote LFS server. The working tree shows the real file — only the store is offloaded.

git lfs track "*.psd" → updates .gitattributes. Then commit and push normally.
G20What are Git submodules vs git subtree, and which should you prefer?
  • Submodules (.gitmodules): A pointer to a specific commit in another repository. The sub-repo stays separate. Downside: Complex UX — developers must remember git submodule update --init --recursive; detached HEAD in submodule; CI friction.
  • Git subtree: Merges another repo's history into a subdirectory. The parent repo is self-contained. Downside: History is mixed; pushing back to the remote subtree is a manual step.
Prefer subtree for teams new to this pattern; prefer submodules when the dependency is truly external and must track upstream changes independently.
G21How do you handle secrets accidentally committed to Git?
Assume the secret is compromised — rotate it immediately. Then remove from history:
  • BFG Repo Cleaner (fast): bfg --delete-files secrets.txt then git push --force.
  • git filter-repo (official replacement for filter-branch): git filter-repo --path secrets.txt --invert-paths.
Prevention: Use git-secrets or pre-commit hooks to scan for secret patterns before commit. Add secrets to .gitignore. Use environment variables or Vault/Secrets Manager instead of files.
G22What is shallow cloning and when is it useful in CI/CD?
git clone --depth 1 <url> downloads only the latest commit rather than the full history — drastically reducing clone time and disk usage for large repos.

CI/CD benefit: Each pipeline run clones fresh — shallow clones can cut clone time from minutes to seconds.

Limitation: Commands that require history (git log, git bisect, git describe) won't work correctly. Deepen with git fetch --unshallow if needed.
G23How do you sign commits with GPG and why does it matter?
Anyone can set any name/email as a Git committer — commit attribution is unauthenticated by default.

GPG-signed commits prove the commit was authored by the holder of a specific private key:
  • Configure: git config --global user.signingkey <key-id>
  • Sign commits: git commit -S -m "message"
  • Auto-sign: git config --global commit.gpgsign true
GitHub/GitLab show a "Verified" badge. Required in high-compliance environments (SLSA level 2+, SOC 2 code integrity controls).
G24What is git sparse-checkout and how does it help with monorepos?
In a monorepo with hundreds of packages, most developers only need a subset of the tree. git sparse-checkout configures Git to only populate specific paths in the working directory while still having access to the full history.

git sparse-checkout set packages/api packages/shared

Combined with partial clones (--filter=blob:none), you avoid downloading blobs you never open — making monorepo development on slow connections practical.
G25How do you use git blame effectively for code archaeology?
git blame <file> annotates every line with the last commit SHA, author, and date that changed it.

Advanced usage:
  • git blame -L 20,40 app.py — blame only lines 20–40.
  • git blame -w — ignore whitespace-only changes.
  • git blame -M — detect lines moved within a file.
  • git blame -C — detect lines copied from other files in the same commit.
  • Once you find a commit SHA, git show <sha> reveals the full context of why the change was made.
G26What is git gc and when should you run it?
git gc (garbage collection) runs housekeeping tasks:
  • Packs loose objects into packfiles for efficiency.
  • Prunes objects no longer reachable from any ref (after the 2-week grace period).
  • Expires old reflog entries.
Git runs git gc --auto automatically after certain operations. Manually useful after removing large files with BFG/filter-repo to actually reclaim disk space. git gc --aggressive does a more thorough but slower repack.
Monorepo tooling: For very large monorepos, pair Git sparse-checkout with tools like Nx, Turborepo, or Bazel for affected-only builds, and git-cliff or semantic-release for per-package changelogs.
🐳 Docker Architecture & Core Concepts
D1 – D10 Engine · Images · Containers

Docker's architecture — daemon, client, containerd, runc, and the image layer model — underpins every operational and debugging question you'll face.

D1Explain Docker's architecture: daemon, containerd, and runc.
  • Docker CLI: The client that sends commands to the daemon via REST API.
  • Docker daemon (dockerd): Manages images, volumes, networks, and delegates container lifecycle to containerd.
  • containerd: An industry-standard container runtime that manages image pull, storage, and container execution. Can run independently of Docker.
  • runc: A low-level OCI-compliant runtime that actually creates and runs containers using Linux namespaces and cgroups. containerd calls runc.
This layered design allows Kubernetes to use containerd directly, bypassing dockerd entirely.
D2What is the difference between an image and a container?
  • Image: A read-only, layered template built from a Dockerfile. Stored in a registry. Immutable — the same image produces the same container every time.
  • Container: A running (or stopped) instance of an image. Has a thin read-write layer on top of the image layers. Ephemeral by default — write layer is discarded when the container is removed.
Analogy: Image = class definition; Container = object instance.
D3How does the Union File System / overlay2 layer model work?
Docker images are built as a stack of read-only layers. Each Dockerfile instruction that changes the filesystem creates a new layer. The overlay2 storage driver merges these layers into a unified view using Linux's OverlayFS.

When a container runs, a thin read-write layer (container layer) is added on top. Changes write here via copy-on-write (CoW) — a file is copied from a lower layer to the writable layer on first modification.

Benefit: Layers are shared across images and containers. 10 containers from the same image share the same read-only layers — only 10 thin writable layers are created.
D4What is the difference between COPY and ADD in a Dockerfile?
  • COPY: Copies files/directories from the build context to the image. Simple, explicit, preferred.
  • ADD: Does everything COPY does, plus: auto-extracts local .tar archives, and can fetch from remote URLs.
Best practice: Always prefer COPY. The auto-extract behavior of ADD is surprising and the URL-fetching bypasses layer caching usefully only in rare cases. Use RUN curl | tar explicitly if you need remote files.
D5What is the difference between CMD and ENTRYPOINT?
  • ENTRYPOINT: Sets the executable that always runs. Cannot be overridden from docker run (only with --entrypoint flag).
  • CMD: Sets default arguments passed to the ENTRYPOINT (or the default command if no ENTRYPOINT is set). Easily overridden by arguments after the image name in docker run.
Best pattern: ENTRYPOINT ["node", "server.js"] + CMD ["--port", "3000"] — the CMD provides overridable defaults; the entrypoint stays fixed.

exec form (["cmd", "arg"]) is preferred over shell form (cmd arg) — exec form runs the process directly without a shell, so signals (SIGTERM) are delivered correctly for graceful shutdown.
D6What is docker compose and how does it differ from running containers manually?
Docker Compose defines multi-container applications in a compose.yaml file — services, networks, volumes, environment variables, and dependencies in one place.

Key benefits over manual docker run:
  • Single command startup: docker compose up -d.
  • Service dependency ordering with depends_on.
  • Shared networks created automatically — services reach each other by service name DNS.
  • Named volumes persist across restarts.
  • Easy teardown: docker compose down -v.
D7What is a Docker volume and how does it differ from a bind mount?
  • Volume (-v mydata:/app/data): Docker-managed storage in /var/lib/docker/volumes/. Portable, can be backed up with docker volume commands. Survives container removal. Best for persistent application data (databases).
  • Bind mount (-v /host/path:/container/path): Mounts a specific host directory into the container. Depends on host filesystem structure. Best for development (mount source code to enable hot-reload).
  • tmpfs mount: In-memory only — data is lost when container stops. Best for sensitive data that must not touch disk.
D8How do you debug a running container?
  • docker logs <container> -f — stream stdout/stderr.
  • docker exec -it <container> sh — open an interactive shell inside the container.
  • docker inspect <container> — JSON dump of all configuration, network settings, mounts, and environment variables.
  • docker stats — live CPU, memory, network, and disk I/O metrics.
  • docker top <container> — running processes inside the container.
  • Distroless / scratch images have no shell — use docker debug <container> (Docker Desktop feature) or ephemeral debug sidecar containers (kubectl debug in Kubernetes).
D9What is the .dockerignore file and why is it important?
The build context (everything sent to the Docker daemon for a build) includes all files in the directory by default. .dockerignore excludes files/directories from the context — similar to .gitignore.

Why it matters:
  • Smaller build context → faster docker build (less data transferred to daemon).
  • Prevents secrets (.env, *.pem) from accidentally ending up in the image.
  • Prevents node_modules/ or .git/ bloating the image.
Always add: .git, node_modules, *.log, .env*, Dockerfile, README.md.
D10What does it mean for a container to be stateless, and how do you persist data?
A stateless container stores no data in its writable layer — all state lives externally. When the container is replaced (upgrade, crash), no data is lost because it was never inside the container.

Persistence strategies:
  • Docker Volumes: For databases, file uploads, any mutable app data.
  • External services: S3 for files, RDS/managed DBs for relational data, Redis for sessions.
  • Environment config: Pass configuration via environment variables or mounted config files — not baked into the image.
This aligns with the 12-Factor App principle: treat backing services as attached resources.
Key distinction: Containers are cattle, not pets. Design them to be replaceable at any time. Any data that matters lives in a volume or external service — never only in the container's writable layer.
🏗️ Dockerfile Best Practices & Multi-Stage Builds
D11 – D18 Multi-Stage · Caching · Image Size

Optimized Dockerfiles produce small, cacheable, secure images — directly impacting CI/CD speed, registry costs, and attack surface.

D11What is a multi-stage build and what problem does it solve?
A multi-stage build uses multiple FROM instructions in a single Dockerfile. Early stages handle building/compiling; only the final stage produces the runtime image — you COPY --from=builder only the compiled artifacts.

Problem solved: Without multi-stage builds, the runtime image would include the compiler, build tools, test frameworks, and source code — often 10–50× larger than necessary.

Example:
  • Stage 1 (builder): FROM node:20 AS builder → npm ci → npm run build
  • Stage 2 (runtime): FROM node:20-alpine → COPY --from=builder /app/dist ./dist
Result: Final image has only the Alpine base + compiled dist — no node_modules, no source, no dev dependencies.
D12How does Docker layer caching work and how do you optimize it?
Each Dockerfile instruction produces a layer. Docker caches layers and reuses them if the instruction and all its inputs are identical. Once a layer is invalidated, all subsequent layers are rebuilt.

Optimization principle — put stable things first, changing things last:
  • Copy dependency manifests first, install dependencies, then copy source code.
  • Bad: COPY . . then RUN npm ci — any source change rebuilds the expensive install step.
  • Good: COPY package*.json . → RUN npm ci → COPY . . — the install step is cached as long as package.json is unchanged.
Use --mount=type=cache (BuildKit) to persist package manager caches across builds without committing them to layers.
D13How do you reduce Docker image size?
  • Use minimal base images: alpine (~5 MB) vs ubuntu (~80 MB). Use distroless (Google) for production — no shell, no package manager, minimal attack surface.
  • Multi-stage builds: Ship only compiled artifacts, not build tools.
  • Combine RUN commands: Each RUN is a layer. Chain with && and clean up in the same layer: RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*
  • .dockerignore: Exclude test files, docs, .git.
  • Avoid installing unnecessary packages: apt-get install --no-install-recommends.
  • Analyze layers: Use dive (CLI tool) to inspect each layer's size contribution.
D14What is BuildKit and what does it add over classic Docker build?
BuildKit is Docker's next-generation build engine (default since Docker 23). Key improvements:
  • Parallel stage execution: Independent stages in a multi-stage build run concurrently.
  • Cache mounts (--mount=type=cache): Persistent package manager cache that doesn't bloat image layers.
  • Secret mounts (--mount=type=secret): Inject secrets at build time without baking them into any layer.
  • SSH agent forwarding (--mount=type=ssh): Use SSH keys for private repo access during build without embedding keys.
  • Inline cache: Push cache metadata to a registry for faster CI builds.
Enable: DOCKER_BUILDKIT=1 docker build . or use docker buildx build.
D15How do you handle environment-specific configuration in Docker images?
Principle: Build the image once; configure it at runtime — never bake environment-specific values into the image.
  • Environment variables: docker run -e DB_HOST=prod.db.internal or via compose.yaml env_file.
  • Config files mounted at runtime: -v /etc/myapp/config.yaml:/app/config.yaml:ro.
  • Secrets manager: Container entrypoint fetches secrets from AWS Secrets Manager / Vault at startup.
  • Build ARGs: ARG is for build-time variables only (e.g., version numbers). Do not use ARG for secrets — ARG values are visible in docker history.
D16What is image tagging strategy for production?
  • Never rely on :latest in production — it's mutable, making deployments non-reproducible and rollbacks impossible.
  • Semantic versions: myapp:2.3.1 — explicit, rollback-friendly.
  • Git SHA: myapp:a3f8c12 — immutable, ties image to exact code state. Preferred in CI/CD.
  • Multi-tag: Tag the same image as myapp:2.3.1, myapp:2.3, myapp:2, and myapp:latest for flexible referencing.
  • Digest pinning: myapp@sha256:abc123... — absolutely immutable, even if the tag is moved.
D17How do you scan Docker images for vulnerabilities?
  • Docker Scout / docker scan: docker scout cves myapp:latest — built-in, scans against CVE databases.
  • Trivy (Aqua Security): trivy image myapp:latest — fast, open-source, scans OS packages and language dependencies (npm, pip, go.sum). Widely used in CI pipelines.
  • Snyk: snyk container test myapp:latest — integrates with GitHub PRs for inline vulnerability comments.
  • Grype (Anchore): SBOM-aware scanner.
Best practice: Scan in CI before pushing to registry; block builds with Critical/High CVEs; rescan images periodically even after deployment (new CVEs emerge).
D18What is an SBOM (Software Bill of Materials) in the context of Docker?
An SBOM is a machine-readable inventory of all software components, libraries, and their versions packaged in an image — like an ingredient list for your container.

Why it matters (supply chain security):
  • When a new CVE is disclosed (e.g., Log4Shell), you can immediately query your SBOMs to find every image containing that library.
  • Required by executive orders and frameworks like SLSA, NIST SSDF, and CISA guidance.
Generate: docker buildx build --sbom=true --output type=registry . or with syft myapp:latest. Stored as OCI attestation alongside the image in the registry.
Cache invalidation rule: Every line in a Dockerfile that changes (or follows a changed line) re-executes. Sort instructions: OS deps → dependency manifests → dependency install → source copy → build. This maximizes cache hits in CI where source changes are frequent but dependencies are not.
🌐 Docker Networking
D19 – D24 bridge · host · overlay · DNS

Understanding Docker network drivers and how container-to-container and container-to-host communication works is essential for both debugging and production architecture.

D19Explain Docker's network drivers: bridge, host, none, overlay, and macvlan.
DriverDescriptionUse Case
bridgePrivate virtual network on the host; containers communicate by IP or DNS name on user-defined bridgesDefault for single-host multi-container apps (Compose)
hostContainer shares the host's network namespace — no NAT, no port mappingHigh-performance apps; removes networking overhead
noneContainer has only a loopback interface — completely isolatedBatch jobs, security-sensitive processing

D20How does DNS resolution work between containers in a user-defined bridge network?
Docker's embedded DNS server (running at 127.0.0.11 inside containers) automatically resolves container names and service names to their internal IP addresses — but only on user-defined networks.

The default bridge network does not support automatic DNS — containers must use --link (deprecated) or IP addresses. Always create a named network in Compose or with docker network create.
D21What is port publishing and how does it work internally?
docker run -p 8080:80 myapp maps host port 8080 → container port 80 via iptables NAT rules that Docker manages automatically.

Variants:
  • -p 8080:80 — bind on all host interfaces (0.0.0.0).
  • -p 127.0.0.1:8080:80 — bind on localhost only (more secure for dev tools).
  • -p 80 — expose port 80 on a random host port (use docker port to find it).
EXPOSE in Dockerfile is documentation only — it does not actually publish the port. You must still use -p at runtime.
D22How do you isolate containers on different networks in a Compose app?
Define multiple networks in compose.yaml and attach each service only to the networks it needs:
  • frontend service on public network only — reachable from the proxy.
  • api service on both public and private networks — bridge between tiers.
  • db service on private network only — never reachable from the public-facing tier directly.
This provides network segmentation without any firewall rules — containers simply cannot resolve each other's names if they share no network.
D23When would you use --network host and what are the risks?
Host networking bypasses Docker's NAT and virtual bridge — the container process binds directly to host ports with no mapping overhead.

Use cases: Network monitoring tools that must see raw host traffic; extremely latency-sensitive apps where the NAT overhead matters.

Risks:
  • No network isolation — a compromised container can directly reach every service on the host.
  • Port conflicts — container and host must not bind the same port.
  • Not available on Docker Desktop (macOS/Windows) — only works on Linux.
D24How do you debug container networking issues?
  • docker network ls — list networks.
  • docker network inspect <network> — see connected containers and their IPs.
  • docker exec -it <container> ping <other-service> — test DNS resolution and reachability.
  • docker exec -it <container> nslookup <service-name> — test DNS directly.
  • Install curl/wget in the image during development to test HTTP endpoints from inside a container.
  • Use a temporary nicolaka/netshoot container attached to the target network — it includes tcpdump, netstat, traceroute, and more without modifying the target image.
Always use user-defined networks in Compose — never rely on the default bridge. User-defined networks provide automatic DNS, better isolation, and the ability to connect/disconnect containers at runtime without restart.
🔒 Docker Security, Resource Limits & Production Patterns
D25 – D34 Security · cgroups · Health · Orchestration

Running Docker securely in production requires understanding privilege escalation risks, resource constraints, health checks, and the role of Docker in a Kubernetes architecture.

D25Why should you never run containers as root, and how do you prevent it?
A process running as root inside a container maps to UID 0 on the host. If an attacker escapes the container namespace (via a kernel exploit), they have root on the host.

Prevention:
  • Create a non-root user in the Dockerfile: RUN addgroup -S app && adduser -S app -G app then USER app.
  • Use --user 1000:1000 flag at runtime to override even if the image didn't specify USER.
  • In Kubernetes: set runAsNonRoot: true and runAsUser: 1000 in the pod's securityContext.
  • Use --read-only filesystem + tmpfs mounts for writable paths to limit blast radius.
D26What are Linux capabilities in Docker and how do you use them?
Linux root privileges are divided into ~40 discrete capabilities (e.g., CAP_NET_BIND_SERVICE to bind port <1024, CAP_SYS_ADMIN for broad system operations). Docker grants containers a limited default set.

Principle of least privilege:
  • --cap-drop ALL — remove all capabilities from the container.
  • --cap-add NET_BIND_SERVICE — add back only what's needed.
Use --security-opt no-new-privileges:true to prevent processes from gaining additional privileges via setuid binaries.
D27How do you set CPU and memory limits on a container and why is it important?
Without limits, a single misbehaving container can starve all other containers and host processes of resources.

docker run --memory="512m" --memory-swap="512m" --cpus="1.5" myapp
  • --memory: Hard limit; container is OOM-killed if exceeded.
  • --memory-swap: Total memory + swap. Set equal to --memory to disable swap.
  • --cpus: CPU quota (1.5 = 150% of one core across all cores).
  • --cpu-shares: Relative weight for CPU scheduling when contention exists.
In Kubernetes, set resources.requests (scheduling hint) and resources.limits (enforcement) on every container.
D28What is a HEALTHCHECK in Docker and how does it affect container orchestration?
HEALTHCHECK in a Dockerfile defines a command Docker runs periodically to test if the container is healthy:

HEALTHCHECK --interval=30s --timeout=5s --retries=3 CMD curl -f http://localhost:8080/health || exit 1

Container states: starting → healthy | unhealthy.

Orchestration impact:
  • Docker Compose: depends_on: condition: service_healthy waits for the dependency to be healthy before starting dependent services.
  • Docker Swarm / Kubernetes: Unhealthy containers are automatically restarted or replaced. Traffic is not routed to unhealthy instances.
D29How do you handle graceful shutdown in a Docker container?
docker stop sends SIGTERM to PID 1. After a timeout (default 10s), it sends SIGKILL. Your app must handle SIGTERM to drain connections and clean up.

Common pitfall: Shell form CMD/ENTRYPOINT (CMD node server.js) wraps the process in /bin/sh -c — signals are sent to the shell, not Node. The shell doesn't forward signals → app gets killed immediately by SIGKILL.

Fix: Use exec form: CMD ["node", "server.js"] — Node becomes PID 1 and receives SIGTERM directly. Or use dumb-init/tini as an init process that forwards signals properly.

D31What is a Docker Content Trust (DCT) and image signing?
Docker Content Trust uses Notary (based on The Update Framework) to sign images and verify their integrity before pulling.

DOCKER_CONTENT_TRUST=1 docker pull myrepo/myimage:1.0

With DCT enabled: Docker verifies the publisher's signature — unsigned or tampered images are refused. Keys are stored in ~/.docker/trust/.

Modern alternative: Sigstore / Cosign — keyless signing using short-lived certificates tied to OIDC identity (GitHub Actions identity, for example). Increasingly adopted for SLSA supply chain compliance.
D32What is a rootless Docker and why is it more secure?
Standard Docker daemon runs as root on the host. If the daemon is compromised, the attacker has root.

Rootless Docker runs both the daemon and containers as a non-root user, using user namespaces to map container UID 0 → an unprivileged host UID.

Benefits:
  • Daemon compromise does not grant host root.
  • Containers can't mount host paths that require root.
Limitations: Some features unavailable (e.g., --network host, --privileged). Performance overhead from user namespace mapping.
D33How do you implement a CI/CD pipeline that builds and deploys Docker images?
  1. Build: docker buildx build --platform linux/amd64,linux/arm64 -t myrepo/myapp:$GIT_SHA .
  2. Scan: trivy image myrepo/myapp:$GIT_SHA — fail build on Critical CVEs.
  3. Test: docker run --rm myrepo/myapp:$GIT_SHA npm test.
  4. Push: docker push myrepo/myapp:$GIT_SHA and :latest.
  5. Sign: cosign sign myrepo/myapp:$GIT_SHA.
  6. Deploy: Update Kubernetes manifest or Helm chart with new image tag; kubectl rollout status to verify.
Use GitHub Actions / GitLab CI with Docker layer cache (--cache-from type=registry) to avoid rebuilding unchanged layers on every run.
D34What is the difference between docker save/load and docker export/import?
  • docker save / load: Exports/imports a full image with all layers, tags, and history. Preserves the complete image structure. Use to transfer images between registries or air-gapped environments: docker save myapp:1.0 | gzip > myapp.tar.gz → docker load < myapp.tar.gz.
  • docker export / import: Exports/imports a running or stopped container's filesystem as a flat tarball — layers are squashed, history is lost, no metadata. Results in a slightly smaller image but loses caching benefits. Rarely used in production workflows.
Docker Security Checklist
✓ Non-root USER in Dockerfile  ·  ✓ Read-only root filesystem (--read-only)  ·  ✓ Drop all capabilities, add only required  ·  ✓ No secrets in ENV or image layers  ·  ✓ Minimal base image (distroless/alpine)  ·  ✓ Image scanning in CI (Trivy/Snyk)  ·  ✓ Resource limits (CPU + memory)  ·  ✓ HEALTHCHECK defined  ·  ✓ No :latest tag in production  ·  ✓ .dockerignore excludes secrets & .git
Container escape mitigations: Keep the host kernel patched, use seccomp profiles to restrict syscalls, enable AppArmor/SELinux profiles, avoid --privileged mode entirely in production, and use gVisor or Kata Containers for hardware-level isolation on multi-tenant workloads.
