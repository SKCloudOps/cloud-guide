Highly Available E-Commerce Architecture

Global, low-latency AWS design

Interviewer

How would you design a highly available and fault-tolerant e-commerce application on AWS?

The candidate first clarified the requirements. The application is global, must be low latency, must be fast for users in locations such as Mumbai, and must treat security as a top priority.

He proposed a three-tier architecture with public, application, and database layers. For global performance, CloudFront would be used as the CDN layer. For data that must be close to users, DynamoDB Global Tables or cross-region database replication would be considered, depending on the data model.

The application would be split into microservices such as cart, catalog, reviews, feedback, payments, and customer support. EKS would host these services, with deployments spread across regions where needed. Kubernetes autoscaling would handle traffic spikes during sale periods or festivals.

Secrets Manager would store sensitive values such as payment gateway credentials and API keys. Systems Manager Parameter Store could hold less sensitive configuration such as endpoint URLs. S3 would be used for logs, backups, and durable storage. CloudWatch, CloudTrail, VPC Flow Logs, IAM least privilege, NAT gateways, and security groups would complete the operational and security baseline.

CDN, Caching, And Data Layer Choices

Static and database caching

Interviewer

CloudFront handles static caching. How would you cache database-driven content?

The candidate explained that the answer depends on the type and criticality of data. If the application uses NoSQL, DynamoDB Global Tables can provide low-latency multi-region reads with minimal operational overhead.

For relational databases such as MySQL or PostgreSQL, RDS read replicas or cross-region replicas can reduce read pressure and improve regional access. For frequently accessed data, ElastiCache Redis can sit in front of the database to reduce query latency.

He also called out cost control. Very old or rarely accessed data should not always be stored in cache, because memory-based caching can become expensive. If users can tolerate a one- or two-second delay for rarely accessed historical data, replicas may be a better fit than ElastiCache.

ElastiCacheRedisRDS ReplicasDynamoDB

EKS Versus ECS

Choosing the right container platform

Interviewer

Why choose EKS instead of ECS for this application?

The candidate described ECS as a simpler AWS-native container platform that works well for smaller services, batch workloads, or applications that do not need deep Kubernetes control.

He chose EKS for this scenario because the application is global, service-heavy, and requires more control over deployment, scaling, and operations. With EKS, the team can standardize deployments using Kubernetes manifests, Helm, pipelines, and GitOps practices. This reduces drift when the same application must run across multiple regions.

He also noted that EKS can help when some workloads remain on-premises or when hybrid Kubernetes management is needed for sensitive or regulated workloads.

Disaster Recovery Tradeoffs

Balancing uptime, data loss, and cost

Interviewer

How would you keep the application running if the primary database or EKS cluster failed?

The candidate framed disaster recovery around two questions: how critical the application is, and how much cost the business can accept. The lower the tolerance for downtime or data loss, the higher the cost of the DR design.

For less critical workloads, a cold recovery model can create infrastructure only after a failure, but this has higher recovery time and possible data loss. For moderately critical systems, global managed services, database replicas, and multi-region Kubernetes capacity can reduce recovery time. For mission-critical systems, a warm or active standby environment in another region can receive traffic through Route 53 or load-balancer health checks when the primary region fails.

Follow-up

For a cost-sensitive e-commerce platform, what would you make highly available first?

The candidate proposed splitting the platform by business criticality. Order creation, user registration, and payment flows should receive stronger DR coverage, such as warm replicas or ready-to-serve regional capacity.

Less critical services, such as feedback, reviews, and complaint workflows, can use a lower-cost cold recovery model. This approach protects revenue-critical paths while controlling infrastructure spend.

CI/CD And GitOps Flow

Application and infrastructure delivery

Interviewer

How would you build a CI/CD architecture for this e-commerce platform?

The candidate said tool choice should follow the customer's current ecosystem. If the code is in GitHub, GitHub Actions is a natural fit. If the organization uses GitLab, GitLab CI/CD is appropriate. If the customer wants AWS-native services, AWS CodePipeline and related tools can be considered.

For the application pipeline, code would be linted and tested first. Then container images would be built and pushed to Amazon ECR. Because the platform runs on Kubernetes, Helm and Argo CD would be used for GitOps-based deployment to EKS.

For infrastructure, Terraform would run through the pipeline. The pipeline would format and validate Terraform, generate a plan, and require review or manual approval before applying changes in sensitive environments.

Secrets, Access, And Pipeline Controls

Managing credentials and deployment permissions

Interviewer

How should secrets and AWS access be handled in CI/CD?

The candidate explained that CI/CD platforms provide secret storage, but long-lived credentials should be avoided wherever possible. Pipelines should use IAM roles, scoped permissions, and short-lived access patterns.

For deployments, the pipeline should assume the required role and only access the target account or environment it needs. Secrets required by applications should be stored in managed secret services instead of being hardcoded in repositories or scripts.

Production deployments should include approval gates, especially when Terraform changes or high-impact application releases are involved.

Ingress And API Gateway

Routing traffic into Kubernetes and APIs

Interviewer

Would ingress be part of this Kubernetes architecture?

Yes. The candidate said that some APIs could be managed through API Gateway, while Kubernetes-hosted services and front-end traffic could use ingress. In AWS, ingress can provision or integrate with an Application Load Balancer to route requests to services inside EKS.

The exact split depends on the application. API Gateway is useful for API management, authorization, throttling, and centralized API controls. Ingress is useful for Kubernetes-native routing to services running inside the cluster.

Kubernetes Upgrade Story

Handling EKS upgrades with limited downtime

Interviewer

Can you describe a challenging DevOps task you handled?

The candidate described upgrading around eight Kubernetes clusters, each with roughly ten nodes and many running pods. The goal was to perform version upgrades with as little downtime as possible.

He explained that Kubernetes control-plane upgrades must move step by step through supported versions. Node groups can sometimes move more flexibly, but compatibility rules still matter. Before a major upgrade, the team should verify Helm-managed deployments, confirm that the cluster state has not drifted from deployment definitions, take backups and snapshots, and prepare rollback steps.

Terraform Drift Management

Keeping cloud state and code aligned

Interviewer

Have you faced drift between Terraform code and actual cloud resources?

The candidate explained that drift usually happens when someone changes resources manually in the console. Terraform then sees a mismatch between the state file, the code, and the real infrastructure.

Depending on the resource, the fix may involve importing the resource into Terraform state, correcting the configuration, reverting the manual change, or recreating the resource. The stronger solution is process control: restrict manual access, require justification for temporary access, log all manual activity, and run Terraform through version-controlled pipelines.

Terraform StateDriftImportPipeline

Emergency Production Changes

Balancing speed and discipline during incidents

Interviewer

If production is down and a manual AWS console change would fix it fastest, what would you do?

The candidate said his first preference is still to follow the defined process and make the change through infrastructure as code. That keeps the environment consistent and reduces long-term risk.

However, if the issue is extremely critical and every minute matters, a manual change may be justified. In that case, the change must be logged, communicated, reviewed, and later brought back under Terraform control through import, code updates, or a follow-up production release.

IncidentManual ChangeTerraform SyncPost-Incident Cleanup
Follow-up

Would you use Terraform for infrastructure that will not change for five years?

The candidate said yes. Even one-time infrastructure should be created through code because people may forget why it exists, who created it, and whether it is still needed.

Infrastructure as code provides documentation, repeatability, ownership, and a clear configuration history. The interviewer noted that manual creation could also be a valid choice in some organizations, but the candidate strongly preferred IaC.

Terraform Structure For Multi-Account AWS

Landing zone and team workflows

Interviewer

How would you structure Terraform for hundreds of AWS accounts?

The candidate proposed a dedicated repository for AWS Organizations, Control Tower, and account-level governance. Accounts would be grouped by purpose, such as logging, networking, security, applications, backups, and cost management.

For application infrastructure, he preferred reusable modules and environment-specific configuration. The same Terraform code should promote from dev to UAT to production, with differences supplied through environment-specific tfvars files or variables. Account IDs, instance sizes, URLs, and environment values should be passed through configuration rather than duplicated code.

ModulestfvarsLanding ZoneMulti-Account
Interviewer

How can multiple DevOps engineers work on the same Terraform repository without blocking each other?

The candidate said remote state and state locking are essential, but they can become a bottleneck when many engineers work at the same time. If every engineer waits on the same lock, productivity drops.

For development environments, he suggested Terraform workspaces so each engineer or merge request can have a separate state file. This allows parallel testing without affecting other engineers. The tradeoff is that temporary resources can create noise and cost, so cleanup automation is important after changes are merged or abandoned.

Follow-up

Are these Terraform Cloud workspaces or open-source Terraform workspaces?

The candidate clarified that he meant open-source Terraform workspaces with a remote backend such as S3. The workspace is selected locally, but the state is stored remotely in the backend.

This means another engineer can switch to the same workspace and continue the work if needed, because the state is not trapped on a developer laptop.

Open Source TerraformS3 BackendRemote State

AI, MCP, And The Future Of DevOps

How AI may change daily work

Interviewer

How do you think AI and MCP will affect DevOps work over the next six months?

The candidate said AI will not replace skilled engineers by itself. AI output depends heavily on prompts and context, and it can be wrong. Engineers still need enough knowledge to verify suggestions and prevent mistakes.

For skilled engineers, AI can reduce the time required for routine work. A task that once took days may take hours if AI can generate a starting point and the engineer can review, correct, and adapt it.

He expects more AI agents to appear inside CI/CD and operations workflows. For example, an agent could inspect failed pipeline logs, identify the likely cause, suggest a fix, reduce container image size, monitor Kubernetes health, or recommend pod restarts. This points toward AIOps and more automated operational workflows.

Interviewer

Would you give AI agents write access to AWS or Kubernetes?

The interviewer said he is currently comfortable giving LLMs or MCP tools read access so they can inspect infrastructure and suggest improvements. He is not yet comfortable giving them write access to terminate or modify production infrastructure.

The candidate responded that trust may increase over time. A year ago, many teams were not comfortable giving AI tools even read access. In the future, with better controls and governance, some teams may allow carefully scoped write access.
